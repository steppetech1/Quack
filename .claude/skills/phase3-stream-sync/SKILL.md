# Работа по ТЗ Фазы 3 в трёх потоках

Источник правды — `documentation/ТЗ Фаза 3 (единое).md` (в тексте скилла и в заметках его называют `PHASE3_UNIFIED_TZ.md`). Перед работой прочитай из него §7.1 (потоки), §7.2 (швы и гейты), §7.3 (владение файлами), §7.4 (ветки) и разделы своих WP. Состояние работы — в `backend/PHASE3_NOTES.md`, для потока A ещё и `documentation/phase3-stream-a-handoff.md`.

## 1. Определи поток и стоп-точку

1. Узнай поток разработчика (A, B или C). Если не сказано — спроси один раз.
2. Возьми порядок пакетов своего потока из §7.1.
3. **Стоп-точка** — ближайшее из трёх:
   - конец текущего WP (зелёный набор проверок, коммиты `red` и `green`);
   - шов из §7.2, который выдаёт твой поток и которого ждёт другой;
   - гейт G0–G4, условия которого теперь выполнены.
4. Делай работу строго до стоп-точки. Следующий WP не начинай, даже если он ясен. Назови стоп-точку разработчику в начале («Делаю WP3.1–3.2, стоп на конце WP3.2»).

## 2. Границы зоны

- Правь только файлы своего потока из §7.3.
- Исключения — пять случаев из §7.3 (WP1.2, WP2.1, WP6.2, WP11.4, WP12), и только если разработчик подтвердил, что владелец зоны предупреждён.
- Общие файлы (`config.py`, `kinds.py`, `redis.py`, `errors.py`) — только в своём блоке `# --- stream X ---` или по просьбе владельца.
- `manifest.json` и `openapi.json` руками не правь.
- Не делай того, что ТЗ не называет, и ничего из §2.2.
- Нужна правка чужого файла — не делай её. Опиши в сигнале, что и кому нужно.
- Спорное место ТЗ — класс C (§0.4): выбери вариант, запиши в журнал (`backend/PHASE3_NOTES.md`, раздел своего потока) и вынеси в сигнал.

## 3. Когда пушить

Push в рабочую ветку потока разрешён всегда. **Имя ветки — `phase-3-<поток>-<тема>`** (например `phase-3-a-wp33`), а не `phase-3/<поток>-<тема>` из §7.4: ветка `phase-3` уже существует, и git не позволяет создать `phase-3/…` (решение D-C-001, подтверждено владельцем). Сообщи разработчику, что пора пушить и открывать PR в `phase-3`, если верно любое:

| Триггер | Что сделать |
| :--- | :--- |
| Зелёный WP (коммит `green`) | Push ветки. PR — если после него есть потребитель в другом потоке |
| Готов шов, которого ждут (S1–S11) | Push и PR сразу, до конца WP: сигнатуры и тесты Этапа I достаточно |
| Условия гейта выполнены | PR в `phase-3`, сообщить остальным потокам |
| Конец рабочего дня | Push ветки, даже красной (`WIP`), чтобы работу видели |
| Нужна правка чужой зоны или решение класса C | Push текущего состояния, вопрос — в сигнал |
| Найден блокер для другого потока | Push исправления отдельным маленьким PR |

В `phase-3` сливается только зелёная ветка: `ruff check`, `ruff format --check`, `pyright`, `pytest` на самом слитом коммите. Красные тесты Этапа II коммить в свою ветку, не в `phase-3`: тесты, которые ещё красные, держи в отдельном файле и отдельной ветке и переноси в основной файл, когда они позеленеют. В `main` не сливать никогда.

## 4. Сигнал разработчику (обязателен в конце)

Закончив до стоп-точки, ответь блоком:

```
СИГНАЛ
Поток / WP: …
Сделано: … (тесты: N зелёных, M красных)
Стоп-точка: … Дальше по ТЗ: …
Твои действия:
  1. push: ветка …
  2. PR в phase-3: да/нет, ревью у потока …
  3. сообщить потоку …: …
Разблокировано: шов/гейт … (кто ждал)
Нужно от владельца (класс C): … или «нет»
Не проверено / риски: …
```

Правила сигнала: действия — по одному глаголу и по порядку; если действий нет, напиши «действий нет, можно продолжать с …»; не пиши «готово», если стоят красные тесты или непроверенные [ПРОВЕРИТЬ]. Правило команды: в сообщениях указывай, **какие проверки на каком коммите прогнаны и с каким итогом**.

## 5. Практика, выработанная на потоке A

- **Коммиты.** `backend/CLAUDE.md`: коммитить и пушить только по просьбе разработчика; автор — настроенный в репозитории пользователь; без `Co-authored-by` и упоминаний ИИ.
- **Тесты не ослабляются.** Менять утверждения существующих тестов можно только в случаях §8.9; для каждой правки сделай «проверку на неверной реализации» (временно сломай код и убедись, что тест падает) и запиши в «Правки тестов».
- **Тестовая инфраструктура.** Нужны три контейнера (`backend/README.md`: `quack-test-pg` :55432, `quack-test-neo4j` :57687, `quack-test-redis` :56379) и `QUACK_TEST_REQUIRE_INFRA=1`. Без них тесты молча пропускаются. **Два `pytest` одновременно не запускай:** общая тестовая БД даёт ложные падения.
- **Слои пакетов (`T-A6`, §4.1).** `quack.jobs` и другие пакеты ядра не импортируют `quack.ops`, `quack.runtime`, `quack.cli`, `quack.api.app`; код, которому это нужно, живёт в слое сборки (`quack/ops/`).
- **Слияние PR.** `gh pr merge <N> --merge` (merge-коммит сохраняет коммиты `red` и `green`). Перед слиянием подтяни свежий `phase-3` в свою ветку merge-коммитом (историю опубликованных веток не переписывать) и перепрогони полный набор.
- **Конфликты.** `tests/support/resources.py::build_job_context` — версия потока B; `openapi.json` и `manifest.json` не править руками.
