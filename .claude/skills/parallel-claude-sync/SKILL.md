Используй, когда разработчик называет свой поток или зону, говорит «продолжай по ТЗ», «что дальше», «закончил пакет», «пушить ли», «разбери PR/issues», просит связаться с другим потоком, или когда несколько Клодов работают по одному документу.

# Параллельная работа потоков по одному ТЗ

Источник правды — документы проекта (ТЗ, техдок, DevOps-док) и журнал решений. Ничего, чего там нет,
не существует: нет ответа — решай по ближайшему правилу документа и записывай (§2), а не додумывай «как принято».

Имена файлов ниже — по умолчанию. Проект задаёт свои в корневом `AGENT.md`; в Quack Фазы 4 это:
- `STATUS.md` — доска пакетов в корне репозитория;
- `documentation/Фаза 4 — решения (единое).md` — сводка решений;
- `backend/notes/<A|B|C>.md` — журналы решений потоков; архив до 2026-11-03 — `backend/PHASE4_NOTES.md`;
- `backend/TESTS.md` — политика тестов;
- `backend/scripts/dev/` — скрипты (`test_infra.sh`, `ct.sh`, `gh_watch.sh`);
- ветки потоков `phase-4-a`, `phase-4-b`, `phase-4-c`, интеграционная ветка `phase-4`.

---

## 1. Старт сессии — не больше 5 минут и 3 файлов

1. **`AGENT.md`**: свой поток и зона, список контрактных файлов, команды. Поток не назван — спроси один раз.
2. **`STATUS.md`**: строки своего потока и раздел «Следующие шаги». Первая незаблокированная строка — твой пакет.
3. **Файл решений**: раздел своего потока и швы. Архив заметок и ТЗ целиком **не читать**. Перед пакетом читай только его раздел ТЗ и названные там первоисточники (`Т-§`, `Д-§`). Детали решения — по его id.
4. **GitHub**, одним проходом:
   - `gh issue list --label to:<X> --state open` — ответить на всё, что можно ответить сразу;
   - открытые PR ветки потока: ревью, комментарии, CI;
   - `gh run list --branch phase-4-<x> --limit 1` — если красный, это первая задача.
5. **Фон**: `scripts/dev/gh_watch.sh <X>` (наблюдатель, §4) и `scripts/dev/test_infra.sh up <K>` (своя инфраструктура, §6).
6. Назови пакет и стоп-точку в одной строке. Дальше — работа, без пересказа прочитанного.

## 2. Зона, стоп-точка, решения

- **Зона.** Правишь только файлы своего потока. Контрактные файлы из `AGENT.md` правишь только в своём блоке (свой вид задачи, свой маршрут в e2e-реестре потока) и с ревью соседа. Нужна правка чужой зоны — issue (§4), не правка.
- **Стоп-точка** — ближайшее из трёх: пакет готов и проверен; шов, которого ждёт другой поток; ворота ТЗ. За стоп-точку не заходи. Пока ждёшь ответа или CI, бери следующий **незаблокированный** пакет из `STATUS.md`. Простоя быть не должно.
- **Решения.** Чего нет в документах, решай сам по ближайшему правилу ТЗ или техдока, если вопрос в твоей зоне или на шве, который ты ведёшь. Сверяй подробно, цитируй раздел. Запиши в журнал потока сверху, в момент решения:
  `### D-<X>-NNN. суть` → Класс, WP / место, Контекст, Решение, Почему (Т-§/Д-§/ТЗ), Обратимость, Тесты, Требует подтверждения владельцем: да/нет.
  Номер — следующий свободный по архиву и журналу. В той же волне добавь строку в файл решений.
- **Владелец** получает только необратимые решения, решения против буквы документа и красные линии ТЗ: issue по шаблону «Вопрос владельцу», метка `owner`. Работа не стоит: в issue пишешь, что взято по умолчанию до ответа.
- Ничего «заодно», ничего сверх ТЗ.

## 3. Ветки, коммиты, волны

- **Одна ветка на поток** (`phase-4-<x>`) живёт всю фазу. Пакеты — серии коммитов в ней. Если ТЗ требует, по два коммита: `phase4(wpN): tests (red)` → `phase4(wpN): implementation (green)`.
- **Отдельная ветка** (`phase-4-<x>-<тема>`) — только для шва, который другой поток ждёт прямо сейчас, или для правки чужой ветки по поручению.
- **Волна** = готовый пакет или 2–4 часа работы:
  1. `git fetch origin && git merge origin/phase-4` (без rebase, без `--force`);
  2. конфликт в генерируемых файлах — взять их версию и пересобрать; `uv.lock` — `uv lock`; конфликт в журнале невозможен (журналы раздельные);
  3. затронутые тесты плюс контрактные (§6) локально;
  4. обновить свои строки в `STATUS.md`;
  5. `git push`;
  6. PR `phase-4-<x>` → `phase-4` с меткой `wave`, если он ещё не открыт, затем `gh pr merge <N> --auto --merge`. PR вливается сам, когда обязательные проверки CI зелёные. Следующий push в ветку потока откроет новую волну.
- **Ревью соседа** — только если волна меняет контрактные файлы из `AGENT.md`: запрос в issue `to:<Y>` со ссылкой на PR. Соседний Клод делает ревью сабагентом Sonnet. Остальное — самопроверка и CI.
- Коммиты — по правилам проекта: в Quack в `backend/` без `Co-authored-by` и без упоминаний ИИ. В `main` — никогда, только владелец.

## 4. Общение — только GitHub, людям ничего не пересказывать

- **Вопрос или задача другому потоку** — issue по шаблону «Запрос другому потоку». Метка `to:<Y>`, плюс `blocking`, если без ответа стоит работа. Заголовок `[X → Y] суть`. Тело — исполнимая инструкция для чужого Клода, а не записка человеку:
  - что сделать;
  - где (файл, раздел ТЗ);
  - критерий готовности;
  - «опирайся только на документы; нет ответа — реши по правилу и запиши или верни вопрос сюда».
- **Ответ** — в том же issue. Сделано — закрывает спрашивающий. Ссылку на issue ставь в PR, ссылку на PR — в issue.
- **Ревью и замечания по строкам** — в PR (`gh pr review`). Если `--approve` недоступен — `--comment` с «Одобряю» в начале.
- **Наблюдатель**: `scripts/dev/gh_watch.sh <X> [интервал]` в фоне. Он завершается, как только меняется что-то из этого: issue `to:<X>`, PR веток потока (голова, ревью), CI ветки потока. На пробуждении: обработать каждое изменение, перезапустить наблюдателя, продолжить пакет. Если механику отдал сабагенту Haiku (§5), он сам чинит то, что можно чинить механически, и возвращает остальное.
- Блоки «A->B» в чате не пишутся: всё, что адресовано потоку, сразу уходит в issue.

## 5. Сабагенты: основная сессия ведёт, модели делают

Основная сессия (Opus) — **диспетчер**. Она выбирает пакеты волны, режет их на задачи, принимает решения на швах, проверяет результаты, сливает, пишет СИГНАЛ. Сама она пишет только то, что требует сквозного понимания: решения, контракты, конфликты на швах.

| Модель | Effort | Отдавать | Не отдавать |
| :-- | :-- | :-- | :-- |
| **Sonnet 5.5** | high | пакет ТЗ целиком (тесты, код, запись решения, строка STATUS); ревью PR соседа; доводка чужого PR до зелёного CI; разбор упавшего CI с правкой; сбор документов (решения, доска) | решения против буквы ТЗ; слияние в `phase-4` без проверки диспетчером |
| **Haiku 5.5** | high | наблюдатель GitHub и сводка событий; выжимка причины падения CI из лога; слияние `phase-4` в ветку, когда конфликт только в генерируемых файлах; пересборка `openapi.json` и манифестов; правки ruff/format; запросы `gh`, подсчёты, обновление строк STATUS по готовому описанию | код с логикой; ответы по ТЗ; ревью; решения |
| **Opus** (сама сессия) | — | швы и решения, план волны, проверка дифф + CI, окончательное слияние | механика, которую может сделать Haiku |

**Правила нарезки и запуска:**
1. Задачи волны независимы: не пишут в одни файлы, ни одной не нужен результат другой. Зависимые идут цепочкой в одном сабагенте.
2. Одновременно — до 4 сабагентов, которые гоняют тесты (память и инфраструктура), и сколько угодно без тестов. У каждого свой номер K (порты `56K01..03`, контейнеры `qa-K-*`), свой worktree (`git worktree add <scratchpad>/w<K> <ветка>`) и своя ветка или задача. Основной checkout не трогать никому.
3. **Бриф** — один общий файл в scratchpad на сессию (`BRIEF.md`). В нём: источники правды; worktree и пути; правила git (merge, генерируемые файлы, журнал); контрактные тесты и e2e-реестр; команды `test_infra.sh` и `ct.sh` с номером K; push и CI (`gh pr checks <N> --watch`); формат отчёта. Задание каждому сабагенту — 5–15 строк: пакет или PR, файлы, критерий готовности, номер K, «прочитай BRIEF.md».
4. **Решения**, которых нет в документах, сабагент записывает сам (`D-<поток>-NNN` в журнал потока) и перечисляет в отчёте.
5. **Отчёт** — не длиннее 12 строк: голова SHA, CI, что прогнано и итог, решения, что осталось диспетчеру. Диспетчер проверяет дифф и CI, а не верит отчёту на слово.
6. Сабагент не сливает в `phase-4`. Исключение — `--auto` на PR волны по прямому поручению.
7. Пока сабагенты работают, диспетчер не ждёт: отвечает в issues, принимает решения, готовит следующую волну.
8. Конфликты при слиянии нескольких готовых PR диспетчер снимает сразу локально: обе стороны, генерируемые файлы пересобираются, затронутое прогоняется. Потом сливает подряд, не дожидаясь нового CI на каждый, и смотрит один CI на итоговом `phase-4`. Красный — правка сразу следующей волной.

## 6. Тесты и CI

- **Своя инфраструктура**: `scripts/dev/test_infra.sh up <K>` / `down <K>`. Два прогона на одних базах ломают друг друга.
- **Локально** (`scripts/dev/ct.sh <K> <тесты>`): тесты пакета и тех, кто использует изменённый код, плюс контрактные (слои пакетов, изоляция SQL, сборка маршрутов, e2e-обход), если менялись пакеты, SQL или маршруты. Полный набор — один раз на волну, если изменение широкое. Обычно его делает CI.
- **CI — два слоя**:
  - быстрый (`fast`: ruff, pyright, тесты без инфраструктуры, контрактные) — на каждый push, включая ветки потоков;
  - полный (`backend` с Postgres, Neo4j, Redis) — на PR и на `phase-4`.

  Задачи по путям (например, `compute`) отчитываются всегда, но тяжёлые шаги пропускают без изменений в своих путях. Обязательные проверки `phase-4` — по `AGENT.md`.
- **Какой тест держать.** Тест остаётся, если ловит ошибку на шве, в изоляции учеников, в идемпотентности, в гонке, в проверке ответов или в обработке сбоев. Дубли и тесты снятого кода удаляются в пакете, который снимает код. Правила проекта — в `TESTS.md`.
- **Красный прогон** должен падать по делу: на неверной реализации, а не на импорте. Для исправления ошибки нужен тест, падающий на старом коде.
- **Новый маршрут** — сразу в e2e-реестр своего потока (`tests/e2e/routes/<x>.py`): тело, флаги, шаг обхода. Без этого CI красный у всех.
- В PR, issue и СИГНАЛЕ указывай: что прогнано, на каком SHA, итог, «не перепрогонять».

## 7. Что когда делать

| Событие | Действие |
| :-- | :-- |
| Пакет готов, затронутое зелёное | коммиты в ветку потока, строка STATUS, push; волна — по §3 |
| Другой поток ждёт шов | push сразу, PR с `--auto`, ответ в его issue со ссылкой |
| Пришло issue `to:<X>` | ответить или сделать в этой же сессии; механику — сабагенту |
| Красный CI своей ветки | первая задача: Haiku — выжимка лога, Sonnet или сам — правка |
| Нужна правка чужой зоны | issue `to:<Y>` с исполнимой инструкцией |
| Вопрос без ответа в документах | решение по правилу + запись D-…; владельцу — только §2 |
| Конец сессии | push всего, волна с `--auto`, STATUS обновлён, наблюдатель остановлен, `test_infra.sh down <K>` |

## 8. СИГНАЛ — в конце каждого ответа

```
СИГНАЛ
Поток: … | Ветка: phase-4-<x> @SHA | Волна: PR #N (auto-merge вкл/влит/нет)
Сделано: … (тесты: что, на каком SHA, итог; «не перепрогонять»)
Решения: D-… — одна строка на каждое, или «нет»
Стоп-точка: … Дальше: … (следующая строка STATUS)
Блокировка: нет, продолжаю с … / да — ждёт issue #N (поток, что именно)
GitHub: открыл …; ответил …; закрыл …
Владельцу: issue #N (owner) или «нет»
Риски: …
```

Строка «Блокировка» обязательна и однозначна. «Готово» не пишется, если есть красные тесты или непроверенные места.
