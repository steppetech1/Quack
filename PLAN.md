# PLAN

Rules for the agent (the orchestrator enforces them):
- The orchestrator picks the next open task. You do ONLY that task, you do NOT commit and do NOT edit this file.
- When you finish you write `.nightrun-result.json` in the worktree root: `{"status":"done","summary":"..."}` or
  `{"status":"blocked","reason":"..."}`; the orchestrator runs build/tests, reviews, commits and marks the task.
- Statuses (set only by the orchestrator): `[ ]` open, `[x]` done, `[!]` blocked, `[-]` skipped because a dependency is blocked.

Task format (one line per task, IDs are stable and never reused):
  - [ ] T-012 [hard] [tests-ok] Title. Done when: ... (files: src/auth/**) (after: T-010)
- Levels: `[easy]` = Claude Haiku first, `[medium]` = Claude Sonnet first, `[hard]` = Claude Opus first and always
  reviewed. No tag = medium. Each failed attempt moves the task one level up.
- `files:` is required: tasks run in parallel only when their `files:` do not overlap; a task without `files:` runs alone.
  For the agent it is a hint, not a hard limit (changes outside it force a review).
- `after:` the task waits until the listed tasks are `[x]`; if one is `[!]`, this task becomes `[-]`.
- `[tests-ok]` allows changing existing tests.
- `[no-tests]` skips the separate test author (docs, config, anything without a testable behavior). Every other task gets tests written first by a stronger model.
Every task needs a "Done when" criterion in its text. Checkbox syntax is reserved for real tasks: put notes in plain bullets.

## Project context
Quack backend (`backend/`): Python 3.12+, FastAPI, SQLAlchemy async + asyncpg (Postgres event log), Neo4j projection,
Redis, `uv`. This night implements Phase 2 Stream 2 (sessions, teacher turn loop over SSE, overlay, extractor,
checkpointer, degradation) strictly by `documentation/ТЗ Фаза 2 Поток 2 Сессия Учитель Экстрактор и Деградация.md`
(below: "ТЗ"). Build: `cd backend && uv run ruff check && uv run ruff format --check && uv run pyright`.
Tests: `cd backend && uv run pytest` (integration tests need Postgres/Neo4j/Redis containers, see backend/README.md).

- The turn commits all its events in one transaction (ТЗ §2.3.6) and `turn_started.user_seq` / `turn_completed.committed_seq` are known only after it, so the order is: lock -> context -> optional evaluation -> teacher call (or fallback) -> commit + enqueue -> stream the SSE (`token` chunks are slices of the final `reply_text`) -> release the lock.
