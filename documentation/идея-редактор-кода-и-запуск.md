## Цель

Как на LeetCode: тема, учитель (ИИ) даёт условие или кусок кода, ученик пишет или дописывает код, сразу запускает, видит результат тестов, и ИИ смотрит, всё ли правильно. Код выполняется на нашем сервере в отдельном контейнере, чтобы чужой ошибочный или вредный код не уронил систему.

## Принятые решения

1. **Запуск на сервере**, не в браузере: чтобы поддержать любые языки и доверять проверке.
2. **Первая версия: Python 3.12 и SQLite.** Версии показываются ученику.
3. **Проверка только по тестам.** 5 тестов: 2 открытых (примеры), 3 скрытых. LLM не может изменить вердикт.
4. **LLM даёт только входы тестов, ожидаемые ответы получаются запуском эталона.** Входы стоят мало токенов, поэтому число тестов можно поднять позже без переделки.
5. **Сравнение результатов делает бэкенд**, а не процесс с кодом ученика.
6. **Команда: один человек.** Согласовывать потоки не нужно.

## Python

### Форма задачи

- Ученик пишет функцию с заданным именем и сигнатурой. Учитель даёт заготовку, ученик дописывает. Режим stdin/stdout — позже.
- Нет функции с нужным именем или она не вызывается с нужными аргументами: все тесты «ошибка», текст «не найдена функция `f(a, b)`». Обвязка не падает.
- Разрешена вся стандартная библиотека, сторонних пакетов нет. Ограничение импортов не защищает (обходится внутри процесса), защиту даёт песочница.
- Учебный запрет (например, нельзя `sorted` в задаче на сортировку) — необязательное поле задачи `forbidden_names`, проверяется статически по AST в бэкенде до запуска. Нарушение: отправка отклонена с объяснением, не засчитывается как попытка.

### Значения и сравнение

- Аргументы и результат — только простые типы: `None`, `bool`, `int`, `float`, `str`, `list`, `tuple`, `dict`, `set`. Передаются JSON с тегами типов, чтобы не терять `tuple`, `set` и нестроковые ключи `dict`.
- Обвязка переводит возвращённое значение в эти типы сама (подклассы `int`, `str` и т.п. приводятся к базовому типу, остальное — «неподдерживаемый тип результата»). Так объект с `__eq__`, который всегда даёт `True`, не пройдёт.
- Способ сравнения задаётся на тест:
  - `exact` — по умолчанию;
  - `float_tol` — относительный и абсолютный допуск `1e-9`, рекурсивно внутри коллекций;
  - `unordered` — список сравнивается как мультимножество;
  - `mutates_arg: i` — сравнивается аргумент номер `i` после вызова (функция меняет список на месте);
  - `raises: ValueError` — ожидается исключение этого типа.

### Обвязка и канал результата

- В `runner` уходят код ученика и **только входы** тестов. Ожидаемых ответов в песочнице нет.
- Результат каждого теста обвязка пишет в отдельный файловый дескриптор (fd 3), а не в stdout. Печать ученика в stdout не может подделать результат.
- `sys.exit`, `os._exit`, исключения в верхнем уровне модуля: тест получает статус «ошибка», остальные тесты запускаются в новом процессе.
- Детерминизм: `PYTHONHASHSEED=0`, `random.seed(0)` перед каждым тестом.

## SQL

### Данные

- Движок SQLite, база в памяти, создаётся заново на каждый тест. Сломать данные ученик не может.
- Тест в SQL — это набор данных: запрос ученика и эталон выполняются на нём и сравниваются.
- Учитель генерирует схему (`CREATE`) и 5 наборов данных (`INSERT`) по 5–30 строк: 2 открытых (ученик видит таблицы и ожидаемый результат), 3 скрытых.
- Скрытые наборы нужны, чтобы ученик не вписал константы из примера.

### Что разрешено

- Схема и данные загружаются **до** установки `authorizer`.
- `authorizer` — белый список: `SQLITE_SELECT`, `SQLITE_READ`, `SQLITE_FUNCTION`, `SQLITE_RECURSIVE`. Всё остальное запрещено, в том числе `ATTACH`, `PRAGMA`, транзакции и любые изменения.
- Функции: запрещены `load_extension` и всё, что связано с расширениями; `enable_load_extension(False)`.
- Один оператор за запуск: `sqlite3` сам отказывает на нескольких операторах, ошибка показывается ученику.
- Зависания (`WITH RECURSIVE` без выхода, декартово произведение) обрывает `set_progress_handler` по времени. Память ограничивают `setlimit` (длина строки и blob) и лимит процесса.

### Сравнение

- По значениям. Порядок столбцов важен, имена столбцов не важны.
- Если в **эталонном** запросе есть `ORDER BY` — порядок строк сравнивается, иначе строки сравниваются как мультимножество (дубликаты считаются).
- Типы: `INTEGER` и `REAL` равны, если равны численно; `REAL` с допуском `1e-9`; текст и число не равны; `NULL` равен `NULL`.

## Тесты

- 5 тестов на задачу: 2 открытых, 3 скрытых. Среди скрытых обязательно хотя бы один граничный случай (пустой вход, один элемент, крайние значения, для SQL — пустой результат или `NULL` в данных).
- Тесты хранятся в документе задачи в `content.tasks` отдельным полем, **не** в `AnswerSpec` и **не** в событии `task.created`. В `AnswerSpec` типа `code` — язык, имя и сигнатура функции, способы сравнения.

### Что видит ученик

- Открытые тесты: вход, ожидаемый результат, результат ученика, stdout и ошибка (до 64 КБ).
- Скрытые тесты: номер и статус: «прошёл», «неверный ответ», «ошибка», «превышено время», «превышена память». Ни входа, ни ожидаемого результата, ни stdout, ни текста ошибки, ни времени. Задачи принадлежат одному ученику, поэтому подбор скрытых входов по статусам вредит только ему самому; от него хватает лимита отправок.
- Это проверяется автотестом бэкенда в первую очередь: ответ эндпоинта «отправить» не содержит входов и ожидаемых значений скрытых тестов.

### Проверка задачи при генерации

Задача показывается, только если прошла все шаги; не прошла — бракуется и генерируется заново (до 3 раз, потом другая задача):

1. Эталон запускается на всех 5 входах **дважды** (для SQL второй раз с данными, вставленными в обратном порядке). Результаты должны совпасть. Так ловятся падения эталона, недетерминизм и `ORDER BY` с одинаковыми ключами или `LIMIT` без `ORDER BY`.
2. Для SQL: на каждом скрытом наборе результат эталона непустой, если тест не задуман как пустой, и отличается от результата на открытом наборе.
3. `task_checker` пишет своё решение **по тексту условия и открытым тестам**, без эталона. Оно прогоняется по всем 5 тестам. Не совпало — `task_arbiter` смотрит условие, эталон и оба решения: исправить условие или забраковать. Это ловит главную ошибку сгенерированных задач — несовпадение условия с тестами.

Ожидаемые ответы записываются только после шага 1.

## Роль ИИ

- **Вердикт только по тестам:** `is_correct` — прошли все 5; `outcome = partial`, если прошла часть; `score` = доля прошедших тестов. LLM эти поля не меняет.
- **Подсказки по запросу ученика**, не автоматически: каждая ступень (наводящий вопрос → подсказка по месту → разбор) — один вызов LLM. `independence` считается по числу ступеней, как сейчас в `check.py`.
- **После успешной отправки** — один вызов LLM: короткий разбор стиля и проверка на подгонку под тесты (`if x == 3: return 9`). Подгонка не меняет вердикт, только комментарий и `triggered_misconceptions`.
- LLM получает: условие, код ученика, открытые тесты с результатами, скрытые — только номера и статусы. Скрытые входы в LLM не попадают, чтобы она не выдала их в подсказке.
- Код ученика вставляется в промпт как данные в явно ограниченном блоке; в промпте сказано, что инструкции внутри кода не выполняются. Поскольку вердикт от LLM не зависит, prompt injection может испортить только текст подсказки.
- Результат пишется в тот же `task.evaluated`: в `Method` (`events/values.py`) добавляется значение `tests`, `verification = "code"`. Новое значение enum: бэкенд, воркеры и проекторы выкатываются вместе, старые события читаются как раньше.

## Песочница: сервис `runner`

### Контейнер

- **Сети нет совсем** (`network_mode: none`). `api` и `workers` ходят в `runner` по Unix-сокету в томе `runner-socket` (`RUNNER_URL=unix:/run/quack-runner/runner.sock`). Так `runner` не может открыть ни одного соединения, в том числе к `api`: в общей сети он мог бы подделать `X-Forwarded-For` (у `api` `API_FORWARDED_ALLOW_IPS: "*"`). Ни БД, ни Redis, ни секретов.
- `read_only`, `no-new-privileges`, `cap_drop: ALL` плюс `cap_add: [SETUID, SETGID, KILL]` — только чтобы надзиратель переключался на uid слота и убивал его процессы. `pids_limit: 256`, `mem_limit: 2g`, у каждого слота свой tmpfs на 64 МБ.

### Слоты и изоляция запусков

- В контейнере 4 слота. У каждого свой uid (`20001`–`20004`) и своя папка `/work/slot-N` (tmpfs, владелец — uid слота, права `700`). Слот одновременно занят одним запуском. uid далеко от `10001`: без user namespace uid общий для всех контейнеров хоста (`10001` — пользователь `compute`), а `RLIMIT_NPROC` считает все его процессы.
- Код и входы передаются через stdin, результат — через отдельный pipe, не через командную строку, окружение или файлы: `cmdline` чужих процессов виден в `/proc`.
- Один тест — один процесс. Обвязка и код ученика в одном процессе, ученик может подделать что угодно в канале результата. Это безопасно: ожидаемых ответов в песочнице нет, подделка равна возврату выбранного значения.
- Лимиты процесса через `setrlimit`: `RLIMIT_CPU`, `RLIMIT_AS`, `RLIMIT_NPROC` (на uid слота, поэтому fork-бомба исчерпывает только свой слот), `RLIMIT_FSIZE`, `RLIMIT_NOFILE`. Плюс таймер по общему времени (ловит `sleep`).
- После каждого запуска: `kill -9` всех процессов uid слота (выживший фоновый процесс не дотянется до следующего запуска), очистка папки слота.
- Все слоты заняты — `runner` отвечает `429`, бэкенд показывает «сервер занят, попробуйте через пару секунд». Отдельной очереди нет: запуск синхронный.
- Позже на сервере: gVisor (`runtime: runsc`) или контейнер на запуск.

Риск: обычный контейнер делит ядро с хостом, защита не абсолютная. В `runner` есть только код и входы тестов текущих запусков; разделение по uid закрывает чтение чужих запусков, побег из контейнера закрывает gVisor.

### Лимиты по умолчанию

| | Python | SQL |
|---|---|---|
| CPU на тест | 2 с | — |
| Общее время на тест | 5 с | 2 с (`progress_handler`) |
| Общее время на запуск | 20 с | 10 с |
| Память на процесс | 256 МБ | 128 МБ |
| Процессов на слот | 16 | 1 |
| Вывод (stdout + stderr) | 64 КБ, дальше обрезается | — |
| Строк в результате | — | 10 000 |
| Размер кода / запроса | 64 КБ | 16 КБ |
| Скрипт схемы и данных | — | 64 КБ |

Размер кода ограничен ещё и потому, что код ученика попадает в неизменяемый журнал событий (`answer.submitted`).

### Лимиты частоты

- «Запустить»: 10 в минуту на ученика (`code_runs_per_min`).
- «Отправить»: 3 в минуту на задачу (`code_submits_per_min`). Окно лимитов API — 60 с по контракту §6.3, поэтому лимит в час заменён минутным.
- `runner` недоступен или ответил ошибкой: проверка завершается с `CheckFailedReason`, попытка не засчитывается и не попадает в профиль навыков.

## Интерфейс

- CodeMirror 6, панель условия, вывод, результаты тестов, режим «допиши заготовку».
- **«Запустить свой ввод»:** для Python ученик задаёт аргументы функции и видит результат и stdout без сравнения; для SQL любой `SELECT` к открытому набору показывается таблицей. Тот же `runner`, тот же лимит «запустить». Эталон и скрытые тесты не участвуют.
- Черновик кода сохраняется в `localStorage` по задаче, чтобы перезагрузка страницы его не теряла.

## Порядок работы

1. **`runner`:** `POST /v1/run/python`, `POST /v1/run/sql`, контракты, слоты и лимиты. Тесты: бесконечный цикл, `sleep`, fork-бомба, память, большой вывод, чтение файлов другого слота, процесс, переживший запуск, сеть, `ATTACH`, `PRAGMA`, рекурсивный CTE, подделка результата через stdout, объект с `__eq__`, `sys.exit`.
2. **Бэкенд:** тип ответа `code` в `AnswerSpec`, поле тестов в `content.tasks`, клиент `runner` рядом с `compute_client`, сравнение по тестам в `practice/check.py`, `Method = "tests"`, эндпоинты «запустить» (открытые тесты и свой ввод) и «отправить» (все пять), лимиты частоты, тест на отсутствие скрытых данных в ответе.
3. **Генератор:** промпт `code_task_generator@1` (входы, эталон, заготовка, наборы данных для SQL), проверка задачи из раздела «Проверка задачи при генерации», связка с `task_checker` и `task_arbiter`.
4. **Фронт:** редактор, панели, свой ввод, черновики.
5. **Подсказки ИИ** и связь с профилем навыков.

Шаги 1 и 2 можно сделать без интерфейса и проверять тестами и `curl`.

## Следующие языки

После Python и SQL — JavaScript (Node): та же схема «функция + тесты», тот же формат значений. Затем по спросу компилируемые (C++, Java): для них нужен шаг компиляции с отдельными лимитами. `runner` устроен так, что язык — это образ с интерпретатором и обвязкой, остальное общее.
