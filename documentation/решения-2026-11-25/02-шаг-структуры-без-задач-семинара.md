# Шаг структуры не ждёт задачи семинара

Ученик положил в один предмет 7 PDF семинаров. Все файлы дошли до статуса `read`, но много минут не появлялось новых узлов графа.

## Что было не так

1. Шаг `structure` задачи `material.parse` держит замок `domain:{id}`. Поэтому файлы одного предмета идут в граф строго по одному (так и задумано, порядок не менялся).
2. Внутри этого шага, после сверки графа (`reconcile_domain`, каждый пакет сверки сразу фиксирует свои события), шёл вызов модели `task_generator` на каждую задачу семинара. Одно `LLMUnavailableError` («provider timeout») валило весь шаг, а замок домена держался всё это время.
3. Повтор шага начинал его с начала. Строитель отвечал чуть иначе, и запись падала с `IdempotencyConflictError: idempotency key 'reconcile:topic.created:…' reused with a different payload`: ключ события тот же (id узла выводится из имени), а содержимое другое. Шаг падал снова и снова, пока не кончались попытки и материал не становился `failed`.

## Что изменено

**1. Повтор шага не спорит с тем, что уже записано** (`backend/quack/agents/reconcile.py`, `append_unwritten`).

- Перед записью пакета сверки берётся блокировка ученика (та же, что в `append_events`), смотрятся ключи пакета в журнале, события с уже записанным ключом не пишутся вовсе, остальные идут одним `append_events`. Всё в одной транзакции: пакет записывается целиком или никак (закон 7).
- Что в журнале, то и остаётся (закон 1). Id узла берётся из ключа события, поэтому результат повтора указывает на те же узлы, что создала первая попытка. Дублей нет (закон 5).
- `append_events` не менялся: конфликт ключа с другим содержимым там по-прежнему ошибка (тех. документ §2.3, п. 2). Правило действует только для записи сверки.
- Известный остаток: если при повторе строитель назвал для уже созданного навыка другую тему, эта тема создастся, а навык останется в старой. Тема окажется пустой (на хаб материала она не влияет: хаб берёт темы по навыкам).

**2. Задачи семинара вынесены в отдельную задачу `material.seminar_tasks`** (`backend/quack/materials/parse.py`, `backend/quack/ops/material_parse.py`).

- Шаг `structure` больше не зовёт модель задач. В той же транзакции, где пишутся `chunk.indexed`, хаб, `material.parsed` и статус `parsed`, он ставит в очередь `material.seminar_tasks`. В полезной нагрузке лежат готовые описания задач: ключ `seminar:{материал}:{n}`, условие, ответ материала, id навыка, имя навыка и темы, домен. Id навыков известны только этому шагу, поэтому правило диспетчера по событию тут не годится.
- У новой задачи свой замок `material:{id}:seminar_tasks`, замка домена нет. Класс P2, в плашке сессии не видна. Параллельность прежняя: `material_parser_concurrency`.
- Материал становится `parsed` сразу после шага структуры и таким остаётся при любом исходе задач. Хука «материал упал» у новой задачи нет.
- Внутри задачи уже созданные задачи пропускаются до обращения к модели (по `content.tasks`, id выводится из ключа). Одна упавшая задача не отбрасывает остальные: пробуются все, готовые остаются (у каждой своя транзакция), потом первая ошибка уходит наверх. Повтор доделывает только остаток. При `LLMUnavailableError` задача повторяется с растущей паузой, пока не кончатся `job_max_attempts`; материал от этого не страдает.

## Почему так

- Замок домена должен держать только запись структуры: это быстрая часть, и она не зависит от моделей задач.
- Падение второстепенной работы (задачи семинара) не должно отнимать у ученика граф и обрекать материал на `failed`.
- Повтор по тех. документу безопасен и после частичной записи (§22.3: ключи выведены из ключа задачи, повтор не создаёт дублей). Раньше это нарушалось тем, что строитель отвечает не одинаково.

## Не менялось

Ожидание порядка загрузки (`_wait_for_older`), логика хабов, векторы.

## Проверено

- `ruff check`, `ruff format --check`, `pyright` на изменённых файлах: чисто.
- `tests/jobs/test_rules_p4.py`, `tests/test_jobs_phase3.py` (без базы): 45 прошли.
- Тесты с базой (`tests/agents/test_reconcile.py`, `tests/materials`, `tests/practice/test_seminar_tasks.py`) написаны, но не запускались: набор тестовой инфраструктуры с номером K=10 скрипт не создаёт (допустимы 1..9). Их надо прогнать до слияния.
- Рабочие процессы стенда после слияния нужно перезапустить: пока они не подхватят обработчик `material.seminar_tasks`, такие задачи будут стоять в очереди.
