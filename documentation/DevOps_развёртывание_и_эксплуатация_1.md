## **0. О документе**

На хакатон вся серверная часть живёт на одном Contabo Cloud VPS 6 в EU (x86\\\_64, 6 vCPU, 12 ГБ, 100 ГБ NVMe) в Docker Compose и рассчитана на 50–100 одновременных учеников (Т-§22.1). Документ отвечает на вопрос «как система живёт на сервере»: где крутится, как собирается, выкатывается, бэкапится и чинится. Он раскрывает Т-§20 и Т-§22 и не меняет архитектуру ядра.

- **Что входит.** Окружения, топология, ресурсы, сборка и CI, выкатка и миграции, секреты, бэкапы, наблюдаемость, безопасность сервера, нагрузочный тест, runbook.
- **Что не входит.** Устройство памяти, моделей, агентов и входа учеников — технический документ. Интерфейс и тексты — продуктовый документ.
- **Главный — технический документ.** Если решение здесь противоречит закону ядра (Т-§1.1) или контракту техдоки, неверно решение здесь. Исключения — инфраструктурные решения из §0.2: они приняты в этом документе, и техдока правится под них.
- **Формат.** Цели с метриками и этапы P0/P1/P2 — как в PRD. Решения — как в техдоке: контракт, ориентир реализации, проверить; ПРИНЯТО, НА ОБСУЖДЕНИИ, ПОЗЖЕ; блоки «Почему» и «Отвергнуто».
- **Ссылки.** Т-§20.4 — раздел технического документа, П-14 — продуктового, §3 — этого. Из других документов этот документ упоминается как Д-§3.
- **Параметры.** Имена и стартовые значения из Т-§21.3 и Т-§22.11 здесь используются как есть. Новые параметры этого документа — §14.1.

**Статус.** ПРИНЯТО: сервер Contabo (§2), домен qvack.online (§3.1), хранилища (§8.4), публичный репозиторий kashanqq/Quack и публичные пакеты GHCR (§5.1), а также решения этой версии, перечисленные в §0.2. Остальное помечено на месте.

## **1. Цели и метрики**

Инфраструктура работает, если любой merge в main сам доходит до сервера, сервер держит 100 одновременных учеников, а потерю сервера мы переживаем без потери данных учеников. Всё остальное подчинено этим целям.

**Проблема.** Деплоя, CI и бэкапов пока нет. Журнал — единственный источник правды (Т-§1.1, закон 1), поэтому потеря диска Postgres — это потеря всей памяти об учениках.

| Цель | Метрика | Сейчас | К демо хакатона | Целевой профиль |
| :-- | :-- | :-- | :-- | :-- |
| Выкатка без ручных шагов | Время от merge в main до новой версии на сервере | Деплоя нет | ≤ 10 мин | ≤ 10 мин, через staging |
| Данные не теряются | RPO — сколько последних данных можно потерять | Бэкапов нет | ≤ 6 ч (Т-§22.10) | Минуты, архив WAL (Т-§20.4) |
| Сервер заменим | RTO — подъём на новой машине из бэкапа, включая пересборку Neo4j | Не измерено | ≤ 2 ч | ≤ 1 ч |
| Сервер держит нагрузку | Нагрузочный тест: 100 учеников с подменённым Meta API проходят в бюджетах §9.2 | Не измерено | Пройден до первых тестировщиков (§11) | 200 учеников (Т-§20.8) |
| Демо не падает | Доля времени, когда /healthz отвечает | Не измерено | 100% в окне демо | ≥ 99,5% за месяц |
| Ход учителя быстрый | teacher\_ttft\_p95\_ms (Т-§12.9) | Замеры на Wonder: 8,2 с при low и 15,4 с при high до первого токена (Т-§11.8) | 10 000 при low, 20 000 при high; статус «учитель думает» — за 300 мс (Т-§12.9) | По данным |
| Проекция не отстаёт | projector\_lag\_p95\_ms (Т-§21.3) | Не измерено | 500 | 500 |
| Инфраструктура дешёвая | Расход в месяц без моделей | 0 | ≤ €21,35: €16,35 за VPS, Object Storage и Auto Backup + до €5 на допы; R2, GHCR, мониторинг — бесплатные тарифы | Пересматривается по итогам хакатона |

Все числа в двух последних столбцах — стартовые (Т-§0.3). Первая задача по каждой строке «Не измерено» — замерить базу.

**Не цели.** Kubernetes, несколько серверов, высокая доступность, автомасштабирование и staging на хакатоне не делаем. Узкое место на нашем масштабе — лимиты и бюджет Meta API (Т-§1.5, Т-§11.4, Т-§22.5), а не сервер, и всё это стоило бы времени без пользы.

**Как пришли к решению.** Техдока закладывала Synteq (6 vCPU, 8 ГБ). Версия 1 этого документа выбрала Oracle Always Free A1, но больше суток Oracle не выдал инстанс (out of capacity). Сайт Synteq на момент решения не открывался, Hetzner Cost-Optimized (CX, CAX) недоступен для создания. Взяли платный x86 VPS с той же памятью, что у Oracle, и втрое большим числом ядер.

**Почему Contabo.**

- **Сервер нужен сейчас.** Contabo заказывается без ожидания квоты. OVH VPS-3 с теми же 12 ГБ тоже заказывается, но оплата из Казахстана не проверена.
- **12 ГБ и 6 ядер.** На 12 ГБ стек помещается с жёсткими лимитами (§4.1), compute\_workers остаётся стартовым 4 из Т-§21.3.
- **x86\\\_64.** Официальные образы и колёса Python (SymPy, PyMuPDF, OpenCV, Playwright с Chromium) в первую очередь собираются и проверяются на этой платформе.
- **Объектное хранилище в том же заказе.** 250 ГБ рядом с сервером под материалы учеников; бесплатные 10 ГБ R2 остаются под бэкапы.
- **Цена в бюджете:** €16,35 в месяц на команду с НДС, по чекауту на 1 месяц.

### **2.1 Окружения**

| Окружение | Где | Для чего | Данные |
| :-- | :-- | :-- | :-- |
| local | Ноутбук разработчика: тот же compose.yaml плюс compose.override.yaml | Разработка, ручная проверка | Синтетические |
| CI | GitHub Actions, сервисы через testcontainers | Тесты, линтеры, сборка образов | Синтетические |
| prod | Contabo Cloud VPS 6, фронтенд app.qvack.online на Vercel | Тестировщики хакатона и демо | Настоящие, с экраном согласия (Т-§19.4, П-14.6) |
| preview | Vercel, ветка preview на preview.qvack.online | Проверка интерфейса с входом против prod API | Тестовые аккаунты команды |
| PR-превью | Vercel, \*.vercel.app на каждый PR | Ревью вёрстки без входа | Нет: prod API их не принимает |

**Контракт.** Один набор образов и один compose.yaml в local и prod. Разница — только в .env и override-файле. Staging появляется на целевом профиле (§13).

- **Override-файл только локально.** Compose подхватывает compose.override.yaml автоматически и склеивает ports:, а убрать порт базового файла override не может. Поэтому порты отладки живут только в override, а на сервере такого файла нет.
- **Провайдер не зашит в код и скрипты.** Адрес сервера — секрет DEPLOY\_HOST (§7), эндпоинты хранилищ — S3\_ENDPOINT и BACKUP\_S3\_ENDPOINT. Переезд на другой VPS — смена этих значений и DNS, а не правка deploy.sh.

**Почему превью устроены так.** Вход живёт на cookie родительского домена, а фронтенд и API — на app. и api. одного домена (Т-§19.1). Превью на \*.vercel.app — другой сайт: cookie туда не придут, а пускать их в prod API значило бы открыть CORS для чужого домена. Поэтому PR-превью показывают вёрстку без API, а проверка с входом идёт на ветке preview, привязанной к preview.qvack.online. Её код пишет только команда.

- **CORS** — точный список источников: <https://app.qvack.online> и <https://preview.qvack.online>, с allow\_credentials. Без regex и без \*.vercel.app.
- **Git Fork Protection** в Vercel остаётся включённой: превью из форков не собираются без одобрения. Иначе чужой код из PR оказался бы на нашем домене рядом с cookie учеников.
- **Hobby** разрешает только некоммерческое использование; на хакатоне это так.

**Проверить.** Привязка домена к ветке на тарифе Hobby (Settings → Domains → Git Branch).

### **2.2 Два профиля нагрузки**

| Параметр | Хакатон (Т-§22) | Целевой (Т-§1.5, Т-§3.6) |
| :-- | :-- | :-- |
| Одновременных учеников | До 50–100 | До 1000 |
| Машина | Contabo Cloud VPS 6, 6 vCPU, 12 ГБ, x86\\\_64 | x86 VPS с большей памятью, выбор по итогам хакатона |
| Диск | 100 ГБ NVMe + Object Storage 250 ГБ | Отдельный том под данные |
| Записи событий | \\\~20 в секунду на 100 учеников (оценка по Т-§1.5), замерить | \\\~200 в секунду |
| Рост журнала | Замерить на нагрузочном тесте и первых сессиях | 15–20 ГБ в сутки на пике |
| compute\_workers | 4 | 4 |
| Окружений | prod | staging + prod |
| RPO | ≤ 6 ч, дампы | Минуты, архив WAL |

**Где упор на хакатоне.** 100 учеников × 2 хода в минуту × \\\~30 тыс. токенов — около 6 млн токенов в минуту при лимите Wonder 4 млн (Т-§22.5). Значит, на верхней границе мы упираемся в лимит Meta API раньше, чем в сервер; это закрывают реактивные лимиты и teacher\_fallback (Т-§22.5). Сервер должен выдержать 100 учеников с запасом по памяти: это проверяет нагрузочный тест (§11) с подменённым Meta API. Спайк подтвердил на ключе команды 3000 запросов и 4 млн токенов в минуту у Spark и у Wonder (Т-§11.3). Общий ли это лимит на обе модели, не доказано, поэтому ёмкость считается по одному лимиту на обе модели и по одному ключу: пул ключей в расчёт не входит (Т-§11.3).

| vCPU делятся с соседями и могут проседать | Лимиты CPU в §4.1 — потолки, а не резерв. Медленно при обычной нагрузке — сначала steal time (st в vmstat, §9.1) |
| Диск и сеть у Contabo по отзывам слабее Hetzner (первичных данных нет) | Замер задержки диска под Postgres до первых данных (§14.2); нагрузочный тест покажет, хватает ли |
| Задержка \\\~116 мс из Алматы до EU | Для хода учителя почти незаметна. Заметна на канвасе — замер на реальном WebSocket (§14.2) |
| Трафик «unlimited» под fair use | Для 100 учеников не опасно. Тяжёлые файлы отдаются из Object Storage по подписанным ссылкам, а не через сервер (§8.4) |
| Снапшоты и Auto Backup живут у того же провайдера и в том же аккаунте | Основной бэкап — дампы Postgres в R2 (§8.1). Auto Backup — второй слой для отката сервера целиком (§8.2) |
| Платёж через одного человека; неоплаченный сервер блокируют | Автопродление и напоминание (§10). Срок до блокировки — проверить (§14.2) |
| Объекты учеников и сервер в одном аккаунте | Потеря аккаунта уносит файлы, но не память: текст материалов по страницам в Postgres (Т-§3.1), Postgres бэкапится вне Contabo |

### **3.1 Вход трафика и домен**

**Контракт.**

- **Домен — qvack.online, ПРИНЯТО, куплен.** Фронтенд — app.qvack.online на Vercel, API — api.qvack.online на сервере, превью с входом — preview.qvack.online (§2.1). Cookie сессии ставится с Domain=qvack.online (Т-§19.1).
- **DNS — у Cloudflare без проксирования**, TTL записи api. ≤ 300 с, чтобы переезд по §8.3 не ждал кэша DNS. Записи SPF, DKIM и DMARC почтового сервиса — там же (§7).
- **Caddy принимает 80 и 443** и сам получает сертификаты. Порт 80 нужен для выдачи сертификата и редиректа на HTTPS.
- **SSE без буферизации.** Для Content-Type: text/event-stream Caddy сбрасывает буфер сам; flush\_interval -1 — подстраховка (Т-§1.10). Проверяется вручную до первых тестировщиков.
- **WebSocket канваса и компаньона** (Т-§1.6) — через тот же Caddy. Перезагрузка конфига Caddy рвёт долгие соединения, поэтому задан stream\_close\_delay; клиент переподключается и досылает неподтверждённые пачки штрихов (Т-§15.2).
- **Компаньон** открывается на телефоне по HTTPS — это требование getUserMedia (Т-§16.1), его закрывает тот же сертификат.

**Записи DNS** в Cloudflare. Все — «DNS only» (серое облако), без проксирования. Значения для Vercel и Resend берутся из их панелей: они зависят от проекта и региона.

| Имя | Тип | Значение | Зачем |
| :-- | :-- | :-- | :-- |
| api | A | IPv4 сервера, TTL 300 | API, SSE, WebSocket; Caddy получает сертификат |
| app | CNAME | Значение из Vercel → Settings → Domains | Фронтенд и компаньон |
| preview | CNAME | То же значение Vercel | Ветка preview (§2.1) |
| @ (qvack.online) | A | Адрес из Vercel | Редирект 308 на app.qvack.online в Vercel |
| www | CNAME | Значение из Vercel | Тот же редирект |
| resend.\_domainkey | TXT | Ключ DKIM из Resend | Подпись писем |
| send | MX | Значение из Resend | Возвраты писем (адрес отправителя конверта) |
| send | TXT | SPF из Resend (v=spf1 include:amazonses.com \~all) | SPF домена конверта |
| @ | TXT | v=spf1 -all | С корня домена почту не отправляем — чужие письма от qvack.online отклоняются |
| \_dmarc | TXT | v=DMARC1; p=none; rua=mailto:<ящик команды>, через неделю чистых отчётов — p=quarantine | Политика для подделок |
| @ | CAA | 0 issue "letsencrypt.org" | Сертификаты выдаёт только Let's Encrypt; Caddy закреплён на нём же (issuer acme), без запасного ZeroSSL |

- **AAAA для api не ставим.** Если она есть, Let's Encrypt и часть клиентов идут по IPv6, а IPv6 на сервере, в ufw и в Docker надо настраивать отдельно. Неработающий IPv6 значит невыданный сертификат и обрывы у части учеников.
- **Письма** уходят с адреса login@qvack.online; домен конверта — send.qvack.online. DMARC проходит по DKIM с d=qvack.online.
- **Не в DNS, но привязано к домену.** Google OIDC: redirect URI <https://api.qvack.online/auth/google/callback>, authorized domain qvack.online. CORS api и бакета — §2.1, §8.4. Cookie — Domain=qvack.online, Secure, HttpOnly, SameSite=Lax.
- **DNSSEC** включается в Cloudflare, DS-запись передаётся регистратору. Это ПОЗЖЕ, после того как всё остальное заработает: ошибка в DS кладёт весь домен.
- **Регистратор:** NS домена — на Cloudflare, автопродление включено, двухфакторный вход у плательщика. Истёкший домен ломает вход, cookie и почту одновременно.

**Отвергнуто — пока.** Cloudflare Tunnel или проксирование через Cloudflare. Это убирает настройку портов, но добавляет звено с собственными таймаутами (у прокси Cloudflare — 125 с ожидания ответа и 900 с простоя соединения) и буферизацией на двух самых чувствительных каналах — SSE хода и WebSocket канваса. Tunnel остаётся аварийным путём до активации VPS (§2.3).

### **3.2 Сети Docker**

**Ориентир реализации.**

| Сеть | Кто в ней | Выход в интернет |
| :-- | :-- | :-- |
| backend | Все сервисы | Нет (internal: true) |
| egress | caddy, api, workers, backup, alerts | Да, в любой адрес |

- **Кому нужен интернет.** api: Meta API, Modal, LangSmith, Object Storage, почтовый сервис, Google OIDC, бакет удалений R2. workers: Meta API, Modal, LangSmith, Object Storage, бакет удалений R2 (ежедневная сверка, §8.5). backup: R2 и heartbeat мониторинга. alerts: вебхук чата и heartbeat мониторинга. caddy: выдача сертификатов. projector и compute в интернет не ходят.
- **compute не видит сеть** (Т-§6.5, Т-§19.8). Файл для разбора скачивает workers из Object Storage и передаёт в compute в теле HTTP-запроса; результат возвращается ответом. Временные файлы compute пишет только в свой том /srv/quack/tmp.
- **Порты баз на сервере не публикуются.** Контейнер только в сети internal: true опубликовать порт не может. Отладка — docker compose exec (psql, cypher-shell) или SSH-туннель к IP контейнера. Локально override-файл подключает базы к обычной сети и публикует их на 127.0.0.1.
- **С самого хоста контейнеры доступны** по IP контейнера. Защита баз — сеть Docker, роли и пароли, а не недоступность с машины.
- **ПОЗЖЕ.** Ограничить выход egress списком адресов — правилами в DOCKER-USER или egress-прокси. Сам Docker ограничивать выход по назначению не умеет.

## **4. Ресурсы и лимиты**

На 12 ГБ стек помещается, если у каждого контейнера жёсткий лимит памяти, а Neo4j и Postgres настроены явно. Сумма лимитов постоянных сервисов — около 10,6 ГБ, остальное — система и короткоживущие контейнеры. Ядер на 6 vCPU хватает с запасом; ограничение — память. Без лимитов первым под OOM-killer попадёт Neo4j, а за ним всё, что от него зависит.

### **4.1 Память и процессор**

**Ориентир реализации.** Лимиты — mem\_limit, memswap\_limit и cpus в compose.yaml; значения стартовые.

| Сервис | Процессов | Память, лимит | CPU, лимит | Настройки |
| :-- | :-- | :-- | :-- | :-- |
| neo4j | 1 (JVM) | 4 ГБ | 2,0 | Куча 1,5 ГБ (initial = max), page cache 1,25 ГБ, dbms.memory.transaction.total.max = 512 МБ; около 1,25 ГБ — память JVM вне кучи и файловый кэш векторных и полнотекстовых индексов |
| postgres | 1 | 1,75 ГБ | 2,0 | shared\_buffers 512 МБ, effective\_cache\_size 1 ГБ, work\_mem 8 МБ, maintenance\_work\_mem 128 МБ, max\_connections 100, shm\_size 256 МБ |
| compute | 4 процесса pebble + Chromium по требованию | 2 ГБ | 3,0 | compute\_workers = 4 (Т-§21.3); Chromium закрывается после chromium\_idle\_close\_s простоя; shm\_size 256 МБ |
| api | 2 воркера Uvicorn | 1 ГБ | 1,5 | Пул psycopg до 10 соединений на воркер; семафоры моделей по Т-§22.5 — на каждый процесс |
| workers | 2 процесса (Т-§20.2) | 1 ГБ | 1,0 | worker\_concurrency = 8 на процесс (Т-§1.2); семафоры моделей по Т-§22.5 — на каждый процесс |
| projector | 1 процесс: проектор + диспетчер | 512 МБ | 1,0 | projector\_batch\_size = 100; диспетчер — отдельная задача asyncio (Т-§22.4) |
| redis | 1 | 192 МБ | 0,25 | maxmemory 128mb, без записи на диск (Т-§1.2) |
| caddy | 1 | 128 МБ | 0,25 | — |
| backup, migrate, alerts | Короткоживущие | 256 МБ | 0,5 | pg\_dump и age пишут потоком, без временного файла в памяти |

Сумма лимитов постоянных сервисов — 10,58 ГБ, плюс 0,25 ГБ на время бэкапа или миграции. Лимиты CPU в сумме больше шести ядер намеренно: это потолки, а не резерв, и под нагрузкой ход учителя (api) не должен ждать символьную проверку (compute).

- **Почему Neo4j так.** На хакатоне граф 100 учеников — сотни тысяч узлов, и хранилище целиком помещается в 1,25 ГБ page cache. Векторные и полнотекстовые индексы Neo4j живут в файлах Lucene и кэшируются вне page cache, памятью процесса. Поэтому вне кучи и page cache оставлено 1,25 ГБ, а не 0,25: иначе контейнер Neo4j падал бы по OOM сам.
- **Память транзакций 512 МБ.** Пересборка ученика идёт одной транзакцией до rebuild\_max\_tx\_ops операций вместе с векторами (Т-§2.7). 256 МБ на такую транзакцию могло не хватить. 512 МБ берутся из кучи, на чтение остаётся около 1 ГБ.
- **Запас тонкий.** Docker, sshd и fail2ban живут вне лимитов — это и есть системный запас. Если MemTotal окажется ниже 11,7 ГБ, page cache Neo4j снижается до 1 ГБ, а не отбирается память у compute.
- **Swap.** Файл подкачки 4 ГБ и vm.swappiness = 10: пик памяти стоит задержки, а не убитого Neo4j. memswap\_limit = mem\_limit × 1,25 у каждого сервиса: без него контейнер может взять swap размером со свой лимит, а при равенстве mem\_limit swap выключен, и пик кончится OOM.
- **shm\_size.** По умолчанию /dev/shm — 64 МБ. Postgres при нехватке падает с could not resize shared memory segment, Chromium тоже упирается в /dev/shm.
- **Neo4j в Docker** — переменные NEO4J\_server\_memory\_heap\_initial\_\_size, NEO4J\_server\_memory\_heap\_max\_\_size, NEO4J\_server\_memory\_pagecache\_size, NEO4J\_dbms\_memory\_transaction\_total\_max (в имени параметра . → *,*  → \_\_). По умолчанию в образе куча 512 МБ.
- **Соединения Postgres.** api 2 × 10, workers 2 × 5, projector 8 (проектор и диспетчер), backup, migrate и alerts 3, служебное \\\~5 — около 46 из 100. Точек сохранения LangGraph на хакатоне нет (Т-§22.3), отдельных соединений под них тоже.
- **Почему compute\_workers = 4.** На 6 ядрах четыре процесса SymPy оставляют два ядра для api и баз, и symbolic\_inline\_timeout\_ms (1500) истекает из-за сложности выражения, а не из-за очереди. Ограничение — память: четыре процесса и Chromium укладываются в 2 ГБ.
- **Chromium по требованию.** Браузер поднимается на первое задание рендера (визуализации, cheat sheet), обслуживает следующие задания новыми страницами и закрывается после chromium\_idle\_close\_s (стартовое значение 120) без заданий. Так 300–500 МБ браузера заняты только во время работы агентов (Т-§20.2).

**Проверить.** Пиковая память compute с четырьмя процессами и Chromium на тяжёлой визуализации; не влезает в 2 ГБ — compute\_workers = 3, а не память за счёт Neo4j. Фактический MemTotal. docker info не выводит No swap limit support, иначе memswap\_limit молча не действует. Пересборка самого большого тестового ученика укладывается в 512 МБ памяти транзакций. После нагрузочного теста — neo4j-admin server memory-recommendation и сверка кучи и page cache.

### **4.2 Диск**

**Ориентир реализации.** В тарифе один диск — 100 ГБ NVMe. Отдельного блочного тома нет; объектное хранилище — отдельная услуга с доступом по S3 (§8.4), файловую систему им не заменить.

| Путь на NVMe | Что там |
| :-- | :-- |
| / | ОС, Docker, образы, логи контейнеров (\\\~15 ГБ, Т-§20.3) |
| /srv/quack/data | Данные Postgres и Neo4j, данные Caddy (сертификаты) |
| /srv/quack/backups | Две последние локальные копии дампа Postgres (§8.1) |
| /srv/quack/tmp | Временные файлы compute; чистится по возрасту раз в час |

- **Логи контейнеров** — драйвер json-file, max-size 10 МБ, max-file 5 на контейнер. Журнал хоста — SystemMaxUse=1G в journald.
- **Тревоги** по заполнению NVMe — 75% и 90% (disk\_warn\_pct, disk\_crit\_pct, как в Т-§20.3).
- **Рост журнала** замеряется на нагрузочном тесте и первых сессиях (Т-§2.3, Т-§3.6). Для 100 учеников на хакатон порядок — единицы и десятки гигабайт, вместе с векторами в embedding.ready; 100 ГБ хватает, но замер обязателен.
- **Файлы материалов на диске не хранятся.** Оригиналы, страницы, штрихи и куски фото — в Object Storage (Т-§3.3); на NVMe только временные файлы разбора.

**Почему базы на NVMe.** Postgres синхронно пишет WAL на каждое событие, а Neo4j живёт page cache и случайным чтением. Задержка диска сразу видна в verdict\_p95\_ms и projector\_lag\_p95\_ms.

**Переносимого тома нет.** Диск живёт и умирает вместе с сервером, поэтому при потере сервера восстановление идёт только из дампов в R2 (§8.3), и RPO — честные ≤ 6 ч.

## **5. Сборка и CI**

CI собирает два образа под linux/amd64 на каждый merge в main и не пропускает в main ничего, что ломает тесты, миграции или изоляцию учеников. Сервер ничего не собирает сам: он только скачивает готовые образы.

### **5.1 Образы**

**Контракт.**

| Образ | Что внутри | Кто из него запускается |
| :-- | :-- | :-- |
| quack-backend | Python 3.12, FastAPI, psycopg 3, LangGraph, драйвер Neo4j, весь код ядра, dbmate, pg\_dump, age | api, workers, projector, backup, migrate — разные команды запуска одного образа |
| quack-compute | SymPy, pint, PyMuPDF, OpenCV, Playwright с Chromium | compute |

- **Один код — один образ.** Все Python-процессы используют один код и один набор обработчиков проектора (Т-§1.2). Один образ делает это свойством сборки: проектор и API не могут оказаться на разных версиях обработчиков внутри одного релиза.
- **compute отдельно**, потому что Chromium и OpenCV — сотни мегабайт, не нужные остальным. Контейнер работает под непривилегированным пользователем и без выхода в интернет (Т-§6.5).
- **Реестр событий в образе.** При сборке quack-backend код выгружает в файл /app/event\_registry.json список пар «тип события + версия схемы», которые знают обработчики проектора, и версию правил rules@N (Т-§2.5). По нему deploy.sh понимает, вводит ли релиз новые типы событий или новые правила (§6.3).
- **Платформа: linux/amd64.** Прод и раннеры ubuntu-24.04 — x86\\\_64, сборка нативная, без QEMU.
- **НА ОБСУЖДЕНИИ: linux/arm64.** Нужен, только если кто-то разрабатывает на Mac с Apple Silicon: amd64-образ там работает через эмуляцию заметно медленнее. Тогда arm64 собирается вторым job на ubuntu-24.04-arm (для публичного репозитория бесплатно), прод его не использует.
- **Теги:** короткий SHA коммита и main. Прод всегда запускает SHA, а не main: откат — смена одного значения (§6.3).
- **Реестр:** GitHub Container Registry рядом с kashanqq/Quack. Пакеты публичные, как и репозиторий: секретов в образах нет (§7), и серверу не нужен токен для docker pull. После первой публикации пакет приватный: видимость меняем вручную и проверяем docker pull без логина.
- **Чужие образы** — официальные, с закреплённой версией, без latest: postgres:16.x, neo4j:2026.10.x-community (не ниже 2026.02, Т-§1.2), redis:8.x, caddy:2.x.

**Проверить.** Кэш buildx в Actions ограничен 10 ГБ на репозиторий; при одной платформе образ с Chromium помещается с запасом.

### **5.2 Проверки**

**Контракт.** PR не сливается, пока не прошли все проверки (Т-§20.5):

1. ruff и проверка типов.
2. squawk по новым миграциям: блокирующие ALTER и индексы без CONCURRENTLY (Т-§1.2). Версия squawk закреплена не ниже 2.51.0: комментарий для файлов без транзакции появился в ней. В конфиге — pg\_version = 16 и assume\_in\_transaction (§6.2).
3. Юнит-тесты и тесты свойств на Hypothesis: применение пачками даёт тот же граф, что пересборка (Т-§2.5).
4. Интеграционные тесты репозиториев на настоящих Postgres и Neo4j через testcontainers (Т-§1.2).
5. Тест изоляции: каждый именованный запрос несёт параметр ученика (Т-§3.5). Там же — тест одного писателя: именованные запросы с записью в Neo4j вызываются только из проектора, а api и workers открывают сессии Neo4j только на чтение (§7).
6. Проверка реестра событий: каждый новый тип или версия схемы имеет обработчик проектора и правило диспетчера либо явную пометку «без обработчика» (Т-§2.4).
7. Сгенерированные из OpenAPI типы фронтенда совпадают с закоммиченными.
8. Сборка обоих образов, без публикации.

На merge в main — те же проверки плюс публикация образов и выкатка (§6). Фронтенд собирает и выкатывает Vercel сам.

**Ориентир реализации.** GitHub Actions; кэш слоёв buildx — в кэше Actions.

### **5.3 Секреты в публичном репозитории**

Репозиторий публичный, и PR может прислать кто угодно. Правило одно: чужой код никогда не исполняется там, где есть секреты. Секреты видит только job выкатки, а он запускается только на merge в main.

**Контракт.**

- **Проверки PR — только на pull\_request.** На PR из форка GitHub не передаёт секреты, а GITHUB\_TOKEN выдаёт только на чтение. Проверкам из §5.2 секреты не нужны.
- **pull\_request\_target запрещён**, как и workflow\_run, который скачивает артефакты или код из PR: они запускаются с секретами и токеном на запись.
- **Окружение production открыто только ветке main** правилом deployment branches.
- **Workflow из форков — только после одобрения** («Require approval for all external contributors»). Перед одобрением смотрим изменения в .github/.
- **Изменения в .github/workflows/ — через ревью.** Защита main требует одобрения PR, CODEOWNERS назначает на .github/ двух членов команды.
- **Минимальные права токена.** На уровне workflow permissions: contents: read; packages: write — только в job публикации образов.
- **Сторонние actions закреплены по SHA коммита**, обновления — через Dependabot.
- **Никакой подстановки чужого текста в run:.** Заголовок, ветка и тело PR не вставляются через ${{ }} прямо в команду — только через env:, в кавычках.
- **Secret scanning и push protection.** Secret scanning для публичных репозиториев работает автоматически; push protection включаем в Settings → Advanced Security. Если ключ всё же утёк — runbook, строка «Утёк секрет» (§12).

**Проверить.** Перед первыми тестировщиками открыть PR из форка с шагом, который печатает секреты окружения, и убедиться, что они пустые. Доступна ли push protection без платного Secret Protection.

## **6. Выкатка и миграции**

Выкатка — один скрипт на сервере, который перезапускает сервисы в порядке «сначала читатели журнала, потом писатели». Так правило Т-§2.4 соблюдается механически, а не по памяти.

### **6.1 Порядок выкатки**

**Контракт.** Job выкатки в GitHub Actions заходит на сервер по SSH (DEPLOY\_HOST, §7) со сверкой ключа хоста по DEPLOY\_KNOWN\_HOSTS и StrictHostKeyChecking yes: подменённый сервер не получит .env с секретами. Затем job рендерит /srv/quack/.env и вызывает deploy.sh \<sha>. Одновременно идёт не больше одной выкатки (группа concurrency: deploy).

1. **Версия.** Скрипт записывает SHA в QUACK\_VERSION и скачивает образы.
2. **Новые события или правила?** Скрипт сравнивает /app/event\_registry.json нового образа и работающего (§5.1): новые типы событий или версии схем и смену rules@N. Результат записывается в журнал выкаток, от него зависит откат (§6.3).
3. **Дамп перед миграцией.** Если в релизе есть новые миграции, сначала делается внеочередной дамп Postgres (§8.1).
4. **Миграции.** docker compose run --rm migrate — dbmate up под ролью quack\_migrator. Упала миграция — выкатка останавливается, сервисы остаются на старой версии. Если упал CREATE INDEX CONCURRENTLY, скрипт удаляет оставшийся INVALID индекс перед повтором.
5. **Читатель журнала.** Перезапуск projector — в нём и проектор, и диспетчер (Т-§22.4). Ждём, пока он поднимется и отметки снова двигаются.
6. **Фоновые процессы.** Перезапуск compute и workers.
7. **Писатель.** Перезапуск api с плавным завершением: текущие ходы учителя дописываются до api\_graceful\_shutdown\_s (стартовое значение 30).
8. **Проверка.** /healthz api, отставание проектора ниже projector\_lag\_p95\_ms, тестовый запрос через Caddy. Не прошла — откат по §6.3.

**Плавная остановка — настройки Compose.** По умолчанию Docker ждёт 10 с после SIGTERM и затем убивает процесс.

| Сервис | stop\_grace\_period | Что делает на SIGTERM |
| :-- | :-- | :-- |
| api | 35 с | Перестаёт принимать новые действия, дописывает текущие ходы до api\_graceful\_shutdown\_s, закрывает SSE и WebSocket |
| workers | 25 с | Перестаёт брать задачи и даёт текущим до 20 с закончиться. Недоделанные отменяет и сам возвращает в очередь (queued, без увеличения attempts); чистильщик через 60 с без пульса (Т-§13.1) — только страховка на случай SIGKILL |
| projector | 15 с | Дописывает текущую пачку одной транзакцией; новая не начинается |
| compute | 10 с | Убивает процессы заданий; вызывающий повторит по таймауту |

- **Caddy и базы при выкатке не перезапускаются.** Их версии меняются отдельной ручной операцией со снапшотом перед ней (§8.2).
- **Заморозка на окно демо.** Переменная репозитория DEPLOY\_FREEZE = true — job выкатки пропускает шаги и пишет об этом в лог; merge в main продолжаются. Ставится за deploy\_freeze\_before\_demo\_h (стартовое значение 12) до демо и снимается после.
- **Что видит ученик** (Т-§20.5). Короткий обрыв стрима хода, канала изменений и WebSocket канваса на шаге 7. Оборванный ход не записан (Т-§2.2), клиент запрашивает его заново; неподтверждённые пачки штрихов клиент досылает (Т-§15.2). Фоновые задачи, прерванные на шаге 6, начинаются заново: точек сохранения нет, а результат идемпотентен по ключу (Т-§22.3).

### **6.2 Миграции и новые события**

**Контракт** (Т-§20.5).

- **Миграции только расширяющие.** Новые таблицы, колонки со значением по умолчанию, индексы CONCURRENTLY. Удаление и переименование — отдельным релизом, после того как код перестал их использовать. Поэтому предыдущая версия кода всегда работает на новой схеме, и откат не требует миграции вниз.
- **Индекс CONCURRENTLY** — отдельным файлом с -- migrate:up transaction:false: dbmate по умолчанию оборачивает миграцию в транзакцию, а CREATE INDEX CONCURRENTLY в транзакции не работает. Маркер dbmate squawk не понимает, поэтому в его конфиге включён assume\_in\_transaction, а рядом с transaction:false ставится -- squawk-disable-assume-in-transaction. Одно без другого видно на ревью.
- **Миграции вниз** пишутся для разработки и в проде автоматически не запускаются.
- **Новый тип события или версия схемы.** Новая версия проектора и диспетчера знает и старые, и новые события, а писатель перезапускается последним (шаг 7). Опасен только откат: старый проектор на новом событии останавливает поток ученика (Т-§2.4).
- **Целевой профиль — два релиза.** Релиз N добавляет обработчики и правила диспетчера, релиз N+1 включает запись. Тогда откат N+1 → N безопасен всегда.
- **Схема Neo4j** — ограничения уникальности и векторные индексы — создаётся проектором при старте командами IF NOT EXISTS. Миграций для Neo4j нет: базу можно удалить и пересобрать (Т-§1.1).
- **Смена версии правил** rules@N (Т-§2.5) — после выкатки фоновая пересборка учеников (§8.7).

### **6.3 Откат**

**Контракт.** Откат — deploy.sh <предыдущий sha> без шага миграций. Предыдущий SHA хранится в журнале выкаток на сервере.

- **Релиз без новых событий** (шаг 2 выкатки) после неудачной проверки откатывается автоматически.
- **Релиз с новыми событиями** автоматически не откатывается: выкатка останавливается и ждёт человека. Команда ops can-rollback \<sha> проверяет по таблице ops.event\_types\_seen (Т-§2.3), появилась ли в ней хоть одна пара «тип события + версия схемы» из реестра нового образа (§5.1): журнал целиком не перебирается. Нет — откат безопасен. Есть — только исправление вперёд: старый проектор остановил бы потоки этих учеников.
- **Релиз со сменой rules@N** тоже автоматически не откатывается (Т-§20.5). После ручного отката проектор не применяет события к ученикам с projectorVersion новее своего: ops rebuild --stale-rules пересобирает их старыми правилами (§8.7). Граф производный, поэтому такой откат безопасен и стоит только времени пересборки.

**Отвергнуто.** Watchtower и подобные автообновлятели: они перезапускают контейнеры в произвольном порядке и нарушают Т-§2.4. Сборка на сервере из git: тратит ядра прода и делает выкатку невоспроизводимой. Blue-green на одной машине: на 12 ГБ вторую копию Neo4j не поднять. Откат кода снапшотом или Auto Backup: они откатывают и базы, то есть теряют события после снимка — это нарушение закона 1 (Т-§1.1).

## **7. Конфиг и секреты**

Числа живут в git, секреты — в GitHub Environment production, а на сервер секреты попадают только при выкатке (Т-§19.2). Тогда новый сервер получает всё нужное одним запуском выкатки, и восстановление не зависит от того, уцелел ли старый диск. Как секреты не попадают к чужому коду из PR — §5.3.

**Контракт.**

- **Параметры** из Т-§21.3, Т-§22.11 и §14.1 — файл конфига окружения в репозитории. Меняются через PR, как код. Несекретные адреса — имена бакетов, META\_API\_BASE\_URL, домен — тоже там.
- **Секреты** — только в GitHub Environment production. Job выкатки собирает из них /srv/quack/.env (права 600, владелец — пользователь deploy). В репозитории лежит только .env.example с именами без значений.
- **Каждый сервис получает только свои секреты.** В compose.yaml у сервиса явный список environment:, а не весь .env. Тогда compute и projector не видят ключей моделей и хранилищ.
- **В образах и логах секретов нет.** Логгер маскирует значения известных секретных переменных.
- **Ротация** — новое значение в GitHub и повторная выкатка того же SHA.

| Секрет | Для чего | Кому |
| :-- | :-- | :-- |
| META\_API\_KEY | Модели Meta | api, workers |
| LANGSMITH\_API\_KEY | Трассы | api, workers |
| MODAL\_TOKEN\_ID, MODAL\_TOKEN\_SECRET | Эмбеддинги | workers |
| S3\_ENDPOINT, S3\_ACCESS\_KEY, S3\_SECRET\_KEY | Объекты учеников в Contabo Object Storage (§8.4) | api, workers |
| BACKUP\_S3\_ENDPOINT, BACKUP\_S3\_ACCESS\_KEY, BACKUP\_S3\_SECRET\_KEY | R2, ключ Object Read & Write только на бакет quack-backups | backup |
| DELETIONS\_S3\_ACCESS\_KEY, DELETIONS\_S3\_SECRET\_KEY | R2, ключ только на бакет quack-deletions (§8.5) | api, workers (ежедневная сверка), backup (для восстановления) |
| BACKUP\_AGE\_PUBLIC\_KEY | Шифрование дампов (§8.1) | backup |
| POSTGRES\_PASSWORD | Суперпользователь: создание ролей и восстановление | postgres (первый запуск), migrate; при восстановлении — вручную (§8.3) |
| APP\_DB\_PASSWORD | Роль приложения quack\_app | api, workers, projector |
| READER\_DB\_PASSWORD | Роль только для чтения quack\_reader | backup (дамп), alerts |
| MIGRATOR\_DB\_PASSWORD | Роль миграций quack\_migrator | migrate |
| NEO4J\_AUTH | Neo4j | neo4j (первый запуск), api, workers, projector |
| EMAIL\_API\_KEY | Resend, ключ только на отправку с нашего домена (Т-§19.1) | api |
| GOOGLE\_OIDC\_CLIENT\_ID, GOOGLE\_OIDC\_CLIENT\_SECRET | Вход через Google (Т-§19.1) | api |
| HEARTBEAT\_BACKUP\_URL | Heartbeat бэкапа (§9.1) | backup |
| HEARTBEAT\_ALERTS\_URL, ALERT\_WEBHOOK\_URL | Heartbeat проверки тревог и чат тревог (§9.3) | alerts; ALERT\_WEBHOOK\_URL — ещё backup (тревога о неудачном бэкапе) |
| DEPLOY\_HOST, DEPLOY\_SSH\_KEY, DEPLOY\_KNOWN\_HOSTS | Адрес сервера, вход job выкатки и ключ хоста для сверки | Только GitHub Actions |

- **Роли Postgres** (Т-§19.8). quack\_migrator владеет схемами и выполняет DDL. quack\_app получает чтение и запись в core, content, ops, без DDL. quack\_reader — только чтение (pg\_read\_all\_data): им пользуются дамп и проверка тревог. Суперпользователь приложением не используется. Роли создаёт идемпотентная команда ops db-roles: при первом запуске, при каждой выкатке и перед pg\_restore (§8.3), потому что pg\_dump ролей не сохраняет.
- **Почта.** Ссылки входа отправляются через HTTP API Resend (Т-§19.1), а не через SMTP с сервера. От девопса нужны ключ и записи SPF, DKIM и DMARC для домена в Cloudflare (§3.1). Бесплатный тариф — 100 писем в сутки: в день, когда заходят первые тестировщики, следим за числом отправок; на нагрузочном тесте письма не отправляются (§11).
- **Neo4j без ролей.** В Community Edition нет управления доступом по ролям, поэтому NEO4J\_AUTH у api и workers даёт права на запись. Закон 3 (Т-§1.1) держится на коде: api и workers открывают сессии с default\_access\_mode=READ, сервер отклоняет в них запись; это проверяет тест в CI (§5.2).
- **Приватный ключ age** для расшифровки бэкапов на сервере не хранится. Он лежит офлайн у двух членов команды: украденный сервер не даёт прочитать бэкапы, а потерянный сервер не мешает их восстановить.
- **Доступ к панели Contabo** — у плательщика, с двухфакторным входом (TOTP). Данные входа в панель на сервере и в GitHub не хранятся: панель может переустановить ОС и удалить сервер.

**Отвергнуто — пока.** Vault, SOPS, облачные хранилища секретов. Для одного сервера и команды из нескольких человек GitHub Environment даёт то же самое без ещё одного сервиса. SOPS — кандидат для целевого профиля со staging.

## **8. Данные: бэкапы, восстановление, удаление**

Основной бэкап — дампы Postgres раз в 6 часов в Cloudflare R2, у другого провайдера (Т-§22.10). Второй слой — Contabo Auto Backup всего диска раз в сутки. Neo4j отдельно не бэкапится: после восстановления Postgres он пересобирается из журнала (Т-§1.8, Т-§2.7), а в Redis нет долговечных данных.

| Слой | Что покрывает | RPO | Где | От чего не спасает |
| :-- | :-- | :-- | :-- | :-- |
| Дамп Postgres → R2 | Журнал и всё в Postgres, включая сессии входа | ≤ 6 ч | Cloudflare | Основной слой |
| Две локальные копии дампа | То же | ≤ 6 ч | Диск сервера | Потеря сервера |
| Contabo Auto Backup | Весь диск: ОС, конфиг, Postgres, Neo4j, сертификаты | ≤ 24 ч | Отдельное хранилище Contabo | Блокировка или потеря аккаунта Contabo |
| Снапшот Contabo | Весь диск, вручную | Момент снимка | Contabo | То же |
| Журнал удалений → R2 | Факты удаления темы, домена, аккаунта | 0 | Cloudflare, отдельный бакет | — |
| Object Storage | Файлы учеников | Бэкапа нет | Contabo | Потеря аккаунта (§2.3) |

### **8.1 Дампы Postgres**

**Контракт.**

- **Расписание.** Полный дамп pg\_dump -Fc --compress=zstd раз в backup\_interval\_hours часов (стартовое значение 6, Т-§22.11) и внеочередной перед каждой миграцией (§6.1). По расписанию его запускает таймер systemd на хосте (docker compose run --rm backup).
- **Шифрование и место.** Дамп шифруется age публичным ключом до выхода с сервера и уходит потоком в бакет quack-backups под префикс dumps/. Ключ сервера — Object Read & Write только на этот бакет: права «только запись» в R2 нет. Удалить или перезаписать дамп нельзя благодаря bucket lock на backup\_retention\_days; прочитать можно, но дампы зашифрованы.
- **Локальные копии.** Две последние копии дампа лежат в /srv/quack/backups — для быстрого восстановления после нашей ошибки без потери сервера. Бэкапом они не считаются. Копии не шифруются: приватного ключа age на сервере нет, и зашифрованная копия не дала бы быстрого восстановления. Каталог доступен только root и пользователю контейнера backup (права 700, файлы 600): сервер и так хранит те же данные в базе.
- **Хранение** — backup\_retention\_days (стартовое значение 14, Т-§19.3), правилом жизненного цикла на dumps/. R2 удаляет по правилу асинхронно, в пределах суток. Срок bucket lock не больше срока жизненного цикла, иначе блокировка не даст правилу удалить старые дампы.
- **Роли** pg\_dump не сохраняет; перед восстановлением их создаёт ops db-roles (§7).
- **Объём.** 4 дампа в сутки × 14 дней = 56 дампов. Бесплатно в R2 — 10 ГБ на аккаунт, то есть до \\\~175 МБ на дамп. На 100 учеников дамп может быть больше: векторы в embedding.ready (Т-§3.1) почти не сжимаются. Тогда платим R2 сверх тарифа ($0,015 за ГБ-месяц, единицы долларов в месяц из €5 на допы), а не сокращаем срок хранения.
- **Неудачный бэкап — тревога** (§9.3), а не строка в логе. Успешный бэкап пингует heartbeat внешнего мониторинга (§9.1): если сервер или таймер умерли, тревогу поднимет внешняя сторона.

**ПОЗЖЕ — целевой профиль.** WAL-G: непрерывный архив WAL и ежесуточная базовая копия в R2, восстановление на момент времени (Т-§20.4). Каждое принудительное переключение WAL даёт сегмент в 16 МБ — учесть в объёме бакета.

### **8.2 Auto Backup и снапшоты**

**Contabo Auto Backup** — второй слой, не замена дампам.

- **Что даёт.** Снимок раз в сутки, до 10 дней. Единственный способ одним действием вернуть сервер целиком — ОС, конфиг, сертификаты, Neo4j без пересборки — после нашей ошибки: кривое обновление, удалённые файлы, сломанная настройка.
- **Почему не основной.** Раз в сутки против раз в 6 часов. Тот же провайдер и аккаунт. Снимок работающего Postgres в лучшем случае консистентен как после выключения питания: Postgres обычно поднимается по WAL, но атомарность снимка Contabo не обещает. Восстанавливается только на исходный VPS.
- **Как используем.** Только по сценарию «сервер жив, но испорчен» (§8.3) и всегда вместе со свежим дампом из R2.
- **Время снимка.** Если в панели его нельзя выбрать, на окно демо Auto Backup отключаем: снимок нагружает диск, пока Postgres пишет WAL.

**Снапшоты Contabo** (2 в тарифе) — не бэкап. Снапшот делается вручную перед рискованной операцией — обновление ОС или Docker, смена версии Postgres, Neo4j или Caddy — и удаляется вручную после проверки, не позже snapshot\_max\_age\_days (стартовое значение 7). Иначе Contabo удалит его сам только через 30 дней, и срок в согласии станет неверным (§8.6). Откат снапшотом теряет все события после него (§6.3), поэтому после успешной операции к нему не возвращаемся.

### **8.3 Восстановление**

**Контракт.** Сценарий «сервер потерян целиком»:

1. Новый сервер — тот же тариф Contabo или любой x86 VPS с 12 ГБ и Ubuntu 24.04 — и скрипт первичной настройки (§10). Скрипт не знает про провайдера.
2. Если старый сервер ещё отвечает — снять с него свежий дамп и использовать его вместо последнего из R2: так RPO почти нулевой.
3. Новый адрес — в DEPLOY\_HOST. Выкатка нужного SHA рендерит .env и поднимает только Postgres.
4. ops db-roles, затем последний дамп из R2 расшифровывается приватным ключом age и восстанавливается pg\_restore.
5. ops replay-deletions --since <время дампа> повторяет удаления из quack-deletions (§8.5).
6. Neo4j поднимается пустым, проектор пересобирает всех учеников (§8.7).
7. Запускаются остальные сервисы, DNS api. переключается на новый адрес (TTL ≤ 300 с, §3.1).
8. ops orphan-objects --since <время дампа> находит в quack-learners объекты новее дампа, на которые нет ссылок в Postgres: загрузки, события о которых потеряны. Они удаляются: файлы учеников без записи — это данные, о которых ученик не знает, и их не покрывает удаление аккаунта по журналу.

Auto Backup на новом VPS не используем: Contabo восстанавливает его только на исходный VPS, а отмена VPS удаляет и снапшоты, и бэкапы.

**Сценарий «сервер жив, но испорчен».** Кривое обновление ОС, удалённые файлы, сломанный конфиг, не поднимаются Neo4j или Docker:

1. **Свежий дамп до отката.** Если Postgres отвечает — ops backup now: внеочередной дамп в R2. Иначе свежим считается последний дамп в R2.
2. **Откат диска.** Восстановить последний Auto Backup до поломки из панели Contabo.
3. **Postgres — на самое свежее.** Остановить api и workers. Если дамп из шага 1 новее снимка — пересоздать базу (dropdb, createdb), ops db-roles и pg\_restore в пустую базу: поверх данных снимка pg\_restore упадёт на существующих объектах, а --clean не уберёт то, чего нет в дампе.
4. **Удаления** — ops replay-deletions --since <время восстановленного состояния>.
5. **Neo4j впереди журнала?** ops restore-check сравнивает у каждого ученика projectedSeq в Neo4j с learners.seq в Postgres. Если отметка в Neo4j больше — граф видел события, которых в журнале больше нет, и новые события получат те же номера. Тогда ops rebuild --all. Если Neo4j отстаёт — проектор догонит сам. Без пройденной проверки остальные сервисы не запускаются.
6. Запуск остальных сервисов и проверка как в §6.1, шаг 8. Если Postgres восстановлен из дампа — ops orphan-objects как в шаге 8 сценария выше.

**Объекты учеников** при потере только сервера не трогаются: новый сервер ходит в те же бакеты Object Storage. При потере аккаунта Contabo файлы теряются; текст материалов по страницам и вся память учеников остаются в Postgres.

**Учения** (Т-§20.4). Полное восстановление на отдельной машине — один раз до демо и затем раз в месяц: дамп поднимается, по нему пересобирается Neo4j, фактическое время записывается в §1 как база для RTO. Бэкап, из которого ни разу не восстанавливались, считается отсутствующим. Подходит временный VPS с почасовой оплатой или ноутбук: проверяются дамп и скрипты, а не провайдер. Сценарий «сервер жив, но испорчен» репетируется один раз до первых тестировщиков, пока на сервере нет настоящих данных.

### **8.4 Объектное хранилище**

**ПРИНЯТО.** Хранилища у двух разных провайдеров:

| Что | Где | Почему |
| :-- | :-- | :-- |
| Объекты учеников: материалы, страницы, штрихи канваса, куски фото, архивы экспорта (Т-§3.3, Т-§19.3) | Contabo Object Storage, 250 ГБ, EU, бакет quack-learners | Уже в заказе; рядом с сервером; объём в 25 раз больше бесплатного R2 |
| Дампы Postgres | Cloudflare R2, бакет quack-backups | Другой провайдер: блокировка аккаунта Contabo не уносит бэкапы |
| Журнал удалений | Cloudflare R2, бакет quack-deletions | Должен пережить любой источник восстановления (§8.5) |

- **Раскладка ключей** — Т-§3.3: всё под learners/{learner\_id}/, объекты неизменяемы.
- **S3-совместимый API** выбран в Т-§1.2 (aioboto3): хранилища подключаются сменой эндпоинта и ключей, без правки кода. Contabo требует path-style адресации: клиент создаётся с addressing\_style=path, и подписанные ссылки тоже получаются в path-style.
- **Бакет приватный.** Загрузки идут через api: тип проверяется по содержимому, лимит upload\_max\_mb (Т-§19.8). Отдача клиенту — по подписанным ссылкам GET со сроком object\_url\_ttl\_s (стартовое значение 300), напрямую из хранилища, мимо сервера. Исключение — архив экспорта данных: ссылка живёт export\_link\_ttl\_hours (24, Т-§19.6), и архив удаляется по правилу жизненного цикла префикса экспорта через тот же срок (на Contabo правило задаётся через API или CLI, в панели такой настройки нет). CORS бакета разрешает app.qvack.online и preview.qvack.online.
- **Штрихи канваса** пишет api раз в stroke\_chunk\_seconds и подтверждает пачку клиенту только после записи (Т-§15.2). Значит, при недоступном хранилище канвас копит штрихи на клиенте и в памяти сервера (Т-§20.7).
- **Contabo Object Storage** тарифицируется кусками по 250 ГБ и заявляет бесплатный исходящий трафик. Ставим потолок роста объёма в месяц, чтобы ошибка загрузки не росла в счёт.
- **Бесплатный тариф R2** — 10 ГБ-месяц хранения Standard, 1 млн операций Class A и 10 млн Class B в месяц, исходящий трафик бесплатный.

**Почему Object Storage, а не диск.** Файлы учеников влезли бы на NVMe, но код по Т-§1.2 и так ходит в S3, файлы в отдельной услуге переживают потерю сервера, а NVMe остаётся базам (Т-§20.3). Если бюджет придётся резать, это первое, от чего можно отказаться: файлы переезжают в R2, и за 10 ГБ надо следить.

**Отвергнуто.** Бэкапы в Contabo Object Storage: тот же провайдер и аккаунт, что и сервер. MinIO на том же сервере: тот же диск и память у Neo4j. Всё в R2: 10 ГБ бесплатно на объекты и бэкапы вместе, а 250 ГБ Contabo уже оплачены.

**Проверить.** Лимиты Contabo Object Storage: 250 запросов в секунду, 10 МБ/с по умолчанию, 3 млн объектов на клиента (увеличивается по запросу). Штрихи — один объект на stroke\_chunk\_seconds (10 с) активного канваса: 100 учеников по часу канваса в день дают \\\~36 тыс. объектов в сутки, порядка миллиона за месяц. Если пойдём к лимиту — запрос на увеличение. Замерить задержку и скорость загрузки из Алматы. Регион бакета совпадает с регионом сервера. Работают ли правило жизненного цикла (только удаление по сроку), CORS и подписанные ссылки в path-style — проверить до первых загрузок.

### **8.5 Удаление и журнал удалений**

**Контракт.** Удаление темы, домена или аккаунта по просьбе ученика идёт по Т-§2.9 и Т-§19.5. Девопс добавляет одно: факт удаления должен пережить восстановление из любой старой копии. Иначе восстановление «воскресит» то, что ученик просил стереть (П-14.3).

1. **Сначала запись в R2.** До физического удаления api пишет объект {deleted\_at}-{deletion\_id}.json в бакет quack-deletions: deletion\_id, learner\_id, вид (topic, domain, account), id цели и время. Данных ученика в объекте нет, только идентификаторы.
2. **Не записалось — не удаляем.** Ученик получает ошибку и повторяет; удаление без следа в R2 невозможно.
3. **Удаление** — шаги Т-§2.9 под advisory-блокировкой ученика, затем строка в ops.deletion\_log с тем же deletion\_id.
4. **Сверка.** Периодическая задача раз в сутки (deletions-reconcile:{дата}, Т-§13.1) находит объекты в R2 без строки в ops.deletion\_log и выполняет удаление заново. Это закрывает падение между шагами 1 и 3.

- **Повтор безопасен.** Удаление того, чего уже нет, ничего не меняет; deletion\_id не даёт записать факт дважды. Поэтому ops replay-deletions после восстановления просто проходит все объекты новее точки восстановления по порядку времени.
- **Хранение бессрочное.** На quack-deletions — bucket lock без срока и без правила жизненного цикла. Записи должны пережить любой источник восстановления: дамп (14 дней), Auto Backup (10), снапшот (до 7).
- **Отдельный бакет и ключ.** api смотрит в интернет, поэтому его ключ R2 даёт доступ только к quack-deletions, а не к дампам.

### **8.6 Сроки хранения и согласие**

После удаления данные ещё живут в копиях: в дампах — до backup\_retention\_days (14 дней) плюс до суток на асинхронное удаление R2, в Auto Backup — до 10 дней, в снапшоте — до snapshot\_max\_age\_days (7), в локальных копиях — до 12 часов. Объекты в Object Storage удаляются сразу и в бэкапы не попадают.

- **Экран удаления** называет срок с запасом — 15 дней (Т-§19.5: «сообщается ученику при удалении»).
- **Экран согласия** (Т-§19.4, П-14.6) называет сторонние сервисы, которые обрабатывают данные: Contabo (сервер и файлы, EU), Cloudflare (бэкапы, DNS), Meta (модели), Modal (эмбеддинги), LangSmith (трассы), Vercel (фронтенд), Resend (ссылки входа).
- **Трассы LangSmith** живут langsmith\_retention\_days (Т-§19.3) — это не девопс, но срок входит в тот же экран.

### **8.7 Пересборка Neo4j**

**Контракт.** Операционные команды идут через тот же код проектора и его advisory-блокировку (Т-§2.4, Т-§2.7):

| Команда | Когда |
| :-- | :-- |
| ops rebuild --learner \<id> | Исправлена ошибка проектора у одного ученика (§12) |
| ops rebuild --all --concurrency \<n> | Восстановление, повреждение базы, смена rules@N |
| ops rebuild --stale-rules | Откат релиза со сменой rules@N: ученики с projectorVersion новее кода (§6.3) |
| ops resume --learner \<id> | Снять остановку потока после исправления (ops.projector\_failures) |

- Пустой Neo4j — нормальное состояние: проектор видит учеников без отметки и пересобирает их сам.
- Большие ученики пересобираются только без активной сессии (rebuild\_max\_tx\_ops, Т-§2.7).
- Векторы не пересчитываются: они берутся из событий embedding.ready, поэтому пересборка не стоит денег на Modal.
- --concurrency по умолчанию 2: пересборка не должна отнимать у живых учеников ядра и память транзакций Neo4j (§4.1).

**Проверить.** Время полной пересборки на данных нагрузочного теста — главная часть RTO.

## **9. Наблюдаемость и бюджеты задержки**

На хакатоне хватает трёх источников: структурные логи, сводка состояния из таблиц ops и трассы LangSmith (Т-§22.10). Сверх техдоки добавлены автоматические тревоги в чат и внешний heartbeat: они стоят пару скриптов и закрывают главный риск — сервер молча умер, а мы узнали об этом от учеников.

### **9.1 Источники**

**Контракт.**

- **Логи** — JSON в stdout у каждого процесса. Обязательные поля: процесс, версия (SHA), learner\_id, correlation\_id, seq события, если есть (Т-§2.1). По correlation\_id одного хода находятся все его следы во всех процессах.
- **Сводка состояния** — команда ops status и внутренний эндпоинт с тем же содержимым, доступный только из сети Docker. Считается запросами к Postgres и Redis:
  - отставание проектора и диспетчера: learners.seq минус их отметки (Т-§2.4);
  - задачи ops.jobs по статусам, возраст самой старой задачи в очереди, доля failed;
  - остановленные потоки в ops.projector\_failures;
  - расход по ops.llm\_usage за час и сутки против бюджетов (Т-§11.4);
  - флаги давления llm:pressure:{model} (Т-§22.5);
  - возраст последнего успешного бэкапа, заполнение NVMe.
- **Трассы моделей** — LangSmith: задержка и стоимость каждого вызова, ошибки 429 от Meta API (Т-§11.7).
- **Внешний мониторинг** — Better Stack Free опрашивает публичный /healthz раз в 3 минуты. /healthz отвечает «жив», только если api достаёт до Postgres; Neo4j и Redis в нём не проверяются — их отказ видит ops status, а ход учителя переживает его сам (Т-§20.7).
- **Heartbeat снаружи.** Тревоги шлёт сам сервер, поэтому умерший сервер молчит. Закрываем это двумя heartbeat: бэкап пингует после каждого успешного дампа, проверка тревог (таймер systemd на хосте) — каждые 5 минут. Не пришёл пинг — тревогу поднимает внешний сервис. Запасной вариант — healthchecks.io.
- **Steal time** — st из vmstat раз в минуту пишется в журнал хоста. Это единственная метрика, которая отличает «у нас медленно» от «соседи по хосту забрали ядра» (§2.3).
- **Мониторинг Contabo не берём.** Он видит CPU, память и диск машины, но не наши отказы.

**ПОЗЖЕ — целевой профиль** (Т-§20.6). Метрики Prometheus в каждом процессе, Grafana Alloy отправляет их в Grafana Cloud.

### **9.2 Бюджеты задержки**

Значения — из техдоки; все стартовые и уточняются по нагрузочному тесту и первым сессиям.

| Параметр | Что измеряется | Старт | Где в техдоке |
| :-- | :-- | :-- | :-- |
| teacher\_status\_p95\_ms | От приёма POST /sessions/{id}/actions до события status: thinking в SSE | 300 | Т-§12.9 |
| teacher\_ttft\_p95\_ms | От приёма POST /sessions/{id}/actions до первого видимого текста хода в SSE | 10 000 при low, 20 000 при high | Т-§12.9 |
| verdict\_p95\_ms | От приёма ответа до verdict.recorded для мгновенных и символьных проверок | 1500 | Т-§1.5 |
| projector\_lag\_p95\_ms | От фиксации события до его применения в Neo4j | 500 | Т-§1.5, Т-§18.6 |
| context\_assembly\_p95\_ms | Сборка контекста учителя | 150 | Т-§10.7 |

- teacher\_ttft\_p95\_ms почти целиком — рассуждение модели до первого токена: на Wonder 8,2 с при low и 15,4 с при high, после чего ответ идёт ещё около 6 с (Т-§11.8). Наша часть — teacher\_status\_p95\_ms и context\_assembly\_p95\_ms; бюджет зависит от уровня рассуждения, который выбирает код (Т-§12.9).
- Бюджеты измеряются на сервере. Ученик в Алматы видит их плюс \\\~116 мс сети до EU.
- На хакатоне p95 считается скриптом по логам за окно; на целевом профиле — метриками.

### **9.3 Тревоги**

**Ориентир реализации.** Проверку делает ops alerts раз в 5 минут: таймер systemd на хосте запускает docker compose run --rm alerts (§3). Контейнер читает Postgres (роль quack\_reader, §7) и Redis, а состояние контейнеров и диска получает от хоста — таймер передаёт ему вывод docker ps и df через смонтированный файл, без доступа к сокету Docker. Сообщения уходят вебхуком в общий чат команды. Условия совпадают с Т-§18.6 плюс тревоги про сам сервер.

| Условие | Уровень |
| :-- | :-- |
| /healthz не ответил 2 проверки подряд (около 6 минут) | Критично |
| Есть остановленный поток проектора | Критично: этот ученик не получает обновлений памяти |
| Попытка бэкапа не удалась | Критично |
| Последний успешный бэкап старше backup\_interval\_hours + 30 мин | Критично: RPO уже нарушен. Поднимает внешний heartbeat |
| Проверка тревог не пинговала 15 минут | Критично: сервер или таймер мёртв |
| Контейнер перезапускается по кругу | Критично |
| NVMe заполнен больше 90% / 75% | Критично / предупреждение |
| Отставание проектора выше projector\_lag\_p95\_ms 10 минут подряд | Предупреждение |
| Самая старая задача в очереди старше 10 минут | Предупреждение |
| Доля failed среди задач за час выше 10% | Предупреждение |
| Флаг давления Meta API стоит больше половины последних 10 минут | Предупреждение: упираемся в лимиты, а не в сервер |
| Размыкатель модели разомкнут (Т-§11.9) | Критично: учитель отвечает ошибкой с кнопкой повтора |
| Расход моделей за сутки выше team\_daily\_alert\_usd (весь бюджет — Т-§11.4) | Предупреждение: плательщику и команде |
| Объекты quack-deletions без строки в ops.deletion\_log старше суток | Предупреждение: сверка удалений не сработала (§8.5) |
| До списания оплаты Contabo 3 дня | Предупреждение: плательщику, если автопродление не настроено |

## **10. Безопасность сервера**

Снаружи у сервера открыты только SSH по ключу и Caddy на 80 и 443. Базы, Redis и compute снаружи недоступны (Т-§19.8). Самый дорогой риск хакатона — не взлом, а чужой трафик, который сжигает лимиты и бюджет Meta API, поэтому лимиты частоты и бюджеты стоят в P0.

**Контракт.**

- **Порты 22, 80, 443** открыты в ufw, всё остальное входящее закрыто (default deny incoming). Те же три порта — в файрволе панели Contabo (бесплатно, только входящий трафик, работает до гостевой ОС). Правило на 22 создаётся до включения, иначе пропадёт SSH. Логов у файрвола Contabo нет, поэтому ufw остаётся вторым слоем. Порт 80 — только для выдачи сертификатов и редиректа (§3.1); техдока сейчас говорит «только 443» и правится (§0.2).
- **Docker обходит ufw.** Опубликованный порт контейнера доступен снаружи, даже если ufw его закрывает. Поэтому ports: в compose.yaml есть только у Caddy, а базы сидят только в internal-сети (§3.2).
- **Docker Engine ≥ 28.3.3.** До 28.0.0 порт на 127.0.0.1 был доступен соседям по сети, 28.3.3 закрывает ещё CVE-2025-54388.
- **SSH:** только ключи. Contabo выдаёт root с паролем — первым шагом настройки вход по паролю и под root выключается, ставится fail2ban. Два пользователя: admin для людей с sudo и deploy для job выкатки без sudo.
- **Обновления безопасности ОС** — unattended-upgrades, перезагрузка — вручную, вне окна демо, со снапшотом перед ней.
- **Docker — не через автообновление.** docker-ce, docker-ce-cli, containerd.io, docker-compose-plugin — в Unattended-Upgrade::Package-Blacklist. Обновление Docker перезапускает демон и все контейнеры разом, в произвольном порядке и в любое время. Docker обновляется вручную, со снапшотом, вне окна демо.
- **TLS** — автоматические сертификаты Caddy.
- **Вход и сессии** — по Т-§19.1: ссылка на почту и Google, непрозрачные токены в Postgres, cookie HttpOnly, Secure, SameSite=Lax на родительском домене. learner\_id берётся только из сессии.
- **Ограничение частоты** — в API, счётчиками в Redis (Т-§19.1); в стандартном Caddy ограничения частоты нет, а своя сборка Caddy со сторонним модулем не стоит того.
  - действия ученика — learner\_actions\_per\_min на ученика;
  - запрос ссылки входа — auth\_link\_per\_email\_per\_hour на адрес и auth\_link\_per\_ip\_per\_hour на IP: иначе через нас можно рассылать письма и сжигать квоту почтового сервиса;
  - без входа доступны только страница входа и /healthz.
  - При недоступном Redis каждый процесс api переходит на консервативные локальные счётчики, как лимиты моделей (Т-§1.2).
- **Бюджеты моделей** — session\_agent\_budget\_usd и learner\_daily\_budget\_usd (Т-§11.4) ограничивают расход одного ученика; тревога по суточному расходу команды — §9.3.
- **Оплата.** Автопродление тарифа и напоминание за 3 дня до списания (§9.3). Неоплаченный сервер провайдер блокирует; аккаунт, деактивированный за неплатёж, восстановить нельзя — нужен новый заказ. Срок до блокировки уточнить в поддержке.

**Известный компромисс.** Пользователь deploy в группе docker фактически равен root. На хакатоне принимаем: ключ deploy лежит только в GitHub Environment. На целевом профиле выкатку запускает узкая команда через sudo с белым списком.

**ПОЗЖЕ.** SSH только через Tailscale, порт 22 закрыт снаружи.

## **11. Нагрузочный тест**

До первых тестировщиков сервер проходит тест на 100 одновременных учеников с подменённым Meta API (Т-§20.8, Т-§22.10). Его результаты заменяют оценки памяти, диска и ёмкости в этом документе и в Т-§1.5, Т-§3.6, Т-§20.2.

**Контракт.**

- **Где.** На prod-сервере, пока на нём нет настоящих данных. Так меряется та самая машина с её диском, соседями и лимитами. Генератор нагрузки — Locust (Т-§20.8) на ноутбуке в Алматы: заодно видна реальная сетевая задержка до EU.
- **Сценарий** (Т-§20.8). 10 минут разгона до 100 учеников, затем 30 минут ровной нагрузки. Каждый ученик: ход учителя раз в 30 с, ответы на задания, строки и штрихи канваса, загрузка PDF раз за тест у каждого десятого.
- **Подмена моделей.** Контейнер meta-mock в профиле Compose loadtest отвечает как Responses API по профилю замеров (Т-§11.8): у Wonder первый токен через 8 с при low и 15 с при high, ответ после него — ещё около 6 с; у Spark — 3 с на вызов при low и 4,4 с при high; ключи объектов по алфавиту; перед вызовом инструмента — элемент с phase: commentary, иногда по два вызова инструментов за шаг. В каждом ответе — заголовки x-ratelimit-\* с остатком, который восстанавливается за секунды; заданная доля ответов 429 — с retry-after в секундах, с датой HTTP и без него. Так тест проходит и флаг давления по заголовкам, и все пути разбора 429 (Т-§11.2, Т-§22.5). api и workers смотрят в него через META\_API\_BASE\_URL. Эмбеддинги тоже подменяются (случайные векторы нужной размерности), трассировка LangSmith выключена. Так тест не тратит бюджет и меряет нас, а не Meta.
- **Учётные записи.** ops seed-learners --count 100 создаёт тестовых учеников без писем. После теста они удаляются штатным удалением аккаунта — это заодно проверка §8.5 на сотне удалений.

**Что меряем и что считается «прошёл».**

| Что | Порог |
| :-- | :-- |
| Время до первого текста без учёта модели (сборка контекста, вердикт, шапка) | В пределах context\_assembly\_p95\_ms и teacher\_ttft\_p95\_ms минус задержка подмены |
| verdict\_p95\_ms, projector\_lag\_p95\_ms | 1500 и 500 |
| Очередь задач | Самая старая задача моложе 10 минут, глубина не растёт к концу теста |
| Пропускная способность compute | Символьные проверки укладываются в symbolic\_inline\_timeout\_ms без ожидания в очереди |
| Память по контейнерам (docker stats) | Ни одного OOM, swap хоста занят меньше 1 ГБ |
| CPU | Нет устойчивого steal выше 10%, api не упирается в свой лимит |
| Семафоры моделей (Т-§22.5) | Ходы не ждут семафора api дольше teacher\_admission\_wait\_ms при 100 учениках; доля ходов на teacher\_fallback из-за семафора — 0. Иначе — правка параметров в техдоке |
| Рост диска | Записан: событий в час, ГБ в час, размер дампа |

**Оценка семафоров до теста.** По закону Литтла одновременных ходов в среднем — частота ходов × длительность: 100 учеников × 2 хода в минуту × 15–25 с хода (замеры на Wonder, Т-§11.8) — около 50–83. Слотов Wonder в api — llm\_concurrency\_wonder × 2 процесса. При 8 слотах на процесс их было бы 16, и этого не хватило бы, поэтому в Т-§22.11 для api стартовые значения — 48 слотов Wonder и 24 слота Spark на процесс (96 и 48 всего). Внешний предел здесь — лимит Meta, его держит флаг давления (Т-§22.5), а не семафор. Тест проверяет, что слотов хватает.

**После теста на тех же данных:** полный дамп и его время, ops rebuild --all и его время (часть RTO, §8.7), учения восстановления на отдельной машине (§8.3). Результаты записываются в §1, §4 и §14.2.

**Если не прошёл.** Сначала смотрим, что упёрлось. Память — лимиты в §4.1 и compute\_workers; CPU — steal time и лимиты; очередь — worker\_concurrency и семафоры. Сервер меняем только по таблице «Когда менять сервер раньше» (§13).

## **12. Runbook**

Почти любая авария на нашем стеке чинится одним из трёх действий: перезапуск, пересборка Neo4j или восстановление Postgres. Первый шаг всегда один — ops status (§9.1). Поведение системы при отказах — Т-§20.7; здесь — что делаем мы.

| Симптом | Вероятная причина | Что делать |
| :-- | :-- | :-- |
| У одного ученика не обновляются темы, в ops.projector\_failures есть запись | Исключение в обработчике проектора, поток ученика остановлен (Т-§2.4) | Воспроизвести на событиях ученика локально, исправить, выкатить, ops resume --learner. Если граф успел испортиться — ops rebuild --learner |
| Отставание проектора растёт у всех | Projector упал или Neo4j тормозит | Перезапустить projector (вместе с ним перезапускается диспетчер); проверить память и page cache Neo4j |
| Задачи не ставятся, хотя события пишутся | Встал диспетчер внутри projector | Перезапустить projector: диспетчер продолжит со своей отметки (Т-§22.4) |
| Копятся задачи в очереди | Лимиты Meta API (флаг давления, 429) или исполнители без пульса | При давлении — ждать, исполнителей не добавлять: упираемся в API, а не в CPU (Т-§22.5). Без пульса — перезапуск workers, задачи вернёт чистильщик |
| Всё медленнее обычного при обычной нагрузке | Соседи по хосту забирают ядра | st в vmstat (§9.1). Устойчиво высокий steal — тикет в поддержку Contabo; не помогает — переезд по §8.3 |
| Neo4j не стартует или данные повреждены | Сбой диска, OOM, ошибка версии | Удалить данные Neo4j, поднять пустым, ops rebuild --all (§8.7). Данные не теряются; учитель пока работает по разговору (Т-§20.7) |
| Сервер жив, но сломан: кривое обновление, удалённые файлы, не поднимается Docker | Наша ошибка | Сценарий «сервер жив, но испорчен» (§8.3) |
| ops restore-check сообщает «Neo4j впереди журнала» | Postgres восстановлен из дампа старше снимка Neo4j | ops rebuild --all; до конца пересборки ход учителя работает, но без свежей памяти |
| Postgres не принимает записи, диск заполнен | Рост журнала, логи, локальные дампы, временные файлы | Удалить старые локальные дампы и /srv/quack/tmp, проверить ротацию логов. Повтор — повод для тарифа с большим диском (§13) |
| Redis недоступен | Падение контейнера | Перезапустить. Данные не теряются: потребители на опросе Postgres, лимиты локальные, «один ход на сессию» — advisory-блокировкой (Т-§20.7) |
| Ход учителя приходит одним куском в конце | Буферизация SSE в прокси | Проверить, что api отдаёт Content-Type: text/event-stream; подстраховка — flush\_interval -1 в Caddy (§3.1) |
| Новый релиз ломает прод | Ошибка в коде | deploy.sh <предыдущий sha> (§6.3). Релиз с новыми событиями — сначала ops can-rollback; нельзя — исправление вперёд. Не снапшотом |
| Сервер недоступен или заблокирован, в том числе за неоплату | Потеря сервера | Проверить оплату в панели Contabo. Не решается за время RTO — восстановление по §8.3 на новом VPS |
| Object Storage недоступен | Сбой Contabo Object Storage | Ход учителя работает по тексту из Postgres. Канвас копит штрихи на клиенте и в памяти сервера, загрузки и фото не принимаются с понятной ошибкой (Т-§20.7). Ждать восстановления; дольше часа — сообщить тестировщикам |
| Не приходят письма со ссылкой входа | Сбой Resend, суточный лимит тарифа (100 писем), записи SPF/DKIM, наш лимит частоты | Проверить ответы Resend в логах api и записи DNS. Упёрлись в суточный лимит — платный тариф Resend. Вход через Google при этом работает |
| Meta API недоступен | Сбой у Meta | Учитель показывает ошибку с кнопкой повтора, размыкатель (Т-§11.9). Ничего не перезапускать |
| Утёк секрет | Ключ попал в логи, чат или репозиторий | Отозвать у провайдера, новое значение в GitHub Environment, повторная выкатка. Первым — META\_API\_KEY и DEPLOY\_SSH\_KEY |

**Данные учеников при отладке.** Локально воспроизводим на синтетических событиях или на событиях своих тестовых аккаунтов. Выгрузка событий настоящего ученика на ноутбук разработчика — только с его отдельного согласия (Т-§19.4).

- Название и цена тарифа на чекауте: публичные источники называют тариф с 6 vCPU, 12 ГБ и 100 ГБ NVMe «Cloud VPS 20» и дают за него €7,00 в месяц, а не €7,50 (§2). Срок активации заказа и прохождение платежа из Казахстана (§2.3).
- Срок до блокировки сервера при неоплате (§10).
- Задержка записи NVMe под Postgres и steal time vCPU под нагрузкой (§2.3, §11).
- Задержка SSE хода и WebSocket канваса из Алматы до EU; база — \\\~116 мс.
- Скорость загрузки в Object Storage из Алматы при лимите 10 МБ/с и число объектов против лимита 3 млн (§8.4).
- Фактический MemTotal (§4.1).
- Auto Backup: можно ли выбрать время снимка, весь ли диск он покрывает (§8.2).

Остальное:

- Пиковая память compute с четырьмя процессами и Chromium (§4.1).
- Пересборка самого большого ученика в пределах 512 МБ памяти транзакций Neo4j (§4.1).
- Стрим хода через Caddy без буферизации (§3.1, Т-§1.10).
- Лимиты Muse: у Spark и у Wonder измерены — 3000 запросов и 4 млн токенов в минуту. Остаются: общий ли лимит у моделей и у ключей и формат ответа 429 (§2.2, Т-§11.8).
- Размер дампа против 10 ГБ бесплатного R2 (§8.1).
- Размер события, рост журнала, время полной пересборки — на нагрузочном тесте (§11).
- Привязка домена к ветке Vercel на Hobby (§2.1).
- Push protection без платного Secret Protection (§5.3).
- Сессия Neo4j в режиме READ на одиночном сервере Community отклоняет запись (§7).
- Отправка Resend из EU и лимиты на своём аккаунте (§7, Т-§19.1).

## **15. Слабые места**

Где схема могла сломаться и что с этим сделано. Первая таблица закрыта решениями этого документа, вторая — риски, которые на хакатоне принимаем сознательно.

### **15.1 Закрыто**

| Слабое место | Чем грозило | Что сделано |
| :-- | :-- | :-- |
| Журнал удалений жил только в Postgres | Восстановление из старого дампа «воскрешало» удалённое (П-14.3) | Запись в R2 до удаления, сверка раз в сутки, повтор при восстановлении (§8.5) |
| Журнал удалений знал только аккаунты | Воскрешение удалённой темы или домена | В записи вид удаления и id цели (§8.5) |
| После восстановления Neo4j мог оказаться впереди журнала | Новые события получают занятые номера, граф тихо портится | ops restore-check перед запуском сервисов (§8.3) |
| Тревоги слал сам сервер | Умер сервер — молчат все тревоги | Внешние heartbeat от бэкапа и проверки тревог (§9.1) |
| Docker убивал api через 10 с после SIGTERM | Ходы учителя обрывались при каждой выкатке | stop\_grace\_period по сервисам (§6.1) |
| JVM Neo4j без запаса памяти, транзакции 256 МБ | OOM контейнера Neo4j, пересборка падала по памяти транзакций | 4 ГБ на Neo4j, 1,25 ГБ вне кучи и page cache, транзакции 512 МБ (§4.1) |
| Не было признака «релиз ввёл новые события» | Автооткат мог остановить потоки учеников | Реестр событий в образе, ops can-rollback (§5.1, §6.3) |
| PR-превью Vercel смотрели в prod API | Чужой код рядом с cookie учеников; вход в превью всё равно не работал бы | PR-превью без API, вход — только на ветке preview (§2.1) |
| Запрос ссылки входа без лимита | Рассылка писем через нас, сгоревшая квота почты | Лимиты на адрес и IP (§10) |
| Ключ api к бакету бэкапов | Взлом api давал чтение всех дампов | Отдельный бакет и ключ для удалений (§8.5) |
| unattended-upgrades обновлял Docker | Все контейнеры перезапускались в случайный момент | Docker исключён из автообновления (§10) |
| Каждый merge сразу уходит в прод | Перезапуск api посреди демо | DEPLOY\_FREEZE (§6.1) |
| Ёмкость сервера бралась из оценок | Первые тестировщики узнали бы предел раньше нас | Нагрузочный тест на 100 учеников до них (§11) |

### **15.2 Принятые риски**

| Риск | Почему принимаем | Что будет, если случится |
| :-- | :-- | :-- |
| RPO до 6 часов | WAL-G — сложность целевого профиля (Т-§22.10) | Ученики теряют до 6 часов работы; дамп со старого сервера, если он отвечает, сокращает потерю (§8.3) |
| Файлы учеников без бэкапа | Память и текст материалов по страницам — в Postgres | Ученики перезагружают оригиналы материалов |
| Блокировка аккаунта Contabo уносит сервер, Auto Backup, снапшоты и файлы разом | Журнал и журнал удалений лежат в R2 | Переезд по §8.3 на другой x86 VPS, файлы материалов — заново |
| Оплата проходит через одного человека | Так договорилась команда | Напоминание и автопродление (§10); при блокировке — §8.3 |
| Приватный ключ age только у двух человек | Ключ на сервере обесценил бы шифрование | Оба недоступны — восстановить дамп нельзя |
| deploy в группе docker ≈ root | Узкая команда через sudo — работа целевого профиля | Утечка DEPLOY\_SSH\_KEY = полный доступ к серверу: ротация по §12 |
| Один сервер без staging | Нагрузка хакатона не окупает второй | Ошибка релиза видна сразу в проде; откат по §6.3 |
| На верхней границе 100 учеников упираемся в лимит Wonder | Лимит Meta, а не наш сервер (Т-§22.5) | Часть ходов идёт на teacher\_fallback, доля видна в метриках |
| Нет проверенного RTO до учений | Учения — P1 | До них RTO ≤ 2 ч — цель, а не факт |
| Не доказано, общий ли лимит у Spark и Wonder и у разных ключей | Замеры шли на одном ключе, а остаток восстанавливается за секунды и общий счётчик не показывает (Т-§11.8) | Ёмкость считается по одному лимиту на обе модели и одному ключу; флаг давления по заголовкам срабатывает до 429 (Т-§22.5) |
