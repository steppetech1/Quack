## 1. Архитектура пакета `quack/session/` `[ОРИЕНТИР]`

Рекомендуемая декомпозиция внутри `backend/quack/session/`:
- `deps.py` — декодирование Bearer JWT (`sub -> learner_id`), проверка отсутствия tombstone в `ops.deletion_tombstones`, rate-limit ходов.
- `locks.py` — контекстный менеджер блокировки хода `acquire_turn_lock(redis, engine, session_id)` (Redis `SET NX EX 60` с прозрачным fallback на Postgres `advisory_lock(engine, LockKeyspace.SESSION_TURN, session_id)` при недоступности Redis, `Т-§17.3`).
- `lifecycle.py` — старт сессии (с авто-закрытием предыдущей активной сессии), получение состояния, heartbeat (`presence:learner:{id}`), завершение сессии и воркер `session.sweep_inactive`.
- `context.py` — сборка контекста для учителя (`Т-§5.3`): загрузка среза графа через `read_consistent_slice`, наложение `build_session_overlay`, чтение последнего `session.checkpointed` и последних `active_window_turns = 12` реплик из `core.events`.
- `turns.py` — пайплайн хода `POST /v1/sessions/{session_id}/turns`, вызов `teacher@1`, детерминированный fallback при деградации LLM (`Т-§17.1`), генерация потока SSE-событий.
- `workers.py` — обработчики фоновых задач `turn.extract` (с поддержкой пересмотра `evidence.superseded` при повторном запуске) и `session.checkpoint`.
- `schemas.py` — Pydantic-модели запросов, ответов и схем промптов.
- `router.py` — `router = APIRouter(prefix="/v1")`.

## 2. Инженерные решения и контракты модулей `[КОНТРАКТ]`

### 2.1. Контракт аутентификации и Rate-Limit (`deps.py`)
- Декодирует `Authorization: Bearer <token>` (`HS256`, секрет `settings.jwt_secret.get_secret_value() or "quack-dev-jwt-secret"`), извлекает `UUID(payload["sub"])`.
- Проверяет, что `learner_id` не числится в `ops.deletion_tombstones`. Иначе — `ApiError("UNAUTHORIZED", ..., status_code=401)`.
- На `POST /v1/sessions/{session_id}/turns` проверяет rate-limit в Redis по ключу `ratelimit_key("turns", str(learner_id))` (`TTL = 60s`, лимит — `20` ходов в минуту; при превышении — `429 RATE_LIMITED`; при отказе Redis — fail-open).

### 2.2. Жизненный цикл сессии и Инвариант единственной активной сессии (`Т-§5.1`, `Т-§5.4`)

1. **Старт сессии (`POST /v1/sessions`):**
   - На таблице `core.sessions` стоит частичный уникальный индекс `uq_sessions_one_active (learner_id) WHERE status = 'active'`.
   - Поэтому перед стартом новой сессии внутри той же транзакции проверяется наличие активной сессии ученика в `core.sessions`:
     - если активная сессия с тем же `idempotency_key` уже создана — она возвращается идемпотентно;
     - если у ученика есть **другая** активная сессия `old_session_id` — в одном вызове `append_events` **сначала** записывается `session.abandoned(session_id=old_session_id, domain_id=old_domain_id, reason="superseded_by_new_session")`, а **следом** — `session.started(session_id=new_id, ...)`.
   - Если `plan` не передан явно, формируется базовый план из 3–5 шагов по навыкам выбранной темы (`topic_id`) или первой доступной (`available`/`in_progress`/`rusty`) темы домена.
   - В Redis выставляется ключ `presence_key(learner_id)` со значением `str(session_id)` и `EX = settings.heartbeat_ttl_sec` (`90s`).
2. **Heartbeat (`POST /v1/sessions/{session_id}/heartbeat`):**
   - Проверяет, что сессия принадлежит ученику и находится в `status = 'active'`.
   - Обновляет `core.sessions.last_activity_at = now()` и продлевает `presence_key(learner_id)` в Redis на `90s`.
3. **Завершение сессии (`POST /v1/sessions/{session_id}/finish`):**
   - Если сессия уже в `status = 'completed'`, возвращает её статистику идемпотентно.
   - В одной транзакции Postgres:
     1) считает `summary_stats` (`turns_count`, `tokens_used`, `duration_sec`),
     2) записывает `session.completed(session_id, domain_id, summary_stats)`,
     3) ставит в очередь `ops.jobs` две задачи: `kinds.session_finish_artifacts(learner_id, session_id, {"domain_id": str(domain_id), "topic_id": str(topic_id) if topic_id else None})` и `kinds.graph_curate(learner_id, domain_id, {"domain_id": str(domain_id)})`.
   - Удаляет `presence_key(learner_id)` из Redis.
4. **Фоновая зачистка неактивных сессий (`@register_job_handler("session.sweep_inactive")`):**
   - Находит все строки в `core.sessions`, где `status = 'active'` и `last_activity_at < now() - make_interval(mins => settings.session_inactivity_timeout_min)`.
   - Для каждой такой сессии вызывает `append_events` с `session.abandoned(session_id, domain_id, reason="inactivity_timeout")` (`idempotency_key=f"sweep:{session_id}"`).

### 2.3. Блокировка хода, Сборка контекста и Пайплайн хода (`POST /v1/sessions/{session_id}/turns`) (`Т-§5.1–5.5`, `Т-§15`, `Т-§17`)

1. **Захват блокировки хода (`lock:turn:{session_id}`):**
   - Пытается взять ключ в Redis `SET lock:turn:{session_id} <request_id> NX EX 60`.
   - Если Redis выбросил ошибку соединения (`Т-§17.3`) — переключается на сессионный advisory lock Postgres `advisory_lock(engine, LockKeyspace.SESSION_TURN, session_id, wait=False)`.
   - Если блокировка уже занята параллельным запросом — немедленно возвращает `ApiError("TURN_LOCKED", "turn already in progress", status_code=409)`.
   - Блокировка удерживается на время генерации SSE-ответа и гарантированно освобождается в `finally`.
2. **Чтение консистентного среза и наложение сессионного оверлея (`Т-§2.6`, `Т-§5.5`):**
   - Вызывает `read_consistent_slice` (ожидание до `projector_lag_timeout_ms = 2000`). Если проектор отстал, `slice.lag_degraded == True`.
   - Вызывает `build_session_overlay(session, learner_id, session_id, slice.applied_seq, slice.data, settings.fold)`.
   - **Инвариант:** учитель выбирает следующую задачу и строит объяснение **только по `overlay.graph` и `overlay.assigned_task_ids`**, поэтому даже при отставании Neo4j он никогда не выдаст повторно задачу, уже назначенную или решённую на предыдущем ходу.
3. **Сборка контекста окна диалога (`Т-§5.3`):**
   - Читает из `core.events` последнее событие `session.checkpointed` данной сессии (`rolling_summary`, `open_threads`, `key_observations`).
   - Читает из `core.events` реплики `turn.student_replied` и `turn.teacher_replied` с `turn_index > last_checkpoint_turn`, ограничивая окно последними `active_window_turns = 12` репликами.
4. **Обработка ответа на задачу внутри хода (если передан `related_task_id`):**
   - Если ученик в этом ходу отвечает на ранее назначенную задачу (`related_task_id != None`), перед вызовом учителя формируются события `task.submitted` и `task.evaluated`:
     - для математической задачи (`kind == "math"`) вызывается `ComputeClient.check_math` (`evaluator = "compute"`);
     - для тестовой (`kind == "choice"`) проверяется совпадение с `reference_solution["option"]` (`evaluator = "compute"`);
     - для открытой задачи или при `parse_error`/`ComputeUnavailableError` оценка выполняется внутри вызова учителя или fallback-проверки;
     - `independence` рассчитывается с учётом выданных по этой задаче подсказок из `overlay.hints[related_task_id]`: `max(0.1, 1.0 - sum(h.independence_penalty))`.
5. **Вызов `teacher@1` и Детерминированная деградация (`Т-§17.1`, `Т-§17.2`):**
   - В штатном режиме вызывается `LLMGateway.generate_structured(role="teacher", prompt_version=1, ...)`.
   - Если модель решила объяснить концепт (`concept_explained != None`), в пачку событий хода добавляется `teacher.concept_explained`.
   - Если модель решила выдать практику или сессия в режиме `'practice'`, подбирается ещё не выдававшаяся в этой сессии задача из `core.task_bank` по теме (приоритет — `family_id`, по которому у ученика ещё нет успешного решения) и добавляется событие `task.assigned`.
   - **При перехвате `LLMUnavailableError`, `LLMBudgetExceededError` или `LLMSchemaError` (`Т-§17.1`):**
     - Ход **НЕ падает с HTTP 503**! Включается режим деградации `degraded_mode = "llm_unavailable"` (или `"budget_exceeded"`).
     - Из `core.task_bank` выбирается готовая задача (`kind in ('math', 'choice')`) по текущей теме сессии, формируется шаблонная реплика учителя с текстом задачи и событие `task.assigned`.
   - Если `slice.lag_degraded == True` (и LLM работает штатно), в `degraded_mode` проставляется `"projector_lag"`.
6. **Транзакционная фиксация хода и постановка фоновых задач:**
   - В одной транзакции Postgres:
     1) вызывается `append_events` со всеми событиями хода: `turn.student_replied` (`turn_index = prev + 1`), опциональными `task.submitted` / `task.evaluated` / `teacher.concept_explained` / `task.assigned`, и `turn.teacher_replied` (`turn_index = prev + 2`, `degraded_mode=...`),
     2) ставится задача `enqueue_job(session, kinds.turn_extract(learner_id, session_id, {"session_id": str(session_id), "turn_id": str(turn_id), "student_seq": ..., "teacher_seq": ...}))`,
     3) если количество реплик с момента `last_checkpoint_turn` достигло `settings.checkpoint_every_turns` (`6`), ставится склеиваемая задача `enqueue_job(session, kinds.session_checkpoint(learner_id, session_id, {"session_id": str(session_id), "up_to_turn_index": teacher_turn_index}))`.
7. **Последовательность SSE-событий (`Спецификация §8.5`):**
   - Ответ `POST /v1/sessions/{session_id}/turns` отдаётся с `Content-Type: text/event-stream` строго в формате `format_sse`:
     1) `turn_started`: `{"turn_id": "<uuid>", "turn_index": <int>, "user_seq": <int>}`
     2) `token`: один или несколько чанков `{"delta": "<text_chunk>"}` с текстом ответа учителя
     3) `task_evaluated` *(если в ходу оценивалась задача)*: `{"task_id": "<uuid>", "is_correct": <bool>, "score": <float>, "feedback": "<str>"}`
     4) `task_assigned` *(если в ходу назначена новая задача)*: `{"task_id": "<uuid>", "kind": "<str>", "prompt_text": "<str>"}`
     5) `turn_completed`: `{"turn_id": "<uuid>", "committed_seq": <int>, "degraded_mode": <str|null>}`
     6) `done`: `{}`

### 2.4. Воркеры `turn.extract` и `session.checkpoint` (`Т-§5.3`, `Т-§5.5`)

1. **`@register_job_handler("turn.extract")`:**
   - Читает реплики хода (`turn.student_replied`, `turn.teacher_replied`) из `core.events` и список навыков/заблуждений темы из Neo4j.
   - Вызывает `LLMGateway.generate_structured(role="extractor", prompt_version=1, ..., idempotency_key=f"extract:{turn_id}:v1")`.
   - **Поддержка пересмотра (`evidence.superseded`):** если в `core.events` для этого `turn_id` уже было записано более раннее событие `turn.extracted` (например, при перепрогоне задачи с новой версией), воркер в том же вызове `append_events` сначала эмитит `evidence.superseded(target_event_seq=old_extracted_seq, reason="re-extracted")`, а затем новое `turn.extracted(...)`.
   - Публикует в Redis-канал `session_events_channel(session_id)` JSON `{"event": "extractor_done", "data": {"turn_id": str(turn_id), "seq": committed_seq}}`.
2. **`@register_job_handler("session.checkpoint")`:**
   - Читает предыдущий `session.checkpointed` (если был) и все реплики сессии до `up_to_turn_index`.
   - Вызывает `LLMGateway.generate_structured(role="checkpointer", prompt_version=1, ..., idempotency_key=f"checkpoint:{session_id}:{up_to_turn_index}")`.
   - Записывает событие `session.checkpointed(session_id, up_to_turn_index, rolling_summary, open_threads, key_observations)`.

### Обязательный и достаточный набор тестов (`backend/tests/session/`):
1. **`test_session_lifecycle.py` (4 теста):**
   - Старт сессии (`session.started`), выставление `presence:learner:{id}` в Redis и продление через `/heartbeat`.
   - **Авто-закрытие предыдущей активной сессии:** при вызове `POST /v1/sessions` с новым ключом старая активная сессия атомарно переводится в `abandoned` (`reason="superseded_by_new_session"`), а новая становится `active` без нарушения индекса `uq_sessions_one_active`.
   - Завершение сессии `POST /v1/sessions/{id}/finish`: пишет `session.completed`, удаляет ключ `presence` и ставит в `ops.jobs` задачи `session.finish_artifacts` и `graph.curate`.
   - Воркер `session.sweep_inactive`: закрывает сессии с `last_activity_at` старше 30 минут событием `session.abandoned(reason="inactivity_timeout")`.
2. **`test_turns_and_sse.py` (5 тестов):**
   - Полный ход `POST /v1/sessions/{id}/turns`: проверка порядка и формата SSE-событий (`turn_started` → `token` → `task_assigned` → `turn_completed` → `done`), записи `turn.student_replied`, `teacher.concept_explained`, `turn.teacher_replied` и постановки `turn.extract`.
   - Оценка математической задачи внутри хода (`related_task_id`) через `ComputeClient` с эмитом `task.submitted`, `task.evaluated` и SSE-события `task_evaluated`.
   - **Защита от параллельных ходов (`TURN_LOCKED`):** пока один ход держит `lock:turn:{session_id}`, второй параллельный запрос к тому же `session_id` получает `409 TURN_LOCKED`.
   - **Работа поверх отстающего проектора (`SessionOverlay`):** когда `appliedSeq` в Neo4j равен `0`, второй ход видит назначенную на первом ходу задачу через `build_session_overlay` и не назначает её повторно, а в `turn_completed` возвращает `degraded_mode = "projector_lag"`.
   - Постановка `session.checkpoint` на 6-й реплике и коалесценция в `ops.jobs`.
3. **`test_degradation_and_workers.py` (4 теста):**
   - **Деградация при отказе LLM / исчерпании бюджета (`Т-§17.1`):** когда `LLMProvider` выбрасывает `ProviderUnavailableError` или превышен `session_token_limit`, ход `POST /v1/sessions/{id}/turns` успешно завершается (`200 OK` SSE), выдаёт задачу из `core.task_bank` и помечает `degraded_mode = "llm_unavailable"` / `"budget_exceeded"`.
   - **Деградация при отказе Redis (`Т-§17.3`):** при `redis = None` (или ошибке соединения Redis) блокировка хода прозрачно работает через Postgres `advisory_lock(keyspace=2)`.
   - Воркер `turn.extract`: записывает `turn.extracted`, отправляет `extractor_done` в `session:events:{id}`, а при повторном прогоне того же `turn_id` эмитит `evidence.superseded` на старый `seq`.
   - Воркер `session.checkpoint`: сворачивает реплики в `session.checkpointed` и обновляет `core.sessions.last_checkpoint_turn`.
