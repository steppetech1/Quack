## 2. Идентичности, детерминизм и криптографические инварианты `[КОНТРАКТ]`

Эти правила обязательны для всех модулей (`Т-§1.1`, `Т-§2.1`, `Т-§2.5`):

1. **Тип `learner_id`:** во всех таблицах Postgres (`auth.users.id`, `core.events.learner_id` и др.) и в API это `UUID`. В Neo4j на узле `(:Learner)` хранятся оба строковых свойства `id = str(learner_id)` и `learnerId = str(learner_id)` (`Т-§2.3`, `Д-§4.2`).
2. **Канонический `payload_hash` (`Т-§2.1`):**
   - Вычисляется как `sha256(orjson.dumps(payload_dict, option=orjson.OPT_SORT_KEYS)).hexdigest()` (строка из 64 hex-символов).
   - Используется для проверки идемпотентности при повторе `idempotency_key`: если ключ уже существует у данного `learner_id` с тем же `payload_hash`, `append_events` возвращает существующую запись без ошибки; если `payload_hash` отличается — выбрасывается ошибка конфликта идемпотентности (`HTTP 409`).
3. **Детерминированная генерация UUID узлов графа в проекторе (`Т-§2.5`):**
   - Проектор **никогда** не вызывает `uuid4()` и не читает системные часы (`datetime.now()`). Всё время берётся из `event.occurred_at`.
   - Фиксированный namespace проекта: `QUACK_UUID_NS = UUID("6ba7b810-9dad-11d1-80b4-00c04fd430c8")`.
   - Формула детерминированного ID: `uuid5(QUACK_UUID_NS, f"{learner_id}:{seq}:{item_index}")`.
   - **Разграничение источников ID:**
     - Сущности, создаваемые с явным ID в событии (`domain_id`, `topic_id` в `structure.proposed`, `task_id` в `task.generated`, `artifact_id`), получают свой ID напрямую из поля `payload`.
     - Сущности, порождаемые внутри проектора при обработке события, получают детерминированный `uuid5`:
       - `(:Evidence)` — `item_index` равен индексу наблюдения в массиве `observations` события `turn.extracted` (`0..N-1`).
       - `(:Exposure)` — `item_index = 0` для `teacher.Concept_explained`.
       - Inline provisional `(:Skill)` (`Т-§4.4`) и новые `(:Misconception)` — `item_index` равен `f"skill:{idx}"` / `f"misc:{idx}"` внутри соответствующего события, если узел ещё не существует в домене по нормализованному имени.
4. **Формат поля `actor` в `core.events` (`Т-§2.1`, `Т-§12.3`):**
   - Допустимые значения: `'learner'`, `'system'`, `'code'` (для детерминированного кода / `compute`), либо `<role>@<N>` (например, `'teacher@1'`, `'extractor@1'`, `'structurer@1'`) для событий, порождённых LLM-вызовом, где `N` — целочисленная версия промпта из `prompts/{role}/v{N}.md`.
5. **Версия правил проектора `rules_version` (`Т-§2.5`, `Д-§6.3`):**
   - Константа в коде: `CURRENT_RULES_VERSION = "rules@1"` (целое число версии `CURRENT_RULES_VERSION_NUM = 1`).
   - Сравнение версий выполняется по целому числу `N` после `rules@`.

## 4. Схема Neo4j и работа проектора (`Т-§2.2–2.5`, `Д-§4.2`) `[КОНТРАКТ]`

### 4.1. Ограничения и индексы Neo4j (`verify-schema`)
При старте воркера и по команде `python -m quack.cli ops verify-schema` идемпотентно создаются и проверяются (`Д-§4.2`):
- **Constraints (`IS UNIQUE`):** `Learner.id`, `Domain.id`, `Topic.id`, `Skill.id`, `Misconception.id`, `Task.id`, `Evidence.id`, `Exposure.id`, `Artifact.id`, `Alias.id`.
- **Indexes:** `Topic.learnerId`, `Skill.learnerId`, `Skill.domainId`, `Misconception.learnerId`, `Evidence.learnerId`, `Exposure.learnerId`, `(s:Skill) ON (s.learnerId, s.nextReviewAt)`, `(t:Topic) ON (t.learnerId, t.domainId, t.status)`.

### 4.2. Каталог типов `Mutation` проектора
Все 3 фазы проектора возвращают плоские списки объектов `Mutation`, которые компилируются в параметризованный Cypher и выполняются **в одной транзакции Neo4j** (`Т-§2.4`):
1. `UpsertNode(label, id, props)` — `MERGE (n:Label {id: $id}) SET n += $props`.
2. `UpsertRel(from_label, from_id, rel_type, to_label, to_id, props)` — `MATCH (a {id: $from_id}), (b {id: $to_id}) MERGE (a)-[r:REL]->(b) SET r += $props`.
3. `DeleteRel(from_label, from_id, rel_type, to_label, to_id)` — удаление ребра (при редактировании структуры).
4. `RebindNodeRel(label, source_id, target_id, merged_at_iso)` — атомарная операция для событий слияния (`topic.merged`, `skill.merged`, `misconception.merged`):
   - Перепривязывает все входящие и исходящие предметные и следовые рёбра (`HAS_TOPIC`, `PREREQ_OF`, `PART_OF`, `DEPENDS_ON`, `ABOUT_SKILL`, `TESTS`, `EVIDENCE_FOR`, `EXPOSED_TO`, `OBSERVED_MISCONCEPTION`, `TRIGGERS_MISCONCEPTION`, `HAS_ARTIFACT`) с `source_id` на `target_id` без создания дубликатов рёбер и петель.
   - Помечает старый узел `status = 'merged'` и создаёт/обновляет `(:Alias {id: source_id, learnerId: ..., kind: label})-[:ALIAS_OF]->(target)`.
5. `AdvanceWatermark(learner_id, applied_seq, projector_version)` — финальный шаг транзакции: обновляет `l.appliedSeq = $applied_seq`, `l.projectorVersion = $projector_version` на `(:Learner {id: $learner_id})`.

### 4.3. Двухшаговое чтение среза графа в пакетном цикле проектора (`Т-§2.4`)
Чтобы соблюсти инвариант **«Phase B — чистая функция без походов в базу»** (`Т-§2.4`, `Т-§7–9`) и при этом не грузить в память весь граф ученика:
1. **Запрос 1 (перед Фазой A):** вычисляется `BatchNeed = analyze_batch(events)`. Одним Cypher-запросом загружаются:
   - текущий `Learner` (`appliedSeq`, `projectorVersion`),
   - все `(:Alias)-[:ALIAS_OF]->(target)` ученика,
   - явно упомянутые узлы из `BatchNeed` и существующие `(:Skill)` / `(:Topic)` / `(:Misconception)` затронутых доменов (для резолва inline provisional сущностей по нормализованному имени, `Т-§4.4`).
2. **Фаза A (`apply_event_to_trace`, чистая функция):**
   - Резолвит все ID через карту `Alias`.
   - Применяет структурные изменения и порождает следовые мутации (`Evidence`, `Exposure`, новые `Skill` / `Misconception`).
   - Возвращает `(trace_mutations, dirty_skill_ids, dirty_misconception_ids, dirty_topic_ids)` и обновляет in-memory представление затронутых узлов/следов этого батча.
3. **Запрос 2 (между Фазой A и Фазой B, если `dirty_skill_ids` или `dirty_misconception_ids` не пусты):**
   - Одним Cypher-запросом догружает из Neo4j все исторические активные (`superseded = false`) узлы `(:Evidence)` (вместе с `Task.familyId` для `Evidence` от задач), `(:Exposure)` для `dirty_skill_ids` и наблюдения для `dirty_misconception_ids`, объединяя их в памяти с новыми следами из текущего батча.
4. **Фаза B (`recompute_skill_fold`, `recompute_misconception_fold`, чистые функции):**
   - Принимает полную историю следов каждого грязного навыка/ошибки из памяти и строго по формулам `Т-§7`, `Т-§8`, `Т-§9` вычисляет обновлённые поля (`pMastery`, `confidence`, `evidenceCount`, `DistinctFamilies`, `decayRate`, `stability`, `lastPracticedAt`, `nextReviewAt`, `status` и т.д.).
5. **Запрос 3 / Фаза C (`recompute_topic_display`, чистая функция):**
   - Для `dirty_topic_ids` (включая темы, чьи навыки изменились в Фазе B) догружает список всех навыков темы и их рёбер `DEPENDS_ON` (для вычисления `hubScore`), после чего чистой функцией вычисляет агрегаты темы (`mastery`, `coverage`, `Confidence`, `status`, `displayState` по правилам `Т-§9.2` и кодам `Т-§22.2`: `locked`, `available`, `in_progress`, `solid`, `rusty`).
6. **Запись (1 транзакция Neo4j):** все мутации Фаз A, B, C + `AdvanceWatermark` выполняются в одной транзакции Neo4j. После коммита в Redis публикуется `projector:applied:{learner_id}` (`{"applied_seq": last_seq}`).

### 4.4. Протокол блокировок и обработка `rules@N` (`Т-§2.2`, `Т-§2.5`, `Д-§6.3`)
- **Двухключевые сессионные advisory locks в Postgres:**
  - Проектор и `rebuild` держат транзакции в Neo4j, поэтому **нельзя** использовать транзакционные блокировки Postgres через сетевые вызовы. Используются сессионные блокировки на выделенном соединении из пула с гарантированным освобождением в `finally`:
    - `keyspace = 1`, `key = hashtext(str(learner_id))`: взаимное исключение проектора, `rebuild` и `purge-deleted` для одного ученика (`pg_try_advisory_lock(1, hashtext(id))`).
    - `keyspace = 2`, `key = hashtext(str(learner_id))`: fallback-блокировка хода сессии при недоступности Redis (`Т-§5.1`, `Т-§17.3`).
- **Поведение при расхождении `Learner.projectorVersion` и `CURRENT_RULES_VERSION` (`Т-§2.5`, `Д-§6.3`):**
  - Если `Learner.projectorVersion > CURRENT_RULES_VERSION` (откат релиза назад): проектор **не применяет** дельту к более новой проекции, логирует `warning` и пропускает ученика до запуска `ops rebuild`.
  - Если `Learner.projectorVersion < CURRENT_RULES_VERSION` (выкат новой версии формул `rules@N`): обычный инкрементальный цикл также пропускает ученика (чтобы не смешивать старые и новые агрегаты), а пересчёт выполняется командой `python -m quack.cli ops rebuild --stale-rules` (которая уважает `presence:learner:{id}` в Redis и режет удаление/пересчёт на батчи по `rebuild_max_tx_ops = 5000`).

## 7. Протокол очереди задач `ops.jobs` (`Т-§13`) `[КОНТРАКТ]`

1. **Каталог видов задач (`kind`) для Фаз 1–2 (`Т-§13.1`, `Т-§22.2`):**
   - `turn.extract` (`priority = 10`, `lock_key = f"session:{session_id}:extract"`, `coalesce_key = None`) — запуск экстрактора после хода.
   - `session.checkpoint` (`priority = 20`, `lock_key = f"session:{session_id}:checkpoint"`, `coalesce_key = f"checkpoint:{session_id}"`) — сворачивание окна диалога каждые 6 ходов.
   - `session.finish_artifacts` (`priority = 30`, `lock_key = f"session:{session_id}:finish"`, `coalesce_key = f"finish:{session_id}"`) — генерация дайджеста сессии и обновление шпаргалки при завершении сессии.
   - `artifact.refresh_cheatsheet` (`priority = 40`, `lock_key = f"topic:{topic_id}:cheatsheet"`, `coalesce_key = f"cheatsheet:{topic_id}"`) — фоновое обновление шпаргалки темы.
   - `graph.curate` (`priority = 80`, `lock_key = f"learner:{learner_id}:curate"`, `coalesce_key = f"curate:{domain_id}"`) — ночная/фоновая курация графа (пропускается/откладывается, если активен ключ `presence:learner:{learner_id}`).
   - `session.sweep_inactive` (`priority = 90`, `lock_key = "global:sweep_inactive"`, `coalesce_key = "global:sweep_inactive"`) — периодическое закрытие неактивных сессий старше 30 минут (`session.abandoned`).
2. **Семантика постановки и выборки (`Т-§13.1`, `Т-§13.2`):**
   - Постановка (`enqueue_job`) может вызываться **внутри той же транзакции Postgres**, что и `append_events` (паттерн transactional outbox). Использует `ON CONFLICT (coalesce_key) WHERE status = 'queued' DO UPDATE SET payload = EXCLUDED.payload, updated_at = now()`.
   - Выборка (`claim_next_job`) использует точный SQL из `Т-§13.1` с `FOR UPDATE SKIP LOCKED` и проверкой `NOT EXISTS (SELECT 1 FROM ops.jobs r WHERE r.lock_key = q.lock_key AND r.status = 'running')`.
   - Heartbeat обновляется каждые `15s`; зависшие задачи (`status = 'running'` и `heartbeat_at < now() - interval '60 seconds'`) возвращаются в `'queued'` с инкрементом `attempt` (или переводятся в `'failed'` + запись в `ops.dlq`, если `attempt >= max_attempts`). Backoff повторов: `min(300, 2 ** attempt * 5)` секунд (`Т-§13.3`).

## 8. Межсервисные и фасадные контракты ядра `[КОНТРАКТ]`

Ниже зафиксированы входы, выходы и инварианты пяти ключевых компонентов Фазы 1, которыми пользуются все 4 потока в Фазе 2. Внутренняя реализация пишется по соответствующим разделам `Т-§`.

### 8.1. Запись событий: `append_events` (`Т-§2.1`)
- **Вход:** `session: AsyncSession`, `learner_id: UUID`, `events: Sequence[NewEvent]`, `publish_wakeup: bool = True`.
- **Поведение:**
  1. Валидирует каждый `payload` через Pydantic-модель из реестра 36 типов событий и вычисляет `payload_hash`.
  2. Гарантирует наличие строки в `core.learner_seq` (`INSERT ... ON CONFLICT DO NOTHING`) и блокирует её `SELECT last_seq FROM core.learner_seq WHERE learner_id = $1 FOR UPDATE`.
  3. Проверяет `idempotency_key`: при совпадении ключа и `payload_hash` возвращает уже записанное событие; при расхождении `payload_hash` выбрасывает `IdempotencyConflictError`.
  4. Присваивает новым событиям последовательные `seq = last_seq + 1 ...`, вставляет в `core.events` и обновляет `core.learner_seq.last_seq`.
  5. Синхронно в той же транзакции Postgres обновляет оперативные таблицы (`core.domains`, `core.sessions`, `core.artifacts`, `core.task_bank`), если событие относится к ним, чтобы реляционное состояние никогда не расходилось с `core.events`.
  6. После коммита транзакции отправляет `{learner_id, seq}` в Redis-канал `projector:wakeup` (ошибка Redis логируется, но не роняет коммит, так как воркер проектора имеет fallback-поллинг `Т-§17.3`).

### 8.2. Чтение консистентного среза и оверлей сессии (`Т-§2.2`, `Т-§5.5`)
- **`read_consistent_slice(learner_id, min_seq, loader_fn, timeout_ms=2000)`:**
  - Если `min_seq is None`, берёт текущий `last_seq` из `core.learner_seq`.
  - Читает `Learner.appliedSeq` и срез из Neo4j через `loader_fn`. Если `appliedSeq >= min_seq`, сразу возвращает результат (`lag_degraded = False`).
  - Иначе подписывается на `projector:applied:{learner_id}` и ждёт до `timeout_ms`. Если не дождался — возвращает текущий срез с флагом `lag_degraded = True` (`Т-§2.2`, `Т-§17.2`).
- **`build_session_overlay(learner_id, session_id, applied_seq, base_slice)`:**
  - Читает из `core.events` события текущей сессии с `seq > applied_seq` (`turn.student_replied`, `turn.teacher_replied`, `task.assigned`, `task.hint_given`, `task.submitted`, `task.evaluated`, `turn.extracted`).
  - Накладывает их поверх `base_slice` в памяти (помечает только что выданные задачи, учитывает свежие `task.evaluated` и подсказки), чтобы учитель на следующем ходу никогда не повторял только что заданный вопрос даже при отставании Neo4j (`Т-§5.5`).

### 8.3. LLM-шлюз: `LLMGateway.generate_structured` (`Т-§11`, `Т-§12`, `Т-§17.1`)
- **Вход:** `role`, `prompt_version`, `response_model: type[T]`, `variables: dict`, `learner_id`, `session_id`, `turn_id`, `idempotency_key`, `temperature`.
- **Поведение:**
  1. Загружает шаблон `prompts/{role}/v{prompt_version}.md`, вычисляет его `sha256` (`prompt_hash`) и рендерит переменные.
  2. Проверяет `core.llm_outbox` по `(learner_id, idempotency_key)`: если запись уже в `status = 'completed'`, возвращает сохранённый `response_json` без сетевого вызова (`Т-§12.4`).
  3. Проверяет бюджеты токенов (`daily_token_limit_per_learner` по `ops.llm_ledger` за текущие сутки UTC и `session_token_limit` по `core.sessions.tokens_used`). При превышении выбрасывает `LLMBudgetExceededError` для перехода вызывающего кода в деградированный режим (`Т-§11.4`, `Т-§17.1`).
  4. Ограничивает параллелизм семафором `llm_semaphore_limit = 32`, выполняет запрос с Structured Outputs (JSON Schema от `response_model`), валидирует ответ, пишет запись в `ops.llm_ledger` и сохраняет результат в `core.llm_outbox`.
  5. При таймауте или `5xx` провайдера выбрасывает `LLMUnavailableError`, чтобы вызывающий модуль применил детерминированный fallback (`Т-§17.1`).

### 8.4. Изолированный сервис `compute` (`Т-§6.3`, `Д-§5.1`, `Д-§7`)
- Единственный внутренний эндпоинт: `POST /v1/check/math` (и `GET /health/live`).
- **Запрос:**
  - `mode: Literal["expression_equiv", "equation_roots", "derivative", "integral", "matrix_eq", "numeric_tol"]`
  - `student_expr: str` (ограничение длины `<= 1000` символов, парсинг только безопасным `parse_expr(..., evaluate=False)` со словарём разрешённых математических символов без `eval`/`__import__`)
  - `reference_expr: str`
  - `variables: list[str] = ["x"]`
  - `tolerance: float = 1e-6`
  - `timeout_ms: int = 1500` (вычисление в дочернем процессе с жёстким убийством по таймауту).
- **Ответ (`200 OK`):**
  - `status: Literal["completed", "parse_error", "timeout", "unsupported"]`
  - `is_equivalent: bool | None`
  - `normalized_student: str | None`
  - `diff_hint: str | None`
  - `error_message: str | None`

### 8.5. Единый формат ошибок API и SSE-событий (`Т-§15`, `Т-§18`)
- **HTTP-ошибки (`ErrorResponse`):**
