## 1. Общий принцип нарезки

Фаза 1 была нарезана по слоям (B1/B2/B3 параллельно, точки стыка через контракты). Дальше резать по слоям нельзя: шаг жюри «ответил на задачу → состояние изменилось → сет пересобрался» проходит через все три слоя. Поэтому дальше фазы режутся **по вертикальным сценариям**, а внутри фазы работа по-прежнему разделена по владельцам модулей.

Порядок фаз — по двум критериям: (1) что нужно раньше по §9, (2) что разблокирует фронт. Правила (фаза 2) идут раньше агентов (фаза 3), потому что: они детерминированы и тестируются на числах; фронт может собрать «Подготовку» и «Подборку» на реальных данных без модели; фоллбек «модель недоступна» (§6.3) требует, чтобы всё считаемое работало само по себе.

Каждая фаза описывается одинаково: цель, результат (что можно показать), состав по владельцам, новые точки стыка, что меняется в контрактах, что вне фазы. Формат ТЗ фазы — тот же пакет: `00-contracts-phaseN.md` (дельта к контрактам) + по файлу на B1/B2/B3, тесты первыми, `tz-executor`.

Итоговая карта:

| Фаза | Название | Что показываем по §9 после фазы |
| :---- | :---- | :---- |
| 2 | Правила: модель знаний, сеты, подбор по жёстким факторам | шаги 4 (ручная правка профиля), 5 (сохранение → требования, вехи, конфликт), 6 (замер), 7 без чата (задачи двигают состояние), 8 (сет, дедлайн, прогноз) |
| 3 | Агенты: ассистент подбора, репетитор, наблюдатель | шаги 1, 2, 3, 4 (через чат), 7 полностью («модель обновлена») |
| 4 | Фон и Quack: тексты, мягкое соответствие, рекомендации, поиск | шаг 3 («подходит тебе»), 5 (сравнение текстом), 8 (Quack, темп, варианты), отчёт по сету |
| 5 | Отказы, предгенерация, демо-аккаунт, деплой | шаг 9; живая защита 5 минут |

## 2. Фаза 2 — правила: модель знаний, сеты, подбор по жёстким факторам

### 2.1 Цель

Всё, что product-logic §7 называет «правилами», работает без языковой модели и без фоновых задач: ответ на задачу меняет состояние навыка, статус заблуждения и очередь сета в одной транзакции; сохранённая программа порождает требования, вехи и конфликты; профиль порождает подборку с реалистичностью. Фронт получает все read-модели «Подготовки» и «Подборки» с реальными числами.

### 2.2 Результат (приёмка словами)

- Тестовый ученик отвечает на задачу через API → в графе новый `KnowledgeState` со старым в `PREVIOUS`, `Evidence` с контекстом, при попадании в дистрактор — `MisconceptionState`; `GET /prep/knowledge/version` увеличился; ответ содержит разбор и новое состояние словами.
- Замер из 8–12 задач проходится до конца, спускается по пререквизитам при ошибке, даёт «твёрдо / шатко / корни», после него сеты перестроены и появился прогноз.
- Ученик с двумя сохранёнными программами видит требования (цель по экзамену), вехи из календарей, конфликт дат, если он есть; сет с дедлайном и прогноз «успеваешь / не успеваешь».
- `GET /matching` (или аналог) возвращает ≥ 3 программы с уровнем реалистичности и факторами с источниками; `PATCH /profile` меняет порядок сразу.
- Всё это работает при `LLM_FORCE_DOWN=1`.

### 2.3 Состав

**B1 — движок и граф** (замена стабов на реализации, чистые функции + Cypher):

- Модель знаний: `knowledge.reconcile.on_task_answered` — 11 шагов §8.2 как правило-обработчик события; приоры из анкеты §4.8 (`on_profile_updated`); общий навык двух экзаменов с `transfer_cross_exam` §4.6; `seen_templates`.
- Заблуждения: `knowledge.misconceptions.next_status` (§5.1 переходы, включая `disputed`/`undisputed`), `update_triggers` (§5.3), видимость §5.2 как функция-фильтр; персональные Cypher `get_misc_states / upsert_misc_state / add_root_cause / list_evidence`.
- Корни: правило `rule` (0.4) и `diagnostic` (0.8) из §6; чтение корней для очереди и контекста.
- Сеты: `sets.queue` (need = weight · gap · urgency · root_boost, топологический порядок по `REQUIRES`, короткие проверки для `conf < c_vis`), `sets.assemble` (голова очереди `set_size`, дедлайн Σ gap·effort / hours_per_week, не позже тест-даты, повторения, закрепление перед тестом, ручная смена), `sets.forecast` (§4.7: predicted_raw, coverage, predicted_scaled по `ScaleTable`, дата готовности, «успеваешь»). Хранение сетов — решить: Postgres (read-модель, простые запросы) с ссылками на `skill_id` в графе; в графе только состояния.
- Замер §8.4: бюджет `diag_base/reserve/max`, спуск по пререквизитам, `diagnostic.progress` для прерывания, `diagnostic.completed` с итогом. Выбор следующей задачи §10.2 (сложность на шаг, `n_seen = 0`, шаблон с `TRAPS` при confirmed).
- Моки §8.3/§10.2: сборщик трёх видов по `Section` из `ExamFormat`, подсчёт по `scoring_rule`, `mock.started.predicted_before`, `mock.completed`, Brier как число.
- Подбор-правила: `matching.hard` (статус каждого требования: ниже / в диапазоне / выше / неизвестно с источником), `matching.realism` (три уровня словами из академических и финансовых факторов; прогнозный балл только при `coverage ≥ c_cov`), `matching.rank` (веса из `priorities.ranking`, «неизвестно» не штрафует, ≥ 3 программ разных уровней), `matching.compare` (табличная часть: различающиеся факторы, топ-приоритеты, стандартные параметры, «одинаково» схлопнуто — без текста модели).
- Требования, вехи, конфликты из сохранённых (product-logic §3.5, §4.1): цель по экзамену = максимальный порог, кандидаты тест-дат из календарей, вехи (регистрация, тест, подача, документы), три правила конфликтов. Чистая функция; где живёт — `sets/` или новый `roadmap/` (решить в контрактах фазы).
- Данные: шаблоны задач до объёма замера и первых сетов — минимум по 2–3 шаблона на каждый навык SAT и ЕНТ (~120–170), распределение по типам и сложности как в `ExamFormat`; библиотека заблуждений расширяется вместе с шаблонами (дистракторы ссылаются на `misconception_id`). Это самый большой артефакт фазы, пишут все по квоте, B1 владеет форматом и `seed --validate`.

## 3. Фаза 3 — агенты: ассистент подбора, репетитор, наблюдатель

### 3.1 Цель

Языковая модель встаёт поверх правил фазы 2 и только через инструменты: ассистент подбора ведёт от пустого профиля к подборке и сохранённым; репетитор отвечает в контексте модели знаний; наблюдатель асинхронно превращает чат в свидетельства. Ни одно число в ответе не берётся не из инструмента (постпроверка в цепочке).

### 3.2 Результат

- Шаг 1 §9: свободный текст → анкета с пометками «сказал / предположили», черты дословно + резюме предпочтений, не больше двух вопросов, без переспроса известного.
- Шаг 2: вопрос по данным → ответ цифрами из `query_dataset` с источниками; интерпретация черты проговорена и записана.
- Шаг 3: резюме понимания (четыре блока с допущениями) → подборка через `run_matching` с карточками в `tool_result`.
- Шаг 4 через чат: «бюджет теперь 5000» → `update_profile` → ассистент называет сдвиг в подборке.
- Шаг 7: в чате топика ответ учитывает `confirmed`-заблуждение из замера; через несколько секунд «модель обновлена», раскрываемо до сообщения.
- `postcheck` в цепочке: число или дата без источника в результате инструмента → ответ помечен и не отдан.

### 3.3 Состав

Резюме предпочтений обновляется при каждой новой черте. Промпт `selection_v3` с блоком инструментов. ## 4. Фаза 4 — фон и Quack: тексты, мягкое соответствие, рекомендации, поиск

### 4.1 Цель

Всё, что модель делает **не в момент запроса** (product-logic §6.5 «фоновое»), и лента Quack как единое место рекомендаций. После фазы ученик почти никогда не ждёт живой генерации, кроме чата.

### 4.2 Результат

- `set.opened` → в очереди `bulk` гайдлайны всех топиков сета и объяснения навыков; открытие топика показывает готовый текст или «генерируется».
- `set.completed` → статистика правилом + текст моделью → `Summary{scope:'set'}`; идёт в слот `previous_set` следующего сета.
- Изменение резюме предпочтений → `soft_match` для кандидатов в фоне, кэш по `(резюме, программа)`; в подборке появляется «подходит тебе: …» и порядок внутри уровней обновляется.
- Вопрос вне пола → `search_programs` → `extract_program` по схеме `Program` с `extracted_auto=True`, `source_url`, `checked_at` → кэш; подборка может использовать.
- Quack: наверху темп по каждому экзамену «успеваешь / не успеваешь» с вариантами (часы, дата, убрать программу, снизить цель — каждый с новым прогнозом); ниже лента по срочности с причиной и действием; принятие = изменение профиля/требования/сета; отказ фиксируется; дни активности; ритм `recs_interval_h`, срочные — сразу.

### 4.3 Состав

**B2**: `jobs.pregenerate_set` (гайдлайн топика по §4.4: как готовиться, что уметь, типичные ловушки этого ученика, что решать; объяснение навыка; кэш `generated_texts` по хэшу входов — состояние + заблуждения + версия промпта), `jobs.set_summary` (§10.4, текст из статистики), `jobs.soft_match` (степень соответствия + одна-две фразы, structured), `jobs.extract_program` + `search.extract` (страница → `Program`), тексты сравнения (вывод «для тебя разница — …» поверх таблицы фазы 2), «почему реалистично» как текст по факторам (кэш по хэшу профиля). Промпты `guideline_v1`, `explanation_v1`, `set_summary_v1`, `soft_match_v1`, `compare_v1`.

**B1**: статистика отчёта по сету правилом (§10.4 п.1: задач/верно, навыков закрыто, `resolved` за сет, дни против дедлайна, сильнее всего выросшие по `PREVIOUS`, прогноз до/после); варианты по темпу (§3.6: пересчёт прогноза при +часы / перенос даты / убрать программу / снизить цель); планировщик Quack как правило (порядок и срочность рекомендаций, что срочное); `daily_aggregates` §10.7 (`hours_per_week_actual`, `active_days`, `error_class_dist`, `pace_signals`); ранжирование с мягким фактором (вес «программа/среда» из приоритетов).

**B3**: реестр `bulk` (`pregenerate_set`, `soft_match`, `extract_program`, `daily_aggregates`, `recommendations_batch`) с кроном ARQ; таблицы `generated_texts`, `set_summaries`, `recommendations` уже есть — репозитории и роутеры: `quack` (лента, темп, активность, принять/отклонить), `texts` (гайдлайн/объяснение топика со статусом «готово / генерируется / сохранённая версия»), `programs/search`; события `recommendation.accepted/declined`, `guideline.opened`, `explanation.opened`, `set.opened/completed` из соответствующих действий; Tavily-ключ и лимит (tech-stack §8.4); общий rate-limit так, чтобы `bulk` не съедал чат (`LLM_RPM_BULK`).

### 4.4 Точки стыка

`set.opened` / `set.completed` — B3 пишет события в обработчиках сетов фазы 2, B2-задачи ставятся из dispatch; `soft_match` читает `traits.summary` и `environment_text`; `recommendations_batch` читает прогноз (B1) и вехи/конфликты (фаза 2). Контракты: `RecommendationOut`, `PaceOut` с вариантами, `GeneratedTextOut` со статусом и пометкой, `SetSummaryOut`, `SoftMatchOut`, дельта `Program` под извлечение.

## 5. Фаза 5 — отказы, предгенерация, демо-аккаунт, деплой

### 5.1 Цель

Продукт переживает отсутствие модели, графа и поиска ровно так, как описано в product-logic §6.3 и memory-architecture §11.4, и стоит на VPS до 24.09 без внимания. Живая защита проходит по подготовленному аккаунту.

### 5.2 Результат

- `LLM_FORCE_DOWN=1`: подборка, сеты, задачи, моки, замер, состояния, прогноз, сравнение (таблица), вехи — работают; чаты, наблюдатель, мягкое соответствие, извлечение, отчёт по сету текстом — один статус «ассистент временно недоступен» через `/health.llm_status`; гайдлайны и объяснения — из кэша с пометкой «сохранённая версия»; отложенные задачи выполняются при восстановлении, статус снимается.
- Neo4j недоступен: события пишутся, ответы на задачи копятся, применяются при восстановлении (очередь отложенных `task.answered`); сеты — статический порядок канонической карты с пометкой; прогноз «недоступен».
- Поиск недоступен: пол с пометкой «показаны только проверенные программы».
- Тестовый аккаунт из `data/users.json` с заранее пройденными шагами 1–5 (профиль, черты, резюме, 3 сохранённых, конфликт) и вторым чистым аккаунтом для шагов 6–8 живьём; сокращённый замер 6 задач параметром.
- `curl -f https://<домен>/health` → `ok`; деплой по push в `main`; README по кейсу (задача, стек, архитектура, запуск, тестовый логин, источники данных, AI/API, готовые компоненты, ограничения), техсправка; `.env` не в репозитории — CI проверяет.

### 5.3 Состав

**B3**: фоллбек-контроллер как единая точка (таймауты по каждой генеративной функции, статус, выбор кэша); отложенное применение событий при недоступном графе (`processed_at` в `events` уже есть — это его назначение); `LLM_FORCE_DOWN` и эмуляция отказа графа для теста; seed демо-аккаунта (события, не прямые записи — чтобы прошёл через правила); секреты и порты (§3.2 контрактов) на prod-compose; наблюдаемость `request_id` api → worker; финальный прогон `make up && make seed && make test-int` на чистой машине; README и техсправка; graphify на `main`.

**B1**: статический порядок сетов из канонической карты как фоллбек; повторное применение отложенных событий идемпотентно (`MERGE` по `event_id` — уже условие §8); тест на replay-совместимость применения (не сам replay).

**B2**: чек-листы живого провайдера по всем шагам §9; пометки «сгенерировано» / «сохранённая версия» в текстах; лимиты и остаток кредитов проверены, порог тревоги, фоллбек-модель в `.env` записан; эвал наблюдателя на 10+ фрагментах вручную (precision/recall по `(kind, skill)`) как гейт версии промпта.

## 7. Сквозные правила для всех фаз

- **Стаб → реализация.** Каждая фаза начинается с перечня стабов, которые она закрывает (см. таблицу ниже). Сигнатуры из фазы 1 не меняются без записи в дельте контрактов; тест `pytest.raises(NotImplementedError)` заменяется настоящим.
- **Миграции** — одна на фазу, только B3, на синке. Модели присылаются через `sync-log.md`.
- **Параметры** — только `settings.knowledge.<имя>` из §12; новые параметры добавляются в §12 документа и в `KnowledgeParams` одновременно.
- **Тесты первыми** в отдельной сессии; чистые модули — на числах из документов; агенты — на `FakeLLMClient`; живой провайдер — только чек-листами.
- **Порядок мержа** внутри фазы: B3 (события, репозитории, роутеры-заготовки) → B1 (правила) → B2 (агенты). Правила должны быть зелёными до того, как агент начнёт их вызывать.
- **Фронт** получает после каждой фазы перегенерированные типы из OpenAPI; изменение Pydantic-модели без `make types` ломает CI.
