# AGENT.md

Инструкции для ИИ-агентов (Claude Code и др.) в этом репозитории. Читай этот файл первым.
Перед правкой файлов в папке прочитай её AGENT.md и AGENT.md всех родительских папок.

## Проект
Quack — событийно-ориентированный ИИ-репетитор: FastAPI + журнал событий в Postgres + проекция в Neo4j + Redis.
Код бэкенда — `backend/`, вычислительный сервис проверки — `compute/`, фронтенд-заглушка — `frontend/`,
проектные документы — `documentation/`. Контекст и команды: `backend/docs/CONTEXT.md`.

## Текущая фаза: Фаза 4
Единое ТЗ: `documentation/ТЗ Фаза 4 (единое).md` (далее «ТЗ Ф4»). Цель — довести систему до хакатонного среза
технического документа `Т-§22` (ТЗ Ф4, вступление и §1).
Три исполнителя работают параллельно — потоки **A**, **B**, **C** (ТЗ Ф4 §7.1). Не знаешь свой поток — спроси.

## Старт сессии (≤ 5 минут; скилл `parallel-claude-sync` — `.claude/skills/`, команда `/parallel-claude-sync`)
1. Этот файл: свой поток и зона (таблица выше), контрактные файлы (ниже).
2. `STATUS.md` (корень): доска пакетов — статус, стоп-точка, блокеры; раздел «Следующие шаги» своего потока.
3. `documentation/Фаза 4 — решения (единое).md`: раздел своего потока и швы. Архив `backend/PHASE4_NOTES.md`
   и ТЗ целиком на старте не читать — только нужный раздел ТЗ перед пакетом и нужное решение по id.
4. GitHub: `gh issue list --label to:<поток> --state open`; свои PR и CI ветки потока.
5. Фоновый наблюдатель: `backend/scripts/dev/gh_watch.sh <поток>`; своя тестовая инфраструктура:
   `backend/scripts/dev/test_infra.sh up <K>` (K — номер сессии или сабагента, 1–9).

## Как работать
- Принципы исполнения — ТЗ Ф4 §0.3: TDD (Этап I — сигнатуры, схемы, миграция, параметры, тела
  `raise NotImplementedError`; II — красные тесты из §8; III — реализация; IV — проверка и документация),
  ничего сверх скоупа §2.1, пороги — только в `Settings`.
- Источники истины по убыванию (ТЗ Ф4 §0.4.1): законы ядра `Т-§1.1` → `Т-§22`, затем остальные контракты `Т-§` →
  `Д-§` → `П-§` → явные контракты ТЗ Ф4 ([КОНТРАКТ], [РЕШЕНИЕ Ф4]) → соглашения кода → инженерные критерии §0.4.3.
  Пропускать уровни нельзя.
- Решения пиши в журнал своего потока `backend/notes/<A|B|C>.md`, в момент решения (ТЗ Ф4 §0.4.5), и строкой
  в `documentation/Фаза 4 — решения (единое).md`. Чего нет в документах — решай сам по ближайшему правилу ТЗ;
  владельцу — только необратимое или против буквы документа (класс C): issue с меткой `owner`.
  `backend/PHASE4_NOTES.md` — архив до 2026-11-03, новые записи туда не добавляются.
- Не получилось — ТЗ Ф4 §0.4.6: откат, `xfail(strict=True, reason="BLOCKED-NNN: ...")`, запись в «Заблокировано».
- Дисциплина — ТЗ Ф4 §0.4.7: пакеты по порядку §7.1, перед пакетом перечитать первоисточники. Локально —
  затронутые тесты плюс контрактные (`scripts/dev/ct.sh <K> …`); полный прогон — один раз на волну
  (политика тестов — `backend/TESTS.md`). После пакета обнови свою строку в `STATUS.md`.

## Красные линии (ТЗ Ф4 §0.4.4) — решает только владелец
1. Нарушить закон ядра `Т-§1.1`.
2. Добавить тип события или поле payload вне каталога WP2 после G1, изменить схему события после G1.
3. Изменить формулы и пороги `Т-§7`–`Т-§9` или правила `Т-§8.6` иначе, чем в документе.
4. Писать миграцию, которая не только расширяет схему, после базовой миграции WP1.1.
5. Ослабить тест, чтобы он прошёл (изменение утверждений — только по §8.15).
6. Реализовать что-либо из §2.2 или помеченное в первоисточнике ПОЗЖЕ.
7. Менять файлы вне `backend/` и списка ТЗ Ф4 §2.1: `compute/**`, `compose.yaml`, `compose.override.yaml`,
   `deploy/**`, `.github/**`, `modal/**`.
8. Слить что-либо в `main`, `--force`-push, `reset --hard` по чужим коммитам, переписать опубликованную историю,
   удалить чужие ветки.
9. Записывать секреты в репозиторий, логи, фикстуры; обращаться к настоящим внешним сервисам из тестов.
10. Отключать `ruff`/`pyright` там, где можно исправить код.
11. Объявлять пункт DoD выполненным, если он не проверен.
12. Решение, которое меняет поведение, видимое ученику, вопреки `П-§`.
13. Писать или переписывать доктрину промптов (слой 1, ТЗ Ф4 §7.6).
14. Править файл другого потока (§7.3) без согласования, кроме разрешённых в §7.3 случаев.

Зависимости — только из списка ТЗ Ф4 §4.6.

## Git и слияние (ТЗ Ф4 §7.4; рабочий процесс с 2026-11-03)
- Интеграционная ветка `phase-4` защищена: слияние только PR с зелёными обязательными проверками CI
  `fast`, `backend`, `squawk`, `compute`, `images` (без требования «ветка обновлена»; force-push запрещён).
  Слои CI и политика тестов — `backend/TESTS.md`.
  `main` не трогай.
- **Одна ветка на поток:** `phase-4-a`, `phase-4-b`, `phase-4-c`. Пакеты — серии коммитов в ней. Отдельная
  ветка `phase-4-<a|b|c>-<тема>` — только для шва, который ждут прямо сейчас.
- **Волна:** готовый пакет (или 2–4 часа работы) → `git merge origin/phase-4`, затронутые тесты → push →
  PR ветки потока в `phase-4` (или push в уже открытый) с `gh pr merge <N> --auto --merge`: вливается сам,
  когда CI зелёный. После слияния ветка потока продолжает жить (не удалять).
- **Ревью соседа** — только для изменений в контрактных файлах (ниже). Остальное — самопроверка + CI.
- Каждый WP — два коммита: `phase4(wpN): tests (red)` и `phase4(wpN): implementation (green)`.
- Коммиты в `backend/` — от настроенного пользователя git, без `Co-authored-by` и без упоминаний ИИ.
- Генерируемые файлы (`backend/openapi.json`, `quack/prompts/manifest.json`, `PROMPT_CONTRACTS.md`) — только
  пересборкой (`uv run python -m quack.cli ops openapi --out openapi.json` и т.д.); при конфликте — их версия +
  пересборка. `uv.lock` — только `uv lock`.
- Перед коммитом — `git status`: без `.env`, кэшей, `.venv`, отчётов нагрузки.

## Общение потоков — только GitHub
- Вопрос или задача другому потоку — issue по шаблону «Запрос другому потоку», метка `to:<поток>`
  (+ `blocking`, если стоит работа). Ответ — в issue; закрывает спрашивающий.
- Ревью и замечания по строкам — в PR. Вопрос владельцу — шаблон «Вопрос владельцу», метка `owner`.
- Людям сообщения не пересказывать: каждая сессия держит фоновый `scripts/dev/gh_watch.sh <поток>`.
