## Часть 1. Как связи строятся сейчас

**Где живут связи.** Связь «нужно до» (`REQUIRES`) существует только между навыками. Связей между темами в базе нет. Стрелка «тема A → тема B» на графе вычисляется при чтении (`topic_requires`): если какой-то навык темы A требует навык темы B, рисуется стрелка, и толщина равна числу таких пар. Нет связей между навыками — нет и стрелок между темами.

**Шаг 1, разметка.** Файл режется на куски примерно по 1–2 КБ. Модель `material_parser` размечает каждый кусок тремя списками:
- `topic` — тема, о которой кусок;
- `teaches` — что кусок объясняет: вводит, определяет, показывает как делать;
- `uses` — что кусок считает уже известным: применяет, на что опирается.

В промпте прямо сказано: если кусок только применяет или перечисляет, `teaches` пустой.

**Шаг 2, структура.** Функция `_subjects` превращает разметку в кандидатов для графа. Связь появляется по одному правилу: всё из `uses` куска, у которого непустой `teaches`, становится требованием для его навыков. Иначе говоря, «этот кусок учит X и при этом опирается на Y» даёт связь X → Y.

**Сверка с графом.** Кандидаты идут в модель-сборщик (`builder`) пачками по 15 (`candidate_k`). Для каждого кандидата сборщик решает: создать новый узел, привязать к существующему или предложить слияние. Код записывает связь только если оба навыка решены в одном вызове сборщика (`resolved` в `_decide`). Требование к навыку из другой пачки или из другого файла просто отбрасывается.

**2. Навыки задач (кусок только применяет).** Если в куске одни `uses`, эти навыки и есть содержание листа. Значит, лист их отрабатывает, и эти навыки должны считаться навыками этого файла, без правила «учит → опирается».

**3. Связи внутри файла.** Сейчас требования из соседней пачки и из соседнего куска теряются. Чтобы этого не было, разрешать требования после всех пачек сразу, по именам всех навыков файла. Тогда связь не зависит от того, в какую пачку из 15 попал навык.

**4. Связи между файлами.** Это главное. Предлагаю отдельный шаг после структуры: «как этот файл стыкуется с предыдущими». Модели дают:
- навыки нового файла;
- навыки уже разобранных файлов этого предмета, найденные по близости векторов;
- порядок материалов: номер в названии, неделя, дата, иначе порядок загрузки.

Модель отвечает только на вопрос, какие навыки нового файла опираются на какие навыки прошлых. Код записывает связи `REQUIRES` с `origin = material`. Тогда у тебя появится «нормальное распределение → дискретные случайные величины → вероятность → …», и стрелки между темами нарисуются сами.

## 4. Как должно быть: сначала карта курса

**Главная идея.** Граф предмета — это карта курса, которую поддерживает одна модель-картограф. Она видит всю текущую карту целиком и вносит в неё правки. Материалы не создают узлы напрямую, а дают сведения для очередной правки карты.

### Что получает ученик (продукт)
- **Ровная карта.** Темы размером с раздел лекции, 1–6 навыков в каждой, без пустых тем. Темы выстроены «снизу основы».
- **Понятные связи.** У каждой связи видно, откуда она: «по программе курса», «по смыслу», «сказано в материале».
- **Пачка файлов — одна правка.** Закинул 7 семинаров — система ждёт окончания загрузки и строит карту сразу по всем, а не семь раз подряд по одному. Пока идёт работа, видно: «читаю файлы → составляю план курса → связываю».
- **Хабы только по просьбе ученика**, как ты решил. Позже система может их предлагать: под дедлайн или «неделя 5–7».
- **Правки руками.** Переименовать, объединить, разделить тему, сказать «это не нужно до» — правки уже есть по §4.11 и становятся уроком для следующих разборов.

### Как это устроено (инженерия)

**Этап A. Конспект материала** (параллельно, без блокировки предмета). Одна модель читает файл целиком. Если файл большой, она сначала проходит его частями, а потом сводит в один конспект. Конспект содержит:
- вид материала: лекция, семинар, силлабус, конспект;
- признаки порядка: номер, неделя, дата;
- план разделов;
- для каждого раздела: какие понятия он вводит и на какие опирается (с цитатой, если текст это прямо говорит);
- список задач с привязкой к разделам.

Это хранится, но граф пока не меняет.

**Этап B. Правка карты** (один вызов на пачку файлов, под блокировкой предмета). Картограф получает текущую карту предмета целиком и конспекты, упорядоченные по неделям или номерам. Карта у предмета маленькая: сотни узлов, несколько тысяч токенов. Ответ — правка в закрытом выборе по меткам (как в §4.5):
- раздел → существующая тема (T3) или новая тема с местом в порядке курса;
- понятие → существующий навык (S12) или новый навык с домашней темой и описанием в одну фразу;
- связи между навыками с типом и обоснованием.

Векторный поиск кандидатов остаётся только для очень больших предметов, чтобы сузить карту.

**Этап C. Проверка кодом**, до записи:
- не больше 6 навыков на тему (иначе — просьба разделить);
- никаких пустых тем;
- никаких навыков инструмента (Excel, SUMPRODUCT) — это задачи, а не навыки;
- нормализация имён;
- никаких встречных связей.

Нарушение возвращается картографу один раз с указанием, что не так. Это тот же приём, что с неизвестными метками.

**Этап D. Связи трёх видов с разной уверенностью.** Это важно для модели ученика:
- **«Сказано в материале»** («используя ЦПТ…», «см. лекцию 3»): высокая уверенность, работает полностью, включая косвенные свидетельства.
- **«По смыслу»** (картограф судит, что для ЦПТ нужно нормальное распределение): около 0.6–0.7.
- **«Порядок курса»** (неделя 7 после недели 6): не связь `REQUIRES` между навыками, а номер места темы в курсе (`courseIndex`). Он нужен раскладке графа и плану, но не даёт ученику ложный косвенный зачёт. Если записать порядок как настоящую предпосылку, решение задачи недели 7 начнёт засчитывать неделю 1. Это испортит модель ученика.

**Этап E. Задачи семинара** размечаются по навыкам карты (связь `TESTS`). Из задач навыки создаются только в крайнем случае, когда задаче нужен навык, которого в карте нет. Задача недели 7, которая требует z-оценку из недели 6, становится сильным доводом для связи «по смыслу».

**Надёжность.** Ответ картографа сначала записывается событием с правкой, а код применяет её детерминированно. Повтор после сбоя применяет ту же записанную правку, а не просит модель заново. Так конфликты, как с `IdempotencyConflictError`, невозможны по самому устройству (законы 2, 5, 7).

**Чистка карты.** Тот же картограф раз в N изменений просматривает весь предмет: сливает дубли (навыки из материала, по которым ещё нет свидетельств, можно сливать без ученика), убирает пустые темы, пересматривает связи.

**Стоимость.** Сейчас на файл уходят N вызовов разметки, вызов `builder` на каждые 15 кандидатов и векторы. Станет примерно 1–2 вызова на файл и один на пачку. Дешевле и быстрее, а вся пачка разбирается одним шагом, а не очередью из 7.

### Как проверить, что стало лучше
- **Эталонные карты.** Нужен набор из 2–3 курсов с картами, составленными вручную: твоя статистика, матанализ по лекциям, один курс с силлабусом.
- **Метрики:**
  - число тем и навыков на тему;
  - доля пустых тем и дублей;
  - точность и полнота связей против эталона;
  - стабильность: те же файлы дважды должны дать почти ту же карту.

Новую схему включаем флагом в настройках только после того, как она обгонит старую на этом наборе.

## 2. Тема

Тема — то, что ученик видит и выбирает: «сегодня занимаюсь ЦПТ». Её размер задаёт одна сессия по ней или рассказ другу о том, что учишь. Поэтому навыки гибкие, а темы меняются редко и заметно для ученика: «объединил „ЦПТ“ и „выборочное распределение среднего“».

## 3. Откуда берётся структура: источников много, механизм один

Сейчас у каждого источника своя логика. Для материалов это `_subjects` и `builder`, для сессий — временные навыки учителя и извлекателя, отдельно есть гигиена графа. Предлагаю один механизм для всех.

**Любой источник оставляет наблюдения.** Наблюдение — это «вот понятие X, вот цитата, вот что про него, похоже, утверждается». Источники:
- **ход учителя и извлекатель** — основной источник, материалы не нужны вовсе;
- **просьба ученика:** «разбери со мной ЦПТ»;
- **задача и её разметка;**
- **материал** — только один из источников, без расчёта на нумерацию и порядок.

**Горячий путь не меняется.** Учитель размечает сразу, временный навык появляется мгновенно (§4.4), закон 9 соблюдён.

**Картограф — одна фоновая роль на предмет.** Он собирает новые наблюдения за последние минуты: из сессии, из файла, из чего угодно. Он видит текущую карту предмета целиком: темы, навыки, связи и сколько по каждому свидетельств. Ответ — правка карты в закрытом выборе по меткам: привязать, создать, переместить навык в другую тему, разделить, слить, связь. Код проверяет правку и пишет события. Повтор применяет уже записанную правку, а не спрашивает модель снова. Это заменяет и нынешний разбор материалов, и сверку временных навыков, и гигиену графа: одна роль, одна правда о предмете.

## 4. Связи: гипотезы с уверенностью, которую считает код

Это главное, что сейчас неправильно. Связь «нужно до» сейчас строится из случайного признака «в одном куске учат одно и используют другое». А связи можно получать из нескольких независимых источников, и они складываются.

| Источник | Пример | Нужен материал? |
|---|---|---|
| Знание предмета моделью | для ЦПТ нужно нормальное распределение и выборочное среднее | нет |
| Слова учителя в сессии | «тут опираемся на z-оценки» | нет |
| Ошибки ученика | ошибка в задаче на ЦПТ, а корень (`ROOT_CAUSE`) — в стандартной ошибке | нет |
| Разметка задач | задача на тему B требует навык темы A | нет |
| Прямое указание в тексте | «используя ЦПТ…», «см. лекцию 3» | да |
| Ученик | «это мне не нужно до», «связаны» | нет |

**Как считается уверенность.** У связи хранится список источников, а итоговую уверенность считает код, а не мнение модели (закон 4).
- Одно суждение модели по знанию предмета даёт среднюю уверенность. Этого достаточно, чтобы связь была видна на графе и задавала порядок плана. Но этого мало для косвенных свидетельств: порог `requires_min_confidence`, решение прошлого раза.
- Каждый следующий независимый источник уверенность повышает.
- Слово ученика сильнее всего.
- Если данные противоречат связи (B стабильно решается без A), уверенность падает.

Так граф получает «снизу основы» сразу, с первых сессий и без единого файла, а потом уточняется на реальном поведении ученика.

**Дешёвый кодовый сигнал.** Навык одной темы называет другую тему, как «apply Central Limit Theorem» в соседней теме. Совпадение имён код находит без модели и подаёт картографу как кандидата в связь. Твой скриншот поймался бы именно так.

**Порядок изучения** (что ученик учил раньше, номер недели, если он вдруг есть) — слабый вспомогательный сигнал. Он помогает раскладке и плану, но связью не становится.

# Навык: разбор с нуля

**Вывод заранее.** Навык — это единица измерения: система заводит его тогда, когда ей нужно что-то измерить или чему-то научить, а не когда в тексте встретилось слово. Размер навыка задаёт не лимит «1–6 на тему», а то, во что обходится его измерение: сколько попыток ученика и сколько сгенерированных задач нужно, чтобы о навыке появилось осмысленное суждение. Все цифры ниже — с первоисточниками, ценами OpenAI на сегодня и реальными объёмами токенов из журнала расходов стенда.

## 1. На чём это стоит: что известно в науке

**Компонент знания (knowledge component, KC).** В когнитивных тьюторах это центральное понятие. Фреймворк KLI (Koedinger, Corbett, Perfetti, 2012) определяет KC как приобретённую единицу знания, которую нельзя увидеть напрямую: о ней судят только по результатам на связанных задачах. Важное следствие для нас: навык — это гипотеза о том, как устроено знание в голове. Её подтверждают или опровергают данные, а не название.

KLI делит KC на виды, и от вида зависит, как учить:
- **факты** — запоминание и беглость;
- **понятия и процедуры** — индукция на примерах;
- **принципы** — понимание, объяснение.

Это прямо полезно учителю: для «формулы стандартной ошибки» и для «понимания, почему работает ЦПТ» нужны разные учебные действия.

**Как измеряется навык.** Классика — Bayesian Knowledge Tracing (Corbett & Anderson, 1995). Для каждого KC у каждого ученика хранится вероятность «знает». Она обновляется после каждой попытки с поправкой на угадывание и ошибку по невнимательности. Типичные параметры: скорость научения около 0.25, угадывание до 0.3, ошибка до 0.1. По моей арифметике при таких параметрах нужно в среднем около 4 попыток, чтобы ученик перешёл в «знает», и ещё несколько, чтобы модель это заметила. Отсюда главный инженерный факт: **у каждого навыка есть цена измерения, примерно 4–6 попыток ученика**. Если в теме 16 навыков, до осмысленного состояния темы нужно 60–100 задач.

Позднее показано (Koedinger et al., PNAS, 2023: 27 наборов данных, около 1.3 млн действий учеников): ученики сильно различаются стартовым знанием, но учатся с похожей скоростью на одну возможность практики. Сколько практики нужно до освоения, определяется в основном тем, что ученик знал до начала. Значит, навык нужно уметь быстро проверить на входе, а не гонять всех по одной программе. У этого вывода есть свежая критика (arXiv, 2026): оценка разброса скорости чувствительна к длине последовательностей. Но основной тезис устоял в независимой репликации Carnegie Learning (EDM 2024).

**Размер навыка — вопрос данных, а не вкуса.**
- В ASSISTments сравнили модели с 1, 5, 39 и 106 навыками для одних и тех же задач по математике 8-го класса. Самая мелкая, на 106 навыков, предсказывала результаты учеников лучше крупных (Pardos et al., 2007; Feng et al., 2009). Но там был огромный поток учеников на каждый навык.
- Learning Factors Analysis (Cen, Koedinger, Junker, 2006) — метод, который ищет лучшую разбивку задач на навыки операциями «разделить», «слить», «добавить». Критерий: насколько гладко падает доля ошибок с каждой попыткой (кривые научения). Экспертная разбивка почти всегда оказывается неточной: где-то два навыка надо слить, где-то один разделить.
- Улучшенная по данным модель навыков, переложенная обратно в тьютор, дала лучшее обучение в эксперименте («closing the loop»: Koedinger, Stamper, McLaughlin, Nixon, 2013).

**Почему нельзя полагаться на то, как эксперт сам описывает навыки.** Когнитивный анализ задач показывает: эксперт, описывая свою работу, пропускает около 70% важных решений (Feldon & Clark, 2006). В исследовании 2014 года хирурги, обучая операции, пропускали 71% шагов знания. Название навыка «от эксперта» (или от модели в роли эксперта) — это только начальное приближение.

**Что умеют языковые модели.**
- Moore, Schmucker, Mitchell, Stamper (2024): GPT-4 придумывал KC для тестовых вопросов, и эксперты в большинстве случаев (больше 60% вопросов) предпочли его названия своим. Но выборка маленькая, 80 вопросов.
- Wang, Lin, Koedinger (2025): навыки от модели почти не уступают экспертным в предсказании ответов учеников (ошибка около 0.426 против 0.421). Главная названная проблема — **повторяющиеся, почти одинаковые названия**. Это ровно наши 90 навыков с «check independence» и «test independence of events».
- KCluster (Wei, Carvalho, Stamper, EDM 2025): модель не придумывает навыки, а группирует похожие задачи, и каждая группа становится навыком. Такая разбивка предсказывала ответы лучше лучшей экспертной.

**Итог исследований:**
1. Модель хорошо даёт начальную разбивку на навыки, но склонна плодить дубли.
2. Лучшая разбивка привязана к задачам, а не к тексту лекций.
3. Её надо уточнять по ответам учеников.

**Важная честная оговорка.** LFA и KCluster работают на данных многих учеников по одним и тем же задачам. У нас граф личный, и данных одного ученика для статистики мало. Поэтому дробление навыков по данным одного ученика — гипотеза, а не проверенный метод. Ниже она так и помечена.

## 2. Какую задачу навык решает в системе

Навык нужен ровно для четырёх решений:
1. **Что ученик знает:** состояние темы, готовность к дедлайну. Это KC и трекинг.
2. **Что дать дальше:** какую задачу, что объяснить. Для этого задача размечена по навыкам — это Q-матрица, «задача → какие навыки проверяет».
3. **Когда повторить.** Забывание считается на единицу памяти. Современный стандарт здесь — FSRS (Ye et al., KDD 2022): у каждой единицы трудность, устойчивость и вероятность вспомнить. С 2023 года он встроен в Anki.
4. **Где корень ошибки:** заблуждение привязано к навыку.

**Отсюда рабочее определение.** Навык — это наименьшая единица, для которой системе нужно отдельное суждение, чтобы принять другое учебное решение, и которую можно наблюдать по задачам. Если по навыку нельзя получить свидетельство, это не навык, а слово. Если отдельное суждение о нём ничего не меняет в обучении, это лишнее дробление.

**Проверка ответа на исходный вопрос.** «1–6 навыков на тему» — не научная норма, а грубая страховка от дорогого измерения. Реальное ограничение — цена измерения (раздел 4). Поэтому вместо лимита — правило: **новая тема начинается с 1–2 центральных навыков, и каждый следующий должен окупиться**: он появляется, когда задачи или ошибки ученика показывают, что внутри навыка есть разные вещи.

**Как решаются твои примеры:**
- **«… in Excel», «NORM.DIST».** В курсе, где Excel обязателен, работа в Excel может быть настоящим процедурным навыком. По умолчанию это пометка «контекст: Excel» у задачи. Отдельным навыком она становится, только если ученик считает руками, но ошибается в Excel. Тогда это расхождение по данным, и навык делится.
- **«Check answer against a sketch»** — метакогнитивный навык, KLI такие признаёт. Но он общий для всех предметов, поэтому его место в профиле ученика, а не в графе статистики.
- **Глубина** («узнать», «применить», «доказать») — это уровни одного навыка, по пересмотренной таксономии Блума (Anderson & Krathwohl, 2001), а не новые навыки.

## 3. Что навык хранит в памяти

| Поле | Зачем | Источник идеи |
|---|---|---|
| `name` | действие: «вычислять стандартную ошибку среднего» | KLI |
| `definition` | одна фраза «умеет…», плюс что входит и что не входит | против дублей (Wang 2025) |
| `exemplars` | 1–2 образцовые постановки задач | разметка задач, KCluster |
| `kind` | факт, понятие, процедура, принцип | от вида зависит учебное действие (KLI) |
| `topic_id` | домашняя тема, одна | |
| эмбеддинг | по `name` + `definition`, а не по тексту куска | сейчас вектор строится по сырому тексту, это источник слепоты поиска |
| состояние | вероятность «знает» по уровням; память по FSRS; сколько показов | BKT, FSRS |
| `opportunities` | число попыток и последовательность исходов | кривая научения, критерий качества навыка |
| `contexts` | у каких задач какой контекст (Excel, руками) | сигнал для дробления |
| `status` | временный, активный, слит, разделён; псевдонимы | уже есть |
| `sources` | откуда взялся: ход, задача, материал, просьба ученика | провенанс |

Из нынешней схемы стоит убрать одно: `summary` как первые 300 знаков сырого текста куска. На этом сейчас стоит поиск кандидатов, и именно из-за этого он слепнет.

## 4. Как навык появляется и сколько это стоит

**Главный принцип: ленивое создание.** Навык становится узлом графа в момент первой нужды: учитель объясняет или даёт задачу, задачу размечают, ответ ученика проверяют, ученик просит. Материал навыков не создаёт. Он кладёт в тему черновой список кандидатов (просто текст, без узлов и без измерения). Из этого списка навыки берутся, когда по теме начинается работа. Так 7 семинаров не превратятся в 90 навыков, по которым никогда не будет ни одного свидетельства.

**Порядок жизни навыка:**
1. **Рождение в горячем пути.** Учитель размечает ход меткой существующего навыка или описанием нового. Сразу появляется временный навык, ход ничего не ждёт. Механизм уже есть.
2. **Сверка в фоне.** Раз в несколько минут на предмет: один вызов дешёвой модели. Она видит все навыки этой темы и соседних (их десятки, векторный поиск не нужен) и новые временные. Ответ — для каждого «это S7» или «новый: определение, вид, образец, тема». Код записывает.
3. **Слияние.** Два навыка всегда проверяются одними задачами с одинаковым исходом, или сверка видит дубль. Слияние без ученика допустимо, пока по навыкам нет расходящихся свидетельств.
4. **Дробление** (гипотеза, проверять). Внутри навыка ученик стабильно решает задачи одного контекста и проваливает другого, или заблуждение касается узкой части, или ученик просит. Тогда вызов модели в режиме «разделить», и задачи переразмечаются.

## 5. Что тут проверено, а что гипотеза

**Опирается на исследования:**
- навык — единица измерения, о нём судят по задачам (KLI);
- состояние навыка обновляется по попыткам (BKT, FSRS);
- разбивку на навыки нужно уточнять по данным (LFA, closing the loop);
- модель даёт хорошую начальную разбивку, но с дублями (Moore 2024, Wang 2025, KCluster 2025).

**Наши гипотезы, проверить до того, как строить:**
1. **Ленивое создание не ухудшает обучение.** Проверка: доля навыков, по которым через 2 недели после создания есть хотя бы 3 свидетельства. Сейчас по 90 навыкам семинаров она ноль.
2. **Сверка по списку навыков темы убирает дубли.** Проверка: прогнать те же 7 семинаров и диалоги дважды. Метрика — доля дублей и стабильность имён.
3. **Дробление по данным одного ученика работает.** Самая слабая гипотеза: статистики мало. Проверка по накопленным попыткам: стала ли кривая научения после дробления глаже, чем до.
4. **Когда появятся десятки учеников на общих предметах** (статистика — типичный), их навыки можно сопоставить между собой. Тогда включается настоящий LFA на общих данных. Это следующий уровень, не первый.

## 1. Компонент знания (knowledge component, KC)

**Коротко.** Навык — это не слово из лекции, а скрытая единица знания в голове ученика. Увидеть её нельзя, о ней судят только по тому, как ученик решает задачи.

**Подробно.** Фреймворк KLI (Koedinger, Corbett, Perfetti, 2012) делит обучение на три вещи:
- **что усваивается:** компоненты знания;
- **как идёт усвоение:** процессы научения;
- **что делает учитель:** учебные действия.

KC бывают явные (факт, принцип: «стандартная ошибка равна σ/√n») и неявные (умение: «вычислить стандартную ошибку по таблице»). Каждому виду подходит свой процесс научения:
- **запоминание и беглость** — для фактов: карточки, повторение;
- **индукция и уточнение** — для понятий и процедур: много разных примеров и задач;
- **понимание и осмысление** — для принципов: объяснение «почему», самообъяснение.

**Данные.** Таксономия выросла из обобщения сотен исследований в реальных классах. По одному из источников их больше 360, точную цифру в оригинале я не проверял.

**Математика.** Своей формулы нет. Это рамка, внутри которой работают модели ниже.

**Что берём в память.** Поле `kind` у навыка (факт, понятие, процедура, принцип). Учитель по нему выбирает действие: для факта — повторение, для принципа — объяснение.

## 2. Q-матрица: какие навыки проверяет задача

**Коротко.** Это таблица «задача → какие навыки она проверяет».

**Подробно.** Без такой разметки результат задачи не к чему приписать. Если задача проверяет два навыка, провал говорит о провале хотя бы одного из них. Это понятие из психометрии (Tatsuoka, 1983) лежит в основе всех моделей ниже.

**Математика.** Матрица Q размера «задачи × навыки» из нулей и единиц: `q[j][k] = 1`, если задача j требует навык k.

| Задача | стандартная ошибка | ЦПТ | z-оценка |
|---|---|---|---|
| «Найдите SE для n = 36, σ = 12» | 1 | 0 | 0 |
| «P(x̄ > 52), если μ = 50, σ = 12, n = 36» | 1 | 1 | 1 |

**Что берём в память.** Связь `(Task)-[:TESTS {level, context}]->(Skill)` и есть Q-матрица. Поле `context` (Excel, руками) мы добавляем, чтобы потом видеть расхождения внутри навыка.

## 3. Bayesian Knowledge Tracing (BKT): знает ли ученик навык прямо сейчас

**Коротко.** Для каждого навыка хранится одно число — вероятность, что ученик его знает. После каждой попытки оно пересчитывается.

**Подробно.** Модель Corbett & Anderson (1995) изначально работала в тьюторе по программированию на LISP. Ученик в каждый момент либо знает навык, либо нет. Ответ — шумный сигнал: знающий иногда ошибается по невнимательности, незнающий иногда угадывает. После каждой попытки ученик может научиться.

**Параметры** (у каждого навыка свои):
- `P(L0)` — знает ли с самого начала; типично 0.1;
- `P(T)` — вероятность научиться за одну попытку; типично 0.25;
- `P(G)` — угадать, не зная; обычно не выше 0.3;
- `P(S)` — ошибиться, зная; обычно не выше 0.1.

**Математика.** Два шага на каждую попытку.

Первый шаг: обновить вероятность по ответу (формула Байеса).
```
ответ верный:    P(L | верно)   = P(L)·(1−S) / [ P(L)·(1−S) + (1−P(L))·G ]
ответ неверный:  P(L | неверно) = P(L)·S     / [ P(L)·S     + (1−P(L))·(1−G) ]
```

Второй шаг: учесть, что за попытку можно научиться.
```
P(L) новое = P(L | ответ) + (1 − P(L | ответ)) · T
```

**Пример** (L0 = 0.1, T = 0.25, G = 0.2, S = 0.05), три верных ответа подряд:
- 1-й: 0.1 → 0.35 по ответу → **0.51** с учётом научения;
- 2-й: 0.51 → 0.83 → **0.87**;
- 3-й: 0.87 → 0.97 → **0.98**.

В тьюторах навык считают освоенным при P(L) ≥ 0.95. Значит, нужно около трёх верных попыток подряд, а с ошибкой посередине — больше. Отсюда цена навыка: 3–6 попыток ученика. Это моя арифметика на типичных параметрах, а не цифра из статьи.

**Что берём в память.** Число `pKnown` на навыке. Его считает код, проигрывая свидетельства по порядку (модель не участвует, закон 2). Параметры зависят от вида навыка и лежат в настройках, а не на узле.

## 4. AFM и Learning Factors Analysis: правильно ли нарезаны навыки

**Коротко.** Это проверка самой разбивки на навыки. Если навык нарезан правильно, доля ошибок по нему падает плавно с каждой попыткой. Если неправильно — кривая рваная.

**Подробно.** Additive Factors Model — логистическая модель успеха попытки. LFA (Cen, Koedinger, Junker, 2006) перебирает варианты Q-матрицы («разделить навык», «слить два», «добавить фактор») и оставляет тот, при котором AFM лучше объясняет данные. Учитывается и число параметров, чтобы не дробить ради дробления.

**Математика.**
```
logit(p_ij) = θ_i + Σ_k q_jk · (β_k + γ_k · T_ik)
```
- `p_ij` — вероятность, что ученик i верно решит задачу j;
- `logit(p) = ln(p / (1−p))` — перевод вероятности в шкалу, где удобно складывать;
- `θ_i` — сила ученика;
- `β_k` — лёгкость навыка;
- `γ_k` — скорость научения навыку;
- `T_ik` — сколько попыток по навыку k ученик уже сделал.

Пример: средний ученик (θ = 0), трудный навык (β = −0.5), γ = 0.1.
- 0 попыток: logit = −0.5, p ≈ **0.38**;
- 10 попыток: logit = 0.5, p ≈ **0.62**.

Критерий выбора разбивки, BIC:
```
BIC = −2·ln(правдоподобие) + (число параметров)·ln(число попыток)
```
Чем меньше BIC, тем лучше. Лишний навык добавляет параметры и штрафуется, если не объясняет данные заметно лучше.

**Данные.** Метод показан на данных когнитивных тьюторов. Найденные по данным разбивки потом заложили обратно в тьютор и проверили экспериментом на новых учениках («closing the loop»: Koedinger, Stamper, McLaughlin, Nixon, 2013). Точные цифры прироста я в оригинале не проверял.

**Что берём в память.** Счётчик попыток `opportunities` и последовательность исходов по навыку (её дают сами свидетельства). Этого хватает, чтобы позже построить кривую и проверить разбивку. Сам перебор LFA требует данных многих учеников, это следующий этап.

## 5. Ученики различаются стартом, а не скоростью (PNAS, 2023)

**Коротко.** Кто-то приходит, уже многое зная, но за одну попытку практики все учатся примерно одинаково.

**Данные.** Koedinger, Carvalho, Liu, McLaughlin: 27 наборов данных, около 1.3 млн действий учеников в тьюторах, онлайн-курсах и играх.
- Скорость научения у учеников почти одинаковая: около +0.1 логит, то есть примерно +2.5% точности за попытку.
- Сильно различается начальная точность.
- **Репликация:** на данных MATHia (EDM, 2024) вывод подтвердился.
- **Критика:** оценку разброса скорости завышает обрезка последовательностей. Обрезка до 10 попыток раздувает разброс на 75%, до 5 — на 205% (arXiv, 2026).

**Математика.** Та же AFM, но у каждого ученика своя добавка к скорости:
```
logit(p) = θ_i + β_k + (γ_k + γ_i) · T
```
Вывод статьи: `γ_i` почти у всех около нуля, а `θ_i` сильно разный.

**Что берём в память и в логику.** Отдельного поля нет. Это довод за быструю входную проверку навыка: 1–2 задачи на старте ставят ученика на правильное место и экономят ему практику.

---

## 6. Размер навыков: мелкая модель точнее, если хватает данных

**Данные.** ASSISTments, математика 8-го класса. Одни и те же задачи размечали моделями на 1, 5, 39 и 106 навыков и предсказывали результат итогового экзамена штата. Модель на 106 навыков предсказывала лучше крупных (Pardos et al., 2007; Feng et al., 2009). Но у неё был огромный поток учеников на каждый навык.

**Вывод для нас.** Мелкость сама по себе не зло. Зло — мелкость, по которой не будет данных. Отсюда правило: навык появляется, когда окупается измерением, а не «чем мельче, тем лучше» и не «не больше 6».

---

## 7. Эксперт не видит своих шагов

**Данные.** Когнитивный анализ задач:
- эксперт, описывая свою работу, пропускает около 70% важных решений (Feldon & Clark, 2006);
- хирурги, обучая операции, пропускали 71% шагов знания, 51% действий и 73% решений (исследование 2014 года).

**Вывод для нас.** Список навыков «из головы» — модели в роли эксперта, лектора, автора семинара — это только черновик. Его исправляют задачи и ошибки ученика.

## 8. Навыки от языковой модели

**Moore, Schmucker, Mitchell, Stamper (2024).** GPT-4 придумывал KC для 80 тестовых вопросов по химии и электронному обучению. Трое экспертов больше чем в 60% вопросов предпочли его названия своим. Минус: выборка маленькая.

**Wang, Lin, Koedinger (2025).** Модель придумывает KC для вопросов, потом почти одинаковые названия склеиваются по близости векторов.

Математика склейки, косинусная близость:
```
cos(a, b) = (a · b) / (|a| · |b|)
```
1 — смысл совпадает, около 0 — не связан. Если близость выше порога (например, 0.9), два названия считаются одним навыком.

Качество проверяли ошибкой предсказания ответов учеников:
```
RMSE = √( среднее по всем попыткам (y − p)² )
```
Здесь y — 1 или 0 (верно или неверно), p — предсказанная вероятность. Навыки модели дали около 0.426, экспертные — 0.421. Почти вровень. Главная проблема, которую авторы называют, — дубли.

**KCluster (Wei, Carvalho, Stamper, EDM 2025).** Модель не придумывает навыки, а оценивает, насколько два вопроса проверяют одно и то же. Похожие вопросы собираются в группы методом affinity propagation, и группа становится навыком. Такая разбивка предсказывала ответы лучше лучшей экспертной. Точную формулу меры сходства я по оригиналу не проверял.

**Что берём в память.**
- **Описание навыка:** `definition` (одна фраза «умеет…», что входит и не входит) и `exemplars` (1–2 образца задач). По ним новый навык сверяется с существующими, и дубли не появляются.
- **Вектор:** строится по `name` + `definition`. Сейчас он строится по сырому тексту куска, и это одна из причин слепоты поиска.

## 9. FSRS: когда повторять

**Коротко.** Это модель забывания: через сколько дней вероятность вспомнить упадёт до порога, когда пора повторить.

**Подробно.** FSRS (Ye, Su, Cao, KDD 2022) с 2023 года встроен в Anki. На каждую единицу памяти три величины:
- `D` — трудность: насколько тяжело даётся;
- `S` — устойчивость: через сколько дней вероятность вспомнить упадёт до 90%;
- `R` — вероятность вспомнить сейчас. Её не хранят, а считают из S и прошедшего времени.

**Математика.** Кривая забывания в версиях FSRS-4.5 и 5:
```
R(t, S) = (1 + (19/81) · t / S) ^ (−0.5)
```
Здесь t — дней с последнего повторения. При t = S выходит ровно 0.9.

Пример при S = 10 дней:
- через 10 дней R = **0.90**;
- через 30 дней R = (1 + 0.704)^(−0.5) ≈ **0.77**.

После каждого повторения код пересчитывает S и D. Удачное повторение увеличивает S: следующий интервал длиннее, и тем сильнее, чем ниже был R в момент повторения. Провал резко снижает S. В FSRS-6 показатель степени подбирается под ученика, в FSRS-7 добавлена кратковременная устойчивость. Точные формулы версий 6 и 7 я по официальному репозиторию не сверял.

**Что берём в память.** На навыке: `retDifficulty`, `retStability`, `retLastRecallAtMs`, `retDueAtMs`. R не хранится.

---

## 10. Уровни — это глубина, а не новые навыки

**Подробно.** Пересмотренная таксономия Блума (Anderson & Krathwohl, 2001): помнить → понимать → применять → анализировать → оценивать → создавать. Это шкала глубины владения одним и тем же знанием. «Применить ЦПТ» и «объяснить, почему ЦПТ работает» — два уровня одного навыка, а не два навыка. Строгую ступенчатость таксономии исследования подтверждают слабо. Поэтому уровни мы используем как шкалу глубины, а не как правило «нельзя уровень 4 без уровня 3».

**Что берём в память.** Состояние по уровням внутри навыка, а не отдельные навыки.

## Как навык лежит в памяти, всё вместе

Источник правды — журнал событий. Всё состояние ниже считает код по свидетельствам; модели только размечают.

**Узел `Skill`:**

| Поле | Хранится или считается | Откуда идея |
|---|---|---|
| `id`, `domainId`, `topicId` (одна домашняя тема) | хранится | |
| `name` — действие | хранится | KLI |
| `definition` — «умеет…», что входит и что нет | хранится | Wang 2025, против дублей |
| `exemplars` — 1–2 образца задач | хранится | KCluster |
| `kind` — факт, понятие, процедура, принцип | хранится | KLI |
| `embedding` по `name` + `definition` | считается при записи | |
| `pKnown` по уровням 1–6 | считает код по свидетельствам | BKT |
| `opportunities` — число попыток | считает код | AFM, кривая научения |
| `retDifficulty`, `retStability`, `retLastRecallAtMs`, `retDueAtMs` | считает код | FSRS |
| `status`, `aliases` | хранится | слияние и деление |
| `sources` — откуда взялся | хранится | провенанс |

**Связи вокруг навыка:**
- `(Task)-[:TESTS {level, context}]->(Skill)` — Q-матрица; `context` — Excel, руками и т.п.;
- `(Evidence)-[:ON]->(Skill)` — каждая попытка с исходом, уровнем, контекстом и временем. Из них код считает `pKnown`, `opportunities` и FSRS;
- `(Misconception)-[:ABOUT]->(Skill)` — заблуждения.

**Чего нет на навыке:**
- сырого текста куска лекции;
- параметров BKT: они в настройках по `kind`;
- R: вероятность вспомнить считается на лету.

## Где предложение ломается

### 1. BKT по уровням не сойдётся на наших данных

BKT придумана для тьютора, где ученик решает десятки однотипных задач по одному навыку, а ответ всегда «верно / неверно». У нас всё не так:

- **Мало попыток.** Сессия — это диалог: 5–15 оцениваемых попыток, разбросанных по нескольким навыкам. При 20 сессиях в месяц и 30 навыках выходит примерно 5 попыток на навык в месяц. Это моя прикидка, данных по реальным ученикам у нас пока нет.
- **Уровни делят и без того малые данные.** Если считать отдельную вероятность на каждый из 6 уровней, на уровень достанется по одной попытке. Я сам выше говорил, что каждый навык стоит 3–6 попыток, и тут же умножил это на шесть.
- **Параметры не из чего оценить.** В исследованиях вероятности угадывания, ошибки и научения подбираются по данным тысяч учеников. У нас граф у каждого свой, и подбирать не на чем. Параметры «по виду навыка» я бы просто придумал. Тогда BKT превращается в правило «три верных подряд», только переодетое в формулы.
- **Задачи разной трудности.** BKT считает все задачи по навыку одинаковыми. У нас задачи генерируются и сильно различаются по трудности. Провал на трудной задаче и провал на лёгкой — разные сигналы, а BKT их не различает.
- **Проверяльщик ошибается.** Вердикт часто выносит модель, и у неё есть своя ошибка, отдельная от ошибки ученика. В BKT такого шума нет вообще.

### 2. FSRS на сложных умениях — экстраполяция

FSRS обучен на миллионах повторений карточек в Anki: атомарный факт, ученик сам оценивает, вспомнил или нет. «Применить ЦПТ» — не карточка. Повторение здесь — это задача с проверкой, а не самооценка, и как такое умение забывается, FSRS не моделирует. Для навыков-фактов (формула, определение) он годится. Для процедур и принципов это непроверенная гипотеза, а я подал её как готовый механизм.

### 3. Проверить разбивку на навыки по данным одного ученика нельзя

LFA и кривые научения работают на данных многих учеников по одним и тем же задачам. У одного ученика за месяц около 5 попыток на навык — кривой нет. Значит, поле `opportunities` полезно как журнал, но решений ещё долго принимать не будет. Дробление навыка по данным одного ученика — самая слабая часть предложения.

### 4. Цифры про языковые модели я подал слишком бодро

Ошибка предсказания около 0.426 у навыков модели против 0.421 у экспертных показывает, что модель примерно не хуже эксперта. Но это не значит, что обе разбивки хорошие: на ответах «да / нет» такая ошибка говорит о слабом предсказании в целом. К тому же эти исследования шли на готовых банках вопросов с данными учеников, а у нас ни того, ни другого.

### 5. Ленивое создание ломает граф тем

Если навыки появляются только тогда, когда по ним идёт работа, у предложенных тем из материалов навыков нет. А связи между темами сейчас выводятся только из связей навыков. Значит, решение про навык сразу требует, чтобы связи между темами существовали сами по себе. Это нужно решать вместе с темой, отдельно не получится.

### 6. Деление навыка дорогое и хрупкое

Чтобы разделить навык, модели нужно заново разметить все прошлые свидетельства. Это деньги и новые ошибки разметки. А сигнал «пора делить» у одного ученика слабый. На практике деление будет случаться редко, и навыки останутся крупными. Это не катастрофа, но тогда весь механизм деления — сложность без отдачи.

## Что в предложении правильно и остаётся

- **Журнал свидетельств** как главная память. Каждая попытка хранит задачу, проверенные навыки, исход, уровень, контекст, подсказки, время и уверенность проверяльщика. В нынешней схеме Quack почти всё это уже есть: `assistance`, `hintStep`, `confidence`, `verification`, `solveTimeMs`. Это сырые факты, и любую модель состояния можно потом пересчитать по ним заново, ничего не теряя.
- **Q-матрица с контекстом:** связь «задача → навык» с пометкой Excel или «руками».
- **Описание навыка:** `definition` и `exemplars` против дублей, вектор по описанию, а не по сырому тексту куска.
- **Вид навыка** (факт, понятие, процедура, принцип). Это простое и полезное поле для выбора учебного действия.

## Что в памяти нужно, чтобы обучение действительно стало эффективнее

Учить лучше помогают конкретные приёмы с сильной доказательной базой, и память должна их обслуживать.

| Приём | Насколько надёжно | Что для него нужно в памяти | Есть в предложении? |
|---|---|---|---|
| Практика с вспоминанием | высокая польза (Dunlosky et al., 2013) | банк задач на навык, история попыток | да |
| Распределённое повторение | высокая польза (Dunlosky et al., 2013) | когда последний раз успешно вспомнил, оценка устойчивости | частично: FSRS только для фактов |
| Освоение до перехода дальше | положительный эффект в 108 контролируемых сравнениях (Kulik et al., 1990) | оценка «освоил ли» и связь «нужно до» | да, но оценка ненадёжна |
| Подходящая трудность задачи | | **трудность задачи** | **нет** |
| Чередование похожих тем | средняя польза (Dunlosky et al., 2013) | **с чем ученик путает навык** | **нет**, хотя заблуждения есть |
| Подсказки и разобранные примеры, когда ученик ещё новичок | | сколько помощи понадобилось | да, `assistance` |

**Двух вещей не хватает:** трудности задачи и пар «путает A с B». Без трудности нельзя давать задачу «чуть выше текущего уровня». Без пар путаницы нельзя строить чередование.

## Что я бы поменял

**1. Оценку знания — на рейтинг Эло для ученика и задачи.** Пелánek (2016) описывает Эло в адаптивных учебных системах так: ответ — «матч» ученика против задачи, после него обновляются и сила ученика по навыку, и трудность задачи. Метод простой и устойчивый, работает онлайн с первой попытки, не требует подбора параметров на тысячах учеников и сам учитывает трудность.

```
p = 1 / (1 + e^(−(θ − d)))        вероятность верного ответа
θ ← θ + K · (исход − p)           сила ученика по навыку
d ← d − K · (исход − p)           трудность задачи
```

Здесь θ — сила ученика по навыку, d — трудность задачи, K — шаг обновления.

**Пример.** θ = 0, задача d = 1, тогда p ≈ 0.27. Ученик решил трудную задачу: θ вырастает заметно, на 0.73·K. Решил лёгкую: почти не меняется. Это ровно та чувствительность к трудности, которой нет у BKT.

**2. Уровни — свойство задачи, а не отдельная оценка.** Сила ученика по навыку одна, а задачи уровня 4 просто трудные. Данные перестают делиться на шесть частей.

**3. Шум проверяльщика — в шаг обновления.** Вердикт с низкой уверенностью двигает оценку слабее: K умножается на уверенность.

**4. Повторение — честно разделить.** Для фактов и формул — FSRS, там он проверен. Для процедур — простое правило «повторить после интервала, который растёт после каждого успеха», с пометкой «гипотеза, проверяем».

**5. Деление навыков — отложить.** Пока навыки только сливаются: дубли при появлении и «всегда проверяются вместе». Деление — только по просьбе ученика. Настоящее уточнение разбивки появится, когда на общих предметах будет много учеников.

**6. Добавить в память трудность задачи** (уровень, заданный генератором, плюс уточнение по ответам) и связь «путает с». Связь можно строить из уже существующих заблуждений.

## Как проверить, что память работает, не гадая

**1. Офлайн, на журнале.** Предсказывает ли память следующую попытку лучше простого базового правила («доля верных ответов ученика по навыку»)? Мера — AUC и ошибка предсказания. Если наша модель не обгоняет счётчик, она бесполезна, сколько бы формул в ней ни было. Это можно делать уже на первых десятках учеников.

**2. Онлайн, сравнение двух групп.** Выбор задачи по модели против выбора без неё. Мера — результат на отложенной проверке через неделю. Это единственный честный ответ на вопрос «стало ли обучение эффективнее».

## Итог

- **Что хранить:** журнал свидетельств, описание навыка, Q-матрица с контекстом. Это правильно, и это фундамент.
- **Не хватает:** трудности задачи и связи «путает с».
- **Как считать:** BKT по уровням и FSRS для всего подряд — неправильно для наших данных. Нужен Эло для ученика и задачи с учётом уверенности проверки, FSRS только для фактов, а всё остальное помечено как гипотеза и проверяется предсказанием по журналу.

## 1. Устройство: дерево навыков внутри темы

- **Корень.** У каждой темы ровно один корневой навык: «владеет темой в целом». Он появляется в том же событии, что и тема. У любой темы с первой секунды есть единица измерения, даже у бледной темы из материала, по которой ещё не было работы.
- **Дети.** Навыки появляются внутри темы по мере работы: «вычислять стандартную ошибку среднего» внутри «ЦПТ». Пока глубина ограничена двумя уровнями, корень и дети. Нужен ли третий, покажут логи.
- **Связи между темами** — это связи между их корнями, они существуют сами по себе. Связи между детьми возможны, но не обязательны. Ленивое создание детей граф тем больше не ломает.

*Основа:* решение продуктовое, гипотеза. Из исследований берём только то, что навык — единица измерения, о которой судят по задачам (KLI).

## 2. Как считается, что ученик знает

Модель Эло для ученика и задачи (Пелáнек, 2016), с иерархией: сила по ребёнку = сила по теме + поправка ребёнка.

```
θ(ребёнок) = θ_корня + δ_ребёнка          (δ нового ребёнка = 0)
p = 1 / (1 + e^(−(θ − d)))                 вероятность верного ответа
после попытки с исходом y (1 или 0) и уверенностью проверки c (0..1):
  θ_корня   += K_корня   · c · (y − p)
  δ_ребёнка += K_ребёнка · c · (y − p)
K = K0 / (1 + a · n)                       n — число попыток по этому навыку
```

**Что это даёт:**
- **Новый ребёнок не начинает с нуля.** Он наследует общую силу по теме. Никакой переразметки прошлых свидетельств, а значит, нет дорогого и хрупкого деления навыков, которое я критиковал.
- **Задачи на ребёнка двигают и тему.** Решил задачи на стандартную ошибку — растёт и сила по ЦПТ.
- **Поправка δ видна напрямую.** Если ребёнок заметно отличается от темы («тему знает, стандартную ошибку путает»), это видно по δ, и учитель может учить точечно.
- **Трудность задачи учитывается.** Провал на трудной задаче почти не роняет оценку, провал на лёгкой роняет сильно.
- **Шум проверяльщика учитывается.** Вердикт модели с низкой уверенностью двигает оценку слабо.
- **Шаг K падает с числом попыток.** В начале оценка подвижная, потом устойчивая.

**Уровни 1–6 — свойство задачи, а не отдельные оценки.** Задача уровня 4 просто имеет большую трудность d: стартовое значение по уровню из настроек. Данные не делятся на шесть частей.

**«Освоил на уровне L»:** вероятность решить типовую задачу уровня L не ниже 0.8. Порог в настройках.

*Основа:*
- Эло в адаптивном обучении — исследование: простой, устойчивый, работает с первых попыток (Pelánek, 2016).
- Иерархическая поправка и учёт уверенности — гипотеза.
- Числа K0, a, порог 0.8 — стартовые значения, подбираются по логам.

## 3. Повторение

- **Для навыков-фактов** (формула, определение) — FSRS: трудность, устойчивость, дата последнего успешного вспоминания. Для такого вида знаний он проверен.
- **Для понятий, процедур и принципов** — простое правило. После успешного вспоминания через паузу интервал растёт вдвое, после провала падает вдвое, минимум 1 день.

*Основа:* распределённое повторение — исследование (Dunlosky et al., 2013, высокая польза). FSRS для фактов — исследование. Правило для процедур — гипотеза.

## 4. Как появляются навыки

1. **Тема появилась** из сессии, материала или просьбы → в том же событии появляется корень. Модель не вызывается, имя корня = имя темы.
2. **Материал** кладёт в тему черновой список детей: только текст, без узлов. Когда дети начнут появляться, сверка возьмёт имена отсюда, и названия будут согласованы.
3. **Ребёнок рождается в горячем пути.** Учитель размечает задачу или объяснение меткой существующего навыка или пишет «новый: имя, тема». Сразу появляется временный ребёнок с δ = 0, ход ничего не ждёт.
4. **Сверка в фоне**, раз в несколько минут на предмет. Один вызов дешёвой модели. Она видит всех детей этой темы (их единицы, векторный поиск не нужен), черновик темы и новых временных. Ответ: «это существующий S3» или «новый: определение, вид, образец задачи». Код дополнительно ловит дубли по близости векторов (`name` + `definition`).
5. **Слияние** — когда два ребёнка всегда проверяются одними задачами или сверка видит дубль. Слить с поправкой — значит сложить попытки, это делает код.
6. **Деления нет.** Если тема стала слишком общей, внутри неё просто появляются новые дети. Для этого и нужно дерево.

## Что она решает по-настоящему

1. **Измерять можно с первой секунды.** У любой темы, включая бледную из материала, сразу есть единица, к которой крепятся свидетельства. Это закрывает дыру ленивого создания: связи между темами — это связи корней, они не ждут, пока появятся мелкие навыки.

## Где она ломается

1. **Широкая тема даёт бессмысленную среднюю оценку.** «Discrete Random Variables» — это биномиальное распределение, Пуассон и матожидание. Ученик знает первое и не знает второе, а корень показывает «средне», и система советует повторять всё подряд. В терминах исследований это ровно «плохой компонент знания»: его кривая научения рваная, и LFA разделил бы его первым делом (Cen, Koedinger, Junker, 2006). То есть корень хорош только для узкой темы, а для широкой он плох по самому устройству.
2. **Непонятно, что такое «задача на всю тему».** Корень называется «владеет темой», но одной задачей это не проверить. Генератор будет брать случайную грань темы, и оценка корня станет зависеть от того, какие грани попались.
3. **Мелкие навыки на самом деле не дерево.** z-оценка нужна и в нормальном распределении, и в ЦПТ, и в проверке гипотез. Дерево заставляет её жить в одной теме. Если правила нет, учитель будет создавать «z-оценку» ребёнком в каждой теме, где она встретилась, и мы получим те же дубли, только в дереве.
4. **Если учитель всегда размечает корень, детей не будет никогда.** Размечать корень проще. Тогда дерево остаётся плоским, а диагностики «что именно не понимает» нет. Самой по себе детализации не произойдёт, нужен механизм, который её запускает.
5. **Деление вернулось через заднюю дверь.** Темы правятся: временные темы из сессий сливаются, ученик просит разделить тему. Раз тема — это корень-навык, слить или разделить тему значит слить или разделить оценку. Слияние решается пересчётом по журналу свидетельств. Деление широкой темы — та самая сложность, которую мы хотели убрать.
6. **«И так далее» вглубь — путь к переусложнению.** Без ограничения глубины рекурсия по навыкам усложняет и разметку, и поиск дублей, и пересчёт.

## Что нужно, чтобы она работала

1. **Темы должны быть узкими:** одна главная идея. Это правило для того, кто создаёт темы. «Discrete Random Variables» — это три темы, а не одна. Тогда корень — нормальная единица измерения, а не среднее по несвязанным вещам. Если тема всё же широкая, оценка корня помечается как грубая и решений «освоил» по ней не принимается.
2. **Задачи на корень покрывают грани по очереди.** Задача «на тему» — это задача на одну из граней из черновика темы. Грани чередуются, а грань записывается в контекст задачи.
3. **Ребёнок принадлежит только своей теме.** Если нужное умение уже живёт в другой теме, это не новый ребёнок, а связь «нужно до» на существующий навык. Сверка это проверяет.
4. **У появления детей есть запуск.** Ребёнок появляется, когда учитель называет конкретику, или когда у корня разные исходы по разным граням (в контексте задач это видно), или когда ученик просит.
5. **Если тема распадается на явно разные части, делится тема, а не оценка.** Признак — дети с сильно разными поправками δ. Тогда тема делится на две, её дети расходятся по новым темам вместе со своими свидетельствами, и корни новых тем пересчитываются по журналу.
6. **Глубина — не больше двух уровней:** корень и дети. Третий уровень — только если логи покажут, что без него не обойтись.

## Что проверить в логах

## 4. Как считается знание

Модель Эло для ученика и задачи (Pelánek, 2016):
```
p = 1 / (1 + e^(−(θ − d)))          вероятность верного ответа
θ += K · c · (y − p)                y — исход (1 или 0), c — уверенность проверки (0..1)
K = K0 / (1 + a · n)                n — попыток по навыку: сначала подвижно, потом устойчиво
```

- **Уровень задачи** входит в её трудность d.
- **«Освоил на уровне L»:** вероятность решить типовую задачу уровня L не ниже 0.8.
- **Старт нового навыка** (гипотеза): θ = средняя сила ученика по другим навыкам этой темы, если они есть, иначе 0. Это мягкий вариант твоей идеи, без дерева.
- Числа K0, a и порог 0.8 — стартовые значения из настроек.

Да, схлопывает, и это серьёзная претензия. Одно θ с уровнем внутри трудности задачи предполагает, что все уровни лежат на одной шкале: умеешь доказывать — значит, точно умеешь применять, и наоборот. В обучении это часто неверно.

## Почему одно число неверно

**Понимание и умение делать развиваются отдельно.** Исследования связи понятийного и процедурного знания в математике показывают, что эти два вида знания влияют друг на друга, но развиваются не синхронно: каждый может обгонять другой. Возможны расхождения в обе стороны. Отсюда «итеративная модель» (Rittle-Johnson, Siegler, Alibali, 2001; обзор Rittle-Johnson, Schneider, Star, 2015). Типичный пример: студент подставляет числа в формулу стандартной ошибки, но не может объяснить, почему там √n. Или наоборот: понимает идею ЦПТ, но путается в вычислениях.

**Учителю нужен профиль, а не балл.** «Делает, но не понимает» требует объяснения и самообъяснения. «Понимает, но не делает» требует отработки. Одно θ = 0.4 говорит «где-то посередине» и не подсказывает, что делать. Для карточки «почему такое состояние» оно тоже бесполезно.

**Технически это допущение одномерности, как в модели Раша.** Оно годится, когда задачи навыка действительно проверяют одно и то же с разной трудностью. Уровни 1–6 по построению проверяют разное: узнать, объяснить, применить, выбрать метод, перенести, доказать.

## Почему 6 отдельных оценок — тоже плохо

Это обратная крайность: данные делятся на шесть частей, и на каждый уровень приходится по 1–2 попытки. Нынешний код смягчает это вручную, выводя уровни друг из друга: доказан уровень 4 — считается доказанным и уровень 3. Но это жёсткое правило, и оно не умеет «частично».

## Что правильно: общая сила плюс поправки по измерениям

Это частичное объединение данных, тот же приём, что был с «темой как крупным навыком», только внутри навыка:

```
θ(навык, измерение) = θ_навыка + δ_измерения       (δ стартует с 0)
предсказание для задачи: p = σ(θ_навыка + δ_её_измерения − d_задачи)
после попытки:  θ_навыка    += K₁ · c · (y − p)
                δ_измерения += K₂ · c · (y − p)
```

- **Любая попытка учит модель общему.** Решил задачу на применение — немного растёт и ожидание по объяснению. Данные не делятся на шесть частей.
- **Расхождение видно.** Если ученик стабильно применяет, но проваливает объяснения, δ по объяснению уходит в минус. Это и есть профиль «делает, но не понимает».
- **Измерений немного: те, которые меняют учебное действие.** Шесть уровней здесь, скорее всего, лишние. Рабочий вариант — три:
  - **знать:** узнать, вспомнить — уровни 1–2;
  - **делать:** применить, выбрать метод — уровни 3–4;
  - **понимать:** объяснить, перенести, доказать — уровни 2, 5, 6.

  Объяснение (уровень 2) я отнёс к «понимать», а не к «знать»: учебное действие для него — разобрать «почему», а не повторить. Точная раскладка уровней по измерениям — гипотеза, её проверяем.

## Как проверить, что это не опять одно бесполезное число

1. **Есть ли расхождения у реальных учеников.** Доля навыков, у которых после 5+ попыток поправка какого-то измерения по модулю больше 0.5. Если почти у всех поправки около нуля, измерения не нужны и одного числа хватает. Если расхождения частые, профиль обязателен.
2. **Предсказание.** Модель с поправками должна предсказывать следующую попытку лучше одного θ и лучше нынешнего расчёта по уровням. Все три считаются рядом по одному журналу.
3. **Польза для учителя.** Когда профиль говорит «делает, но не понимает», объяснение должно давать больший прирост, чем ещё одна задача на применение.

Итог: ты прав, одно θ с уровнями внутри трудности — это ошибка. Правильная форма — общая сила навыка плюс поправки по 2–3 измерениям. Она не делит данные на шесть частей и при этом сохраняет то, что нужно учителю.

## 2. Что отпало из моих предположений

- **Порядок курса как сигнал связей** — ты отверг: система не должна зависеть от материалов и нумерации.
- **Эло вместо свёртки** — ошибка: смешивает понимание и забывание, теряет знакомство, границу цели и объяснимость.
- **«Тема — крупный навык» как основа** — не берём, гипотеза.
- **Ленивое создание навыков** — критик показал, что оно ломает всё:
  - у задачи семинара должна быть связь `TESTS` и `skill_id` (проверка формы разметки);
  - поиск по материалам идёт через связь «кусок → навык»;
  - тема с одним проверенным навыком из пяти выглядела бы готовой, хотя проверено не всё;
  - «Сегодня» и темп используют `MATCH (t)-[:COVERS]->(s)`, и темы без навыков просто выпадают;
  - косвенные свидетельства не применяются задним числом, а навыка-предпосылки ещё нет.
- **Хранимые связи между темами** воссоздают два расходящихся графа, которые документ (§3.4.5) отверг не зря.

## 3. Что показали исследования про связи от модели

- **В открытой генерации, как у нас, ошибок много.** В ближайшей к нашей постановке работе (InstructKG, 2026) F1 около 0.3, а направление угадывается в 62% случаев. Разбор неверных связей:
  - 49% правдоподобны, но ничем не подтверждены;
  - 28% перевёрнуты;
  - 22% не того типа.
- **Когда пары уже выбраны и сбалансированы,** GPT-4 без обучения даёт F1 около 0.78, но склонен говорить «да, предпосылка». Цепочка рассуждений вредит.
- **Даже эксперты согласны между собой лишь умеренно:** каппа 0.59–0.65.
- **Нет надёжных данных, что упорядочивание по предпосылкам само по себе улучшает обучение.** У ALEKS — «не хуже традиционного обучения, но и не лучше». Адаптивный порядок в эксперименте Mu et al. повысил эффективность, но не итоговый результат.

**Вывод.** Связи от модели — подсказка для навигации, а не правда о голове ученика. Они должны быть слабыми и исправляемыми.

## 4. Решение

**1. Навыки — узлы с самого начала, но отобранные; состояние появляется лениво.**
- При создании темы писатель структуры (п. 3) составляет её навыки из всего, что известно: разделы материала, задачи, слова учителя.
- Новый навык сверяется с навыками темы (закрытый список) и с похожими навыками других тем по вектору. Если умение уже живёт в другой теме — ставится связь «нужно до», а не создаётся навык.
- У навыка: `name`, `definition`, `exemplar`, `kind`; вектор по имени и определению. Сырой текст куска на навыке не хранится.
- Инструмент (Excel) — контекст задачи. Метанавыки — профиль ученика.
- Ориентир: начинать с 1–4 навыков на тему, больше — только если источники показывают явно разные вещи. Ориентир документа «1–6» тут остаётся оправданным: это цена измерения, а не догма.
- **Состояние у всех навыков сначала «не проверено».** Тема честно показывает «проверено не всё». Есть метки для учителя, цели для задач, концы для связей. Пересборка детерминирована.

**2. Связи остаются одной правдой — между навыками.** Связи тем по-прежнему выводятся из них, документ §4.6 не меняется. Источники:
- **прямо в материале:** учит X и опирается на Y — высокая уверенность, как сейчас;
- **знание предмета моделью (новое):** при появлении навыка модель оценивает в обе стороны пары с короткого списка кандидатов, по шкале от −1 до 1, без цепочки рассуждений. Код оставляет только согласованное направление и делает транзитивное упрощение. **Уверенность ниже порога 0.6:** такая связь видна на графе, задаёт порядок и мягкое предупреждение, но не даёт косвенных свидетельств;
- **ученик:** правка — максимум или удаление;
- **позже — ошибки ученика** с корнем в другом навыке повышают уверенность.

**3. Один писатель структуры на предмет** — расширение нынешней гигиены, под той же блокировкой предмета.
- Он единственный решает «новая тема или существующая»: закрытый выбор против полного списка тем, пока их около 80 или меньше. Дальше — по короткому списку: ближайшие по вектору, соседи по графу, темы того же материала.
- Он же составляет навыки и ставит связи.
- Работает пачками примерно по 15 разделов, и каждая пачка сразу записывается: граф растёт на глазах.
- Описание темы — новое событие.

**4. Материал: сначала оглавление.** Один проход по всему файлу даёт разделы с описаниями. Потом куски относятся к уже готовому оглавлению, а не придумывают темы сами — это стабильность. Каждая задача листа относится к теме и навыку. Прямые утверждения «нужно до» сохраняются с цитатой.

**5. Разметка задач — выбор из навыков темы.** Генератор, учитель и задачи семинара получают метки навыков темы. Новый навык — только если ни один не подходит: он временный и сверяется писателем. Это закрывает те 74 лишних навыка.

**6. Горячий путь.** У учителя есть метки, потому что навыки темы уже существуют. Временный навык получает тему текущей сессии. Сейчас здесь расходятся код и документ: в коде у нового навыка учителя только `name` (`teacher/v3.md:118`), и проектор оставляет его без темы до гигиены.

**7. Хабы.** Из материалов — нет, по твоему решению. Хабы под дедлайн из силлабуса и по просьбе ученика остаются: это его явное намерение.

**8. Не меняется:** свёртка, свидетельства, FSRS, правила косвенных свидетельств.

1. **«Задача на всю тему» не определена.** Закрыто так: центральный навык — это не «владеет темой», а главное умение темы, названное действием: «применять ЦПТ к выборочному среднему». Его можно проверить одной задачей.
2. **Широкая тема даёт среднюю оценку.** Закрыто так: внутри темы появляются новые навыки, когда по ним идёт работа (следующий раздел). Состояние темы уже сейчас собирается из всех её навыков по правилам приоритета (§8.6): если один навык провален, тема покажет «пока не получается», а не среднее.
3. **«Дробление» не нужно.** Центральный навык не делится. Новые навыки просто появляются рядом и копят свидетельства с момента рождения, а история центрального навыка остаётся при нём.

## Новый навык посреди сессии

**Когда он появляется.** Только из конкретного действия ученика: учитель даёт задачу или объяснение по чему-то более узкому, чем навыки темы, и ученик на это отвечает. Разметка этого хода и рождает навык. Свидетельство появляется сразу, поэтому навык без единой попытки ученика родиться не может.

**Механизм:**
1. **Учитель выбирает из меток навыков текущей темы.** Новый навык — только если отдельная проверка этого умения изменит, что учитель делает дальше. Это правило в промпте.
2. **Проектор**, без модели (закон 2): временный навык в теме, на которой сейчас сфокусирована сессия. Тот же приём, что уже есть у извлекателя (`evidence_validation.py:120-129`). Совпадение имени с существующим навыком предмета — это тот же навык. Свидетельство крепится сразу.
3. **Писатель в фоне** сверяет временный навык с навыками темы и похожими навыками других тем. Варианты исхода:
   - дубль → слить, свидетельства переходят;
   - новый → дописать определение и образец задачи;
   - на самом деле это умение другой темы → привязать туда и поставить связь «нужно до».
4. **Целесообразность меряем, а не предполагаем:**
   - сколько новых навыков набрали хотя бы 3 свидетельства за 14 дней;
   - сколько писатель слил как дубли;
   - сколько ушло в другие темы.

- Свидетельства, правила косвенных свидетельств (§7.5–7.6), порог `requires_min_confidence = 0.6`.
- Временные навыки горячего пути как механизм (§4.4), короткие метки (§4.5).
- Связи тем не хранятся, а выводятся из связей навыков (§3.4.5, §4.6).
- Хабы из силлабуса с дедлайном, хабы по просьбе ученика (`new_hub_name` учителя), хаб всего предмета.
- Существующие предметы не перестраиваются.

## 4. Решение

### 4.1 Тема и её центральный навык

**Правило.** У каждой темы со статусом `proposed` или `active` ровно один центральный навык: главное умение темы, названное действием («применять ЦПТ к выборочному среднему»). Он создаётся в той же пачке событий, что и тема. Других навыков при создании темы нет.

**Критерий темы, для любого источника:** у темы есть одно центральное умение, которое можно назвать действием. Не получается назвать одно — это две темы.

**События (только добавочные необязательные поля, старые события должны валидироваться):**
- `_TopicNew` (`events/event_types.py`, около строки 285; общий для `topic.created` и `topic.proposed`): добавить `description: str | None = None`, 1–3 фразы о теме.
- `SkillCreated` (около строки 332), добавить:
  - `core: bool = False`;
  - `definition: str = ""` — одна фраза «умеет…», что входит и что не входит;
  - `exemplar: str = ""` — один образец постановки задачи;
  - `kind: Literal["fact","concept","procedure","principle"] | None = None`.
- `summary` у новых навыков заполнять значением `definition`. Сырой текст куска в навык не писать нигде.
- Если каталог событий или тесты схем требуют поднять `schema_version` при новых полях — сделать по существующему образцу (`turn.committed`).

**Проекция.**
- `Topic.description`; `Skill.core`, `Skill.definition`, `Skill.exemplar`, `Skill.kind`.
- `embedding` навыка: `name` + `definition`, у старых навыков `name` + `summary`. Правка `node_text` в `ops/material_parse.py` и везде, где навыку считается текст для вектора.

**Инварианты (проверяются кодом и тестами):**
- Ровно один `core = true` навык на тему.
- При слиянии тем центральный навык темы-дубля сливается в центральный навык выжившей темы (`skill.merged`), свидетельства переходят, как сейчас.
- При делении темы (`agents/topic_split.py`) каждая новая часть получает центральный навык: либо существующий навык части, назначенный центральным, либо новый.
- Центральный навык нельзя удалить отдельно от темы; удаление темы удаляет его вместе с ней (как сейчас удаляются навыки темы).

**Все места создания тем** должны давать центральный навык. Найти поиском `TopicCreated(` и `TopicProposed(`: сейчас это `agents/reconcile.py:376` и `agents/hygiene.py:612`, плюс `topic_split.py`. Новые темы в коде создаёт только писатель структуры (4.2). Устаревшая ветка `topic_hint` в `handlers.py` остаётся только для старых событий журнала.

### 4.2 Писатель структуры (один на предмет)

Расширение нынешней задачи `graph.hygiene` (`agents/hygiene.py`): тот же `lock_key = domain:{id}`, та же роль `builder`, новый режим промпта **Structure**. Он заменяет `reconcile_domain` в разборе материалов и режим Topics гигиены. Режим Hygiene (пары дублей навыков и заблуждений) остаётся.

**Входы одного вызова:**
- **Кандидаты в темы** из разбора материала (4.3): имя, описание, имя центрального умения, утверждения «опирается на» с цитатой.
- **Временные навыки без темы** и временные навыки, у которых есть тема фокуса (4.5).
- **Все темы предмета** со статусами `proposed`/`active`, с описаниями и метками их центральных навыков; для временных навыков в теме — ещё и остальные навыки этой темы.
- **Похожие навыки других тем** по вектору (существующий `find_candidates`), чтобы ловить дубли между темами.

Полный список тем подаётся до порога `structure_full_list_max_topics = 80` (новая настройка). Выше порога — пока только предупреждение в лог с числом тем. Короткий список в этой задаче не делается.

**Выход модели** — закрытый выбор по коротким меткам (§4.5):
- **Для кандидата в тему:**
  - `link(T…)` — это существующая тема;
  - или `create`: имя, описание, центральный навык (`name`, `definition`, `exemplar`, `kind`);
  - плюс список «опирается на» — метки центральных навыков существующих тем, с оценкой от −1 до 1 и типом источника: `material` (есть цитата из входа) или `model` (знание предмета).
- **Для временного навыка:**
  - `same(S…)` — дубль, слить;
  - `keep` — оставить в его теме и дописать `definition`, `exemplar`, `kind`;
  - `move(T…)` — переместить в другую тему;
  - `core_of_new_topic` — создать тему, где этот навык станет центральным;
  - `other_topic_skill(S…)` — это умение другой темы: слить в него и поставить связь «нужно до».

**Код после ответа модели:**
- Проверяет метки (неизвестная метка — один возврат модели, как сейчас).
- Проверяет инвариант «один центральный навык».
- **Связи:**
  - не пишет связь с оценкой ниже настройки `structure_requires_min_score = 0.3`;
  - не пишет встречную связь, если обратная уже есть или идёт в той же пачке;
  - если для пары пришли обе стороны с положительной оценкой — отбрасывает обе;
  - не пишет связь, которая следует транзитивно из уже существующих (A→B→C — не писать A→C).
- Пишет события: `topic.created` с `description`; `skill.created` с `core`; `skill.merged`; `skill.placed`; `edge.added`.

**Повторы.** Ответ модели применяется через `append_unwritten` (`reconcile.py`), как в нынешнем шаге структуры. Повтор не падает на конфликте ключей.

**Пачки.** Не больше `structure_batch_size = 15` кандидатов в теме и временных навыков на вызов. Пачки идут по порядку, каждая видит результат предыдущей, и каждая записывается сразу, чтобы граф рос на глазах.

**Запуск** — по правилам диспетчера (`jobs/rules_p4.py`): после шага структуры материала, после `session.ended`, после появления временных навыков (как сейчас запускается гигиена), с задержкой-дребезгом.

**Промпт:** `prompts/builder/v2.md`. Режим Structure; правила Reconcile, Hygiene, Split, Topics переносятся без изменений смысла. Новые правила:
- центральный навык — действие, проверяемое одной задачей;
- инструмент (Excel и т.п.) — не навык;
- общие учебные умения — не навыки предмета;
- одна тема — одно центральное умение;
- «опирается на» — только пары, где без одного нельзя освоить другое; оценка числом от −1 до 1; без рассуждений в ответе.

### 4.3 Разбор материала

**`parse_step`** (`materials/parse.py`) остаётся: страницы, куски, задачи семинара, дедлайны силлабуса. Промпт `prompts/material_parser/v2.md`, на кусок:
- `section` — о чём кусок, свободный текст; `null`, если ни о чём (титул, литература);
- `builds_on` — на что текст прямо опирается: имя понятия плюс короткая цитата, только если опора сказана в тексте;
- задачи семинара и дедлайны — как сейчас.

**Убрать:** `teaches` и `uses` как источники навыков.

**Новый шаг «оглавление»** перед структурой — один вызов дешёвой модели на материал. Вход: все `section` кусков с номерами и первыми ~200 знаками текста каждого куска. Выход:
- список кандидатов в темы (имя, описание 1–3 фразы, имя центрального умения);
- для каждого куска — номер кандидата;
- для каждой задачи семинара — номер кандидата;
- утверждения «опирается на» с цитатой, сведённые по кандидатам.

Если кусков больше лимита одного вызова (настройка), оглавление строится частями, и последний вызов сводит части. Ни в каком правиле не используются номер файла, «неделя», «лекция» или порядок загрузки.

**Шаг структуры** отдаёт кандидатов писателю (4.2) и получает id тем и их центральных навыков. Потом, в одной транзакции, как сейчас:
- `chunk.indexed`, где навык куска — центральный навык его темы. Так поиск по материалам (`graph/read/materials.py`, связь `TEACHES`) продолжает работать.
- `material.parsed`, статус материала.
- Задача `material.seminar_tasks`: в спецификации каждой задачи `skill_id` — центральный навык её темы, плюс метки всех навыков этой темы (4.6).

**Удалить:**
- создание хаба «из материала» (`parse.py`, около 1063–1068) и `_topics_of_skills` для него;
- вызов `reconcile_domain` из `ops/material_parse.py` (`reconcile_subjects`);
- ожидание `_wait_for_older`. Порядок загрузки больше не важен, но последовательность по предмету сохраняется блокировкой.

**Оставить:** хабы и дедлайны из силлабуса (`_syllabus_events`, около строк 866–941).

### 4.4 Связи «нужно до»

**Где живут.** Только между навыками (`REQUIRES`), как сейчас. Связь между темами на графе выводится из связей их навыков (`graph/read/neo4j_reader.py`, `topic_requires`).

**Источники и уверенность.** Уверенность считает код, не модель.

| Источник | Как появляется | Уверенность | Косвенные свидетельства |
|---|---|---|---|
| `model` (знание предмета) | писатель, оценка ≥ 0.3 | `reconcile_requires_confidence["model"]`: поменять 0.65 → **0.5** | нет (ниже 0.6) |
| `material` (цитата из текста) | писатель, тип `material` | 0.85, как сейчас | да |
| `learner` | будущая правка ученика | 1.0 | да |

**Несколько источников у одной связи.**
- Ключ идемпотентности `edge.added` по связи: `requires:{a}:{b}:{origin}`. Нынешний ключ `requires:{a}:{b}` остаётся для старых событий.
- Проектор при `edge.added` на существующую связь ставит `confidence = max(старое, новое)` и добавляет `origin` в свойство-список `origins`. Пересборка из журнала даёт тот же результат: максимум не зависит от порядка.
- Новых вызовов модели для «подтверждения» нет: подтверждение — это просто ещё одно событие от другого источника, когда оно приходит.

**Чтение для графа.** `topic_requires` возвращает дополнительно `confidence = max(r.confidence)` по связям навыков между двумя темами. Добавить поле в модель `TopicRequires` и в ответ API графа. Перегенерировать OpenAPI: `uv run python -m quack.cli ops openapi --out <файл снимка>`, затем снимок фронтенда и `frontend/lib/api/schema.d.ts`.

**Фронтенд** (`frontend/components/quack/graph/layered-graph.tsx` и место, где рисуются рёбра тем). Прозрачность и толщина ребра по уверенности, например:
- 0.5 → прозрачность 0.35, тонкая линия;
- 0.85 → 0.8;
- 1.0 → 1.

Таблицу перевода держать в одном месте, константой. Других изменений графа нет.

### 4.5 Новый навык посреди сессии

**Тема фокуса хода.** Новое поле `focus_topic_id: UUID | None = None` в `turn.committed`. Его считает код сессии при записи хода (не модель, не проектор), по порядку:
1. `topic_id` последнего `message.sent` этой сессии, если есть;
2. иначе `topic_id` из `session.started`;
3. иначе тема последнего существующего навыка, размеченного в ходах этой сессии;
4. иначе `None`.

**Проектор** (`handlers.py`, `_Markup.skill_for`): у нового навыка без `topic_hint` при наличии `focus_topic_id` сразу создаётся `COVERS` от темы фокуса. Остальное как сейчас: один временный навык на нормализованное имя в предмете, свидетельства крепятся сразу. Без темы фокуса навык остаётся без темы до писателя, как сейчас.

**Промпт учителя** `prompts/teacher/v4.md`:
- правило: `new_skill` — только если отдельная проверка этого умения изменит, что учитель сделает дальше; иначе метка существующего навыка темы, в том числе центрального;
- в `new_skill` добавить необязательное поле `reason` — коротко, зачем отдельный навык. В `NewSkill` (`events/values.py`, около строки 169) добавить `reason: str | None = None`.

Поведение извлекателя не меняется: тема для его новых навыков уже передаётся.

### 4.6 Разметка задач — выбор из навыков темы

- **Генератор задач** (`agents/task_generation.py`, `prompts/task_generator`) и **задачи семинара** (`practice/seminar_tasks.py`) получают метки всех навыков темы задачи (центральный и остальные) через `LabelMap`. Сейчас в метках только один навык (`seminar_tasks.py`, `LabelMap.build(settings, skills=[task.skill_id])`).
- Правило в промптах: выбирать из меток; `new_skill` (с `reason`) — только если ни один не подходит.
- Новый навык из разметки задачи получает тему задачи (`COVERS` в проекторе, по тому же принципу, что 4.5), дальше его сверяет писатель.

### 4.7 Хабы

- Оставить: хабы с дедлайном из силлабуса, хабы по просьбе ученика (`new_hub_name`), хаб всего предмета.

### 4.8 Логи и отчёт для проверки в реальности

Новых таблиц нет: всё нужное лежит в событиях и `ops.llm_usage`.
- В событиях разметки (`turn.committed`, `task.created`) у нового навыка есть `reason`. Источник события виден по `actor`.
- Писатель пишет в лог (structlog) одну строку на вызов: число тем во входе, кандидатов, временных навыков, исходы (`link`, `create`, `same`, `keep`, `move`, `other_topic_skill`), число связей по источникам, отброшенных связей с причиной (оценка, встречная, обе стороны, транзитивная), токены.

**Команда отчёта** `uv run python -m quack.cli ops structure-report --learner <id> --domain <id>` печатает:
- темы: число, пустые (без навыков), без центрального навыка — оба числа должны быть 0;
- навыки на тему: распределение;
- новые навыки по источнику (учитель, генератор, семинар, извлекатель) и их судьба у писателя: слит, оставлен, перенесён;
- доля новых навыков, набравших хотя бы 3 свидетельства за 14 дней;
- связи: число по источникам, распределение уверенности;
- хабы по видам;
- стоимость по ролям за период из `ops.llm_usage`, в токенах и в долларах по таблице цен из настроек.

## 6. Тесты

Только затронутые; полный прогон — один раз перед PR. Тесты с базой — через `scripts/dev/test_infra.sh up K`, `scripts/dev/ct.sh K <файлы>`, `down K`. Два прогона на одном K одновременно запускать нельзя.

1. Каталог событий и образцы (`tests/events`): новые поля, старые события валидируются.
2. Проекция: `topic.created` + центральный `skill.created` → один `core` навык; `Topic.description`; `Skill.definition`, `exemplar`, `kind`; `edge.added` двумя источниками → `max confidence` и список `origins`; пересборка из журнала даёт тот же граф.
3. Писатель: закрытый выбор, неизвестная метка, инвариант центрального навыка, отбрасывание встречных, двусторонних, транзитивных и слабых связей, пачки, повтор без конфликта.

5. Горячий путь: `focus_topic_id` по четырём правилам; новый навык учителя получает тему фокуса; без фокуса — без темы.
6. `topic_requires` отдаёт `confidence`; снимок OpenAPI.
7. Слияние и деление тем: центральные навыки по инвариантам.
8. Фронтенд: `tsc`, `eslint`; вид рёбер разной уверенности на моках (скриншот).

## 7. Приёмка

На локальном стенде, в новом предмете:
1. **Те же 7 листов семинаров по статистике, в любом порядке:**
   - 0 пустых тем, у каждой темы ровно один центральный навык;
   - навыков после разбора = числу тем;
   - больше 0 связей, на графе видны рёбра разной яркости;
   - 0 хабов из материалов;
   - отчёт `structure-report` сохранить и приложить к PR.
2. **Повторная загрузка тех же файлов в другой новый предмет:** число тем отличается не больше чем на 20%, совпадающих имён тем (после нормализации) не меньше 70%. Привести обе цифры в PR.
3. **Предмет без файлов:** сессия с учителем по новой теме → появились тема и центральный навык. Новый навык, названный учителем, сразу стоит в теме фокуса. Писатель после сессии его сверил (видно в отчёте).
4. **Сравнение рядом со старой версией** на тех же семинарах — делает владелец, исполнитель даёт оба отчёта.
5. Стоимость разбора 7 семинаров по ролям из отчёта.
