Т-§2 · Т-§13

Ядро памяти: журнал, проекции, очередь

Журнал событий служит сразу источником правды и «исходящим ящиком». Два потребителя читают его по порядку номеров ученика: проектор строит граф, диспетчер ставит задачи. Результаты задач снова становятся событиями, так что петля замыкается через журнал.

СобытиеЗадача диспетчера
episode.closedизвлечение наблюдений
task.closed, session.endedаналитик границы
agent.requestedагент по поручению учителя
material.uploadedразбор материала
новый кусок, тема, навык, заблуждениеэмбеддинг на Modal

Почему так

  • Пересборка Neo4j из журнала не вызывает моделей и даёт тот же результат: оспаривание, смена правил, удаление и проигрывание — одна операция.
  • Без NOTIFY: глобальная блокировка при фиксации сериализовала бы записи. Пробуждение — Redis, страховка — опрос.
  • Своя очередь на Postgres (~300–400 строк) нужна ради допуска по лимитам модели: фоновая задача берётся, только если хватает лимита и остаётся место ходам учителя.
  • Одни обработчики во всех режимах: применение, полная пересборка, наложение сессии, состояние на момент N.

Граф памяти в Neo4j

У каждого ученика свой граф предмета; каждый узел несёт id (UUIDv5) и learnerId. Навык — единица измерения, к нему крепятся свидетельства. Текста сессий, штрихов, артефактов и очереди в графе нет.

Что помнимКак лежит в графе
Как устроен предмет ученикаDomain, Topic, Skill, Hub; связи REQUIRES и SAME_IDEA
Что он умеетСостояние навыка по трём осям свойствами на Skill
Почему мы так считаемEvidence с исходом, ярусом, классом проверки, цитатой и ссылкой на источник
Что ему показывалиExposure
Как он ошибаетсяMisconception: формулировка, статус, условия проявления, с чем путает
На чём он учитсяMaterial, Chunk с эмбеддингом, Task с разметкой
Какой он ученик и что сейчас важноProfile (явное и выученное), Digest — последняя сводка аналитика
П-§2 · П-§4 · П-§12

Продуктовый слой

Всё начинается с сессии. Темы возникают из сессий, хабы объединяют темы, дедлайн привязывает хаб ко времени. Модель ученика лежит под всеми доменами сразу.

Учитель действует из памяти (П-§4)

  • Новая сессия получает контекст из памяти, а не сырую историю прошлых сессий.
  • Ход выбирается по плану сессии и графу действий; ответвления ученика разрешены, ученика ничем не ограничиваем.
  • Защитные правила: не спойлерить, показывать только размеченные и проверенные задания.
  • Кнопки — шорткаты к намерениям, а не отдельная логика.

Вокруг учителя

  • Фоновые агенты не ведут ученика и не собирают контекст учителя; их результаты доходят как события.
  • Повторение встраивается в сессии, без завалов; «Сегодня» готовит рекомендации.
  • Компаньон: телефон снимает рукопись, SAM выделяет строки, строки летят в канвас по WS.
  • Контроль ученика: «не согласен» и «почему ты так считаешь» раскрываются до сырья через провенанс.
Т-§1.1 · принято

Десять законов ядра

Если решение в любом разделе противоречит закону, неверно решение.

1

Источник правды — журнал

Всё, что влияет на модель ученика, сначала пишется событием. Neo4j можно удалить и собрать заново.

2

Модель толкует, код считает

Уровни, удержание и статусы считает детерминированный код. Пересборка бесплатна и воспроизводима.

3

Один писатель на хранилище

В Neo4j пишет только проектор. Учитель, агенты и API пишут события.

4

Силу свидетельства назначает код

По виду источника и классу проверки. Одно суждение модели не ухудшает состояние ученика.

5

Идемпотентность

Детерминированные ключи: номер события, источник + версия извлекателя, id задачи. Повтор заменяет запись.

6

Провенанс

Любое свидетельство раскрывается до места в сырье: сообщения, строки канваса, попытки задачи.

7

Сбой фона ничего не фиксирует

Фоновая работа применяется целиком или никак и не трогает ход учителя.

8

Отсутствие не равно нулю

«Не проверено» — явное значение 'unknown', а не null и не провал.

9

Горячий путь не ждёт фон

Учитель отвечает по разговору и последней проекции с наложением событий текущей сессии.

10

Никакого накопления выводов

Сводка для учителя каждый раз собирается заново из структуры, без прошлой сводки на входе.

Отвергнуто и почему

  • Kafka / Redpanda — второй журнал с двойной записью и тяжёлый сервис на 12 ГБ.
  • Celery, RabbitMQ, очереди на Redis — задача и породившее её событие оказались бы в разных системах.
  • Только Postgres — почти каждый запрос памяти это обход графа плюс вектор с фильтром по ученику. Только Neo4j — журнал и очередь не графовые данные.
  • ORM, Alembic — ключевые запросы держатся на SKIP LOCKED, ON CONFLICT, частичных индексах. Chat Completions — не переносит рассуждение между шагами с инструментами.

D-§5–§12

Эксплуатация

CI собирает два образа (quack-backend, quack-compute) под linux/amd64; сервер ничего не собирает, только скачивает готовое.

Сборка, выкатка, конфиг

  • Проверки CI: тесты, миграции, изоляция учеников; интеграционные тесты репозиториев на настоящем Postgres (testcontainers).
  • Миграции dbmate отдельным контейнером migrate при выкатке; squawk ловит блокирующие ALTER.
  • Окружения: local (тот же compose + override), CI (GitHub Actions), prod (VPS + app.qvack.online), preview.qvack.online против prod API, PR-превью на *.vercel.app без входа.
  • Домен qvack.online: DNS в Cloudflare без проксирования, TTL api ≤ 300 с.

Данные и восстановление

  • Бэкапится только Postgres: дампы в R2, шифрование age, две локальные копии. RPO ≤ 6 ч.
  • Neo4j восстанавливается пересборкой из журнала, в Redis долговечного нет.
  • Удаление: журнал удалений в R2 и ежедневная сверка.
  • Наблюдаемость: бюджеты teacher_ttft_p95_ms, verdict_p95_ms, projector_lag_p95_ms; тревоги по диску 75% и 90%.
